## Purpose
Two of these break the rule AGENTS.md calls void-making: **exactly one model resident** (S5-F3: a start checks only
its own port; S5-F5: an engine is unrecorded for its whole load, so a backend killed mid-load leaves a detached
engine no launch recovers). The rest let a recycled pid either get signalled (Stop now on a stale ledger file,
Handle.stop on a reaped launcher, the Swift `kill`) or wedge a lock or ledger forever (pid-only liveness, EPERM read
as alive). The handoff of 2026-11-15 already chose the shape: **one identity check, every caller.**

already green, kept as a regression); one new Swift test; `docs/interfaces/v5-app.md` (Stop now now reaches a loading
engine; the ledger has no `stop_command`); `05-09-SUMMARY.md`.

## AC-1: One definition of "the same process" (S1-F2, S5-F4 half)
```gherkin
Given a pid and the identity recorded for it (start time + argv), or no identity
When any caller asks whether that pid is still the recorded process
Then one function in runtimes.py answers: the pid exists and is signallable by this user (EPERM means "not ours",
     never "alive"), and, when an identity was recorded, `ps` reports the same start time and argv now
And `ps` for identity runs with `LC_ALL=C` and `TZ=UTC`, so the same process renders the same string in a CLI shell,
     under launchd and across a DST change
And `_stop_orphan`, `stop_orphaned_engines`, `stop_own_engines` and fetch's lock all call it; no second identity
     comparison remains (grep proves it)
```
<!-- audit-added --> **One liveness definition too.** `same_process` asks `_process_alive` first (so it inherits the reap
and AC-7's reaped set), then whether the pid is this user's (`kill(pid, 0)` without `PermissionError`), then the
identity. `fetch._pid_alive` is deleted. `_process_alive`'s own EPERM→alive answer is unchanged for engine checks
(a resident engine of another user still blocks a start); the docstring of `same_process` says why the two differ.
This process's own identity is read once and cached (one `ps`, not one per ledger write).

## AC-2: A ledger file belongs to the process that wrote it, not to its pid (S1-F1, S1-F2b)
```gherkin
Given each ledger file now records its owner's pid and identity beside its entries
When the startup sweep reads a file
Then the file is live-owned only when its owner identity matches a live process; a recycled owner pid, an owner with
     no recorded identity whose pid is not this user's, and a file named for this process's own pid but written by
     an earlier process are all orphans and are swept
And a file whose owner is this process (identity matches) or a live CLI grid is never read or touched
And `_record_running_engine` never merges entries from a file this process did not write
And <!-- audit-added --> such a file is never silently discarded either: its entries go through the same orphan
     handling as the startup sweep (stop when proven, keep-and-report when unprovable per AC-3) before this process
     writes its own file. A CLI grid never runs the startup sweep, so dropping them would lose the only claim on a
     live engine
And "Stop now" (`stop_own_engines`) signals only entries in a file whose owner identity is this process, and only an
     engine pid whose recorded identity still matches (belt and braces)
```

## AC-3: An unprovable orphan is kept and reported, not deleted (S5-F4)
```gherkin
Given a dead owner's entry
When the port cannot be read, or the recorded pid is alive but its identity cannot be proved
Then nothing is signalled, the ledger file is kept for the next launch, and one stderr JSON line with
     `LEDGER_ERROR_CODE` names the pid and port
And when a stranger holds the port, or nothing recorded is alive and nothing listens, the entry is dropped as today
     (S5-F4 control test stays green)
And <!-- audit-added --> the stderr line says which of the two reasons applied (port unreadable / identity unproven),
     so a kept file can be explained from the log alone
```

## AC-4: The ledger never stores a command to execute (S5-F13)
```gherkin
Given a ledger entry with any `stop_command` field
When Stop now or the orphan sweep stops it
Then the stop command is derived from `RUNTIMES` by the entry's recorded port (one helper), the field on disk is
     ignored, and new entries no longer write it
And an entry on a port no runtime owns is stopped by signal only
```

## AC-5: An engine is in the ledger from its spawn (S5-F5)
```gherkin
Given `Runtime.start` has spawned an engine and is awaiting readiness
When the backend is killed, or Stop now is pressed, during the load
Then the ledger already names the spawned pid, its identity, its port (written right after `_spawn`, before
     `await_ready`)
And after readiness the same entry gains `serving_pid` and its identity (replace by pid, no duplicate)
And `cold_load_s` still excludes the ledger's `ps` and write time (05-07 AC-4): the write is timed and subtracted,
     with a test that a slow ledger write does not move `cold_load_s`
     <!-- review-amended 2026-11-16 --> **Superseded at review:** subtracting is wrong, because the engine keeps
     loading while the write runs, so it under-reports the load. The early write is one `ps` plus a file and is not
     subtracted. Settling an earlier process's file (which may stop an engine) runs before the clock starts, with a
     test. Identity is compared by start time, since an `exec` from a launch script changes argv.
And a ledger write failure is one stderr line and the start goes on, as today
And <!-- audit-added --> when the start fails and its cleanup `_shutdown` succeeds, the early entry is forgotten; when
     cleanup fails, the entry stays so the next launch can recover the engine. A test covers both
And `docs/interfaces/v5-app.md` no longer says Stop now does nothing before the entry exists
```

## AC-6: The download lock: no steal, no wedge (S1-F2a, S4-F13)
```gherkin
Given `download.lock`
When `_acquire_lock` finds it
Then a lock naming a live owner with matching identity is busy; a bare-pid lock (legacy, and the existing tests)
     is busy only when that pid is alive and this user's (pid 1 → reclaimed; this process → busy; 999999 → reclaimed)
And an empty or unparseable lock younger than one named constant (seconds, by mtime) is held — the live owner's
     create/write window — and an older one is reclaimed
And the lock records pid + identity; `_release_lock` still removes it only while it names this process
And the existing `tests/test_fetch.py` lock tests pass unmodified
```
