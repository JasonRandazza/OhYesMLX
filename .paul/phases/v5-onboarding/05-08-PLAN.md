## Purpose
S3-F1 means the app has never received a single `progress`, `result`, `error` or `done` event over the real
transport. Every job stays `.running` and holds the one slot. It is the reason the live Phase 5 checks
(Stop now, a real download) cannot run yet, and the UI tests missed it because they inject a fake line
stream. The rest are races and wrong-owner bugs around the one-job slot, quitting, and relaunching. Each one
can strand the app, or lose or overwrite a result, in ways a user cannot recover from without a terminal.

## AC-12: The backend owns the single-instance lock (S3-F8)
```gherkin
Given an app that crashed or was force-quit while its backend is still unwinding
When the app is launched again
Then the new launch reports already-running (or "still finishing") until the old backend has exited, and never runs two backends at once
```
Test: `FableS3F8Tests`. Design (coordinator, 2026-11-16): the backend takes the exclusive `flock` on
`<App Support>/OhYesMLX/app.lock` itself, before it prints the launch line. If it cannot take the lock, it prints a
one-line JSON refusal and exits non-zero, and the launcher maps that refusal to `.alreadyRunning`. The app no longer holds
the lock across the child's life. Its own pre-spawn check stays only as a fast path for activating the running
app. `docs/interfaces/v5-app.md` P5-7 is rewritten to state the new owner.
<!-- audit-added --> **Two refusals are told apart.** When the refusal comes and no other app instance is running
(activation by bundle id finds none), the app does not exit silently. It shows "The previous session is still
finishing" with **Check again**, because the lock is held by an orphaned backend that is still unwinding. "Already
running" plus activation is kept for a live second app. The refusal line carries the holder's pid, read from the lock
file's contents, which the backend writes after it locks.
<!-- audit-added --> **The lock never outlives the backend through a child.** The lock descriptor is non-inheritable
(`os.open` default, asserted in a test). Engine servers the backend spawns, which may be orphaned, must never hold
`app.lock`, or the app could never start again.
<!-- audit-added --> **One lock path.** The backend derives it from `ohyesmlx.app_support_dir()` (the existing
definition), and the launcher passes its own `appSupportDirectory` to the child (environment or argument), so a test
or scratch launch locks its own directory and never the real one.

## AC-14: The job slot is freed when the job thread returns (S1-F5, S1-F6)
```gherkin
Given a download whose done event is emitted before its ledger write and lock release, or a job that hits MAX_EVENTS and keeps running
When a second job is requested before the first job's thread has returned
Then it is refused busy; the slot is freed in _run_job's finally, and a quickbench that hits the cap gets abort_requested
```
<!-- audit-added --> **`done` means the slot is free.** The module's `done` event is held by the server and
published to the stream only after `_run_job`'s cleanup has freed the slot. Otherwise a client that starts the next job
the moment it sees `done` (which the app does after S3-F5) is refused `busy` in the window between them. A test starts a
second job from the first job's `done` callback and gets 202.
Tests: `tests/test_fable_s1_f5.py`, `tests/test_fable_s1_f6.py`.
