<acceptance_criteria>

## AC-1: Schema is validated, errors name the model and field
Given a catalog file
Then each entry requires: `repo` (org/name), `title`, `params` (int, base model), `format` (str), `modality` ("text"|"vision-language"), `license` (str), `tier` ("starter"|"standard"), `revision` (40-hex commit sha), `size_bytes` (int, equals the sum of `files[].size`), `files` ([{path, size, sha256}] all LFS files carry a 64-hex sha256), `engines` (subset of the five engine names), `measured_here` (bool), `notes` (str); a violation raises ValueError naming file, repo and field (drive the loader with a tmp path)

## AC-2: The seed is exactly the approved set
Given the shipped catalog
Then starter tier = the research table rows 1-8 and 10-11 (Qwen3-0.6B-4bit, Qwen3.5-0.8B-4bit, Qwen3.5-0.8B-OptiQ-4bit, LFM2.5-1.2B-Instruct-4bit, granite-4.0-h-1b-4bit, Qwen3.5-2B-4bit, RepublicOfKorokke/Qwen3.5-2B-oQ4, LFM2.5-2.6B-4bit, SmolLM3-3B-4bit, Llama-3.2-3B-Instruct-4bit) each with size_bytes <= 2 GiB; standard tier = `mlx-community/Qwen3.5-4B-4bit` (measured here) and `mlx-community/LFM2.5-8B-A1B-MLX-4bit` (measured here); gemma-4-e2b is NOT in the seed (3.58 GB, no live row)

## AC-3: Nothing gated, nothing unverified
Given every entry
Then `gated` is false at build time (recorded in a build note, not a field), and `engines` lists only engines the research table marks as able to serve it; `measured_here` is true only for the two standard-tier rows

## AC-4: Pinned and reproducible offline
Given the catalog
Then `revision` and per-file sha256/size come from the Hugging Face API tree listing at one revision per repo, so a downloader never asks "what is latest"; the build date is recorded once at the top of the file

## AC-5: Shipped in the package
Given a wheel/sdist build
Then `catalog.json` sits inside `ohyesmlx/` like `engines-tested.json` (no hatch force-include)
</acceptance_criteria>
