<objective>
## Goal
Run the v5.0 backend (`ohyesmlx app`) as `oymlxtest`, a standard user with no engines, no models and no
OhYesMLX state, and drive every API surface a first-time user reaches. This closes the item carried since 04-01:
`GET /engines` has never listed a real install plan for a genuinely absent engine, because everything is
installed on Jason's account. It is also the first time the 045-02a/02b fixes run on an account they were not
developed in.

## Purpose
Phase 5 hands this backend to people who never open a terminal. The account the backend has been developed in
hides every "works because it is already there" defect: an installed engine, a warm HF cache, a lab path, a
pip config, a Python on PATH. A fresh account removes them all at once.

## Output
- `scripts/smoke_clean_account.sh` (setup, run, teardown as Jason, using `sudo -n -u oymlxtest`) and
  `scripts/smoke_clean_account.py` (stdlib client run as oymlxtest: it spawns `ohyesmlx app` the way the Swift
  client will, reads the launch line from the child's stdout, and drives the API). The model repo id it
  downloads is written in the script (AGENTS.md "Downloads need a reason and a record").
- A results JSON per run under `/Users/Shared/oymlx-smoke/results/`, one entry per check with PASS/FAIL and
  evidence. Copied into the SUMMARY verbatim where it matters.
- Every defect the smoke finds is fixed test-first in this plan, recorded in the SUMMARY and, when it is a
  security property, in `docs/threat-model.md`.
- The host fetch ledger's scratch-residue entry removed (Jason, 2026-11-13).
</objective>

## AC-1: Setup builds what a user gets, not the working tree
Given `HEAD` with a clean tree
When the setup step runs
Then the package is a wheel built from `git archive HEAD`, installed `--no-deps --no-index` into a venv in
oymlxtest's home made with `python3.14 -I -m venv`, and every later step runs that venv's python with `-I`
under `env -i HOME=/Users/oymlxtest USER=oymlxtest PATH=/usr/bin:/bin:/usr/sbin:/sbin` (launchd's default, P5-9).
Before anything runs, the preconditions hold or the script exits non-zero naming the one that failed:
`sudo -n -u oymlxtest true`; no listener on 1337/8000/8080/8081/8100/8200; the Osaurus app is not running
(matched by full executable path `^/Applications/osaurus.app/Contents/MacOS/osaurus`, never by name);
`xcode-select -p` succeeds (optiq builds pygame from source); ≥ 5 GiB free; oymlxtest has no
`~/Library/Application Support/OhYesMLX` and no `~/.cache/huggingface/hub/models--mlx-community--Qwen3-0.6B-4bit`.

## AC-2: The backend starts the way the app will start it
Given the client spawns `ohyesmlx app` with a stdin pipe it holds open
When the child prints its launch line
Then the client reads port and token from the child's stdout only (P5-2), stdout carries exactly that one line,
and `~/Library/Application Support/OhYesMLX` exists with mode `0700` (P5-5).

## AC-3: Read endpoints describe a fresh Mac
Given the running backend
When the client calls `GET /hardware`, `/engines`, `/recommendations`, and `/quickbench/plan?repo=<model>`
Then the first three answer 200 with the pinned shape, and `/quickbench/plan` answers `400 bad_args` naming
"download it first" (`quickbench.py:279-283`; the model is not downloaded yet — AC-5 repeats it after download); `/engines` reports mlxlm and optiq not installed, each with a
non-null install plan whose pip step carries `--require-hashes`, `--isolated` and `--only-binary :all:` and a
constraints path inside the installed package; the app engines' state is recorded as observed. **No response
body contains `/Users/jrazz`.** A request without the token is refused (`401`-class per interfaces.md).

## AC-4: Hash-pinned installs succeed on a clean account
Given consent (`confirmed: true`)
When the client posts `install` for `mlxlm`, then for `optiq`, and follows each job's SSE stream to `done`
Then both end in success; `lab-paths.json` under oymlxtest's Application Support names both venv `bin`
directories; each passes `engines.check_lab_dir`; `GET /engines` now reports both installed. optiq's plan carries
`--no-binary pygame` (the source-build exception), and the results JSON records the client-observed interval
from each job's first to last SSE event.

## AC-5: Download, quickbench and evict work end to end
Given both pip engines installed
When the client downloads `mlx-community/Qwen3-0.6B-4bit` (HTTPS from the clean account, P5-4 against Homebrew
Python), runs `quickbench` on it with `osaurus: false`, then evicts it
Then the download succeeds into oymlxtest's HF cache with its ledger in oymlxtest's Application Support;
`GET /quickbench/plan` now answers 200 with the pinned shape; quickbench reports mlxlm and optiq cells PASS the coherence gate (app engines: PASS, skipped with a stated
reason, or FAIL recorded with its evidence — AC-1 frees their ports, so oMLX and vMLX do run); after evict the model directory and its ledger entry are gone.

## AC-6: Shutdown leaves nothing behind
Given the backend idle
When the client closes the child's stdin
Then the child exits 0 within 10 s, no port in AC-1's list is held, and a `pgrep -lu oymlxtest` snapshot equals
the one taken before setup. The .sh installs a `trap` (EXIT/INT/TERM) that closes the child's stdin, waits,
then sweeps any oymlxtest-owned engine process left listening on an AC-1 port, so a crash mid-quickbench
leaves no model resident.

## AC-7: Jason's account is untouched
Given snapshots taken before setup
When the smoke ends
Then `~/Library/Application Support/OhYesMLX` (listing + mtimes + `cmp` of `lab-paths.json` and `fetched.json`),
`~/.cache/huggingface/hub` (top-level listing), and `~/.osaurus/config` (`cmp` per file) are identical to their
snapshots, except for the ledger change in AC-9 made by the coordinator outside the smoke.

## AC-8: Findings are fixed, not just noted
Given any check fails for a defect in the code (not in the environment)
When it is found
Then it gets a red test, a fix, a green full suite, and a re-run of the failing check; it is listed in the SUMMARY
with file:line, and in `docs/threat-model.md` if it is a security property. An environment failure (network,
Apple CLT missing) is recorded as such and not "fixed" in code.

## AC-9: The host ledger's scratch residue is gone
Given the real ledger's one entry (`mlx-community/Qwen3.5-2B-4bit`, 60 paths under 2026-11-03 scratch caches)

Then the ledger has no entry naming a path outside the real HF cache, the backup is kept beside the SUMMARY's
evidence, and the 16 leftover scratch files are left alone (they are under `/private/tmp`, cleared at reboot).
