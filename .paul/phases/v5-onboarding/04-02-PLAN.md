<objective>
## Goal
The server accepts `POST /jobs` for `install`, `download` and `evict`, runs one job at a time on a background
thread through the existing consent-gated module functions, and streams each job's events over
`GET /jobs/{id}/events` (server-sent events), with `POST /jobs/{id}/cancel` for a download.

## Purpose
Seam S6, ticket T4.3. These are the first endpoints that change the user's Mac: they install software, write
gigabytes into the Hugging Face cache and delete files. The modules already carry the consent gates, locks and
rollback (02-03, 03-03); the server must add nothing that weakens them and nothing that duplicates them. The
attack this plan is shaped against is a web page or local process that gets a request through: install and
download take an engine or repo NAME only (never a command, URL or path), and require `"confirmed": true`.

## Output
Job routes in `ohyesmlx/server.py`, tests against a real server with fake module seams, the pinned job, event
and error shapes in `docs/interfaces.md`.
</objective>

<acceptance_criteria>

## AC-1: POST /jobs takes names, never commands
```gherkin
Given an authorised `POST /jobs` with `Content-Type: application/json` and a body of at most 4,096 bytes
When the body is {"kind": "install", "args": {"engine": <name>, "confirmed": true}},
 {"kind": "download", "args": {"repo": <catalog id>, "confirmed": true}} or
 {"kind": "evict", "args": {"repo": <id>, "confirmed": true}}
Then 202 with {"job_id": str} (`secrets.token_hex(8)`) and the job starts on a background thread
And `args` must have exactly those keys with those types: an extra key, a missing key, a non-string name, or
 `confirmed` that is anything but JSON `true` (not "true", not 1) is 400 `bad_args` naming the key, and no job starts
And an unknown `kind` is 400 `bad_kind`; a non-JSON content type 415 `unsupported_media_type`; a missing or
 non-integer Content-Length, or one over 4,096, 413 `body_too_large` (the body is not read); invalid JSON 400 `bad_json`
And `quickbench` is 400 `bad_kind` until 04-03 lands
```

## AC-2: The module owns every rule the job runs
```gherkin
Given an accepted job
When it runs
Then it calls exactly `engines.install(name, True, macos_major=<from scan>, emit=...)`,
 `fetch.download(repo, True, emit=..., cancel=...)` or `fetch.evict(repo, True, emit=...)`
And the server validates no engine name, repo id, version, path or disk number itself: an unknown name is the
 module's own refusal (`unknown_engine`, `unknown_repo`), delivered as the job's `error` and `done` events
And a module that raises appends {"type": "error", payload {"code": "internal"}} and {"type": "done"} events
 continuing the job's `seq`, so a stream always ends
```

## AC-3: One job at a time
```gherkin
Given a job that has not emitted `done`
When another `POST /jobs` arrives (any kind)
Then 409 `busy` with the running job's id in the message, and no second job starts
And the slot frees the moment the running job's last event is stored
```

## AC-4: The event stream
```gherkin
Given an authorised `GET /jobs/{id}/events`
Then 200 `Content-Type: text/event-stream`, `Cache-Control: no-store`, each event written as
 `id: <seq>\ndata: <event JSON>\n\n` in seq order, starting after the `Last-Event-ID` request header when given
And events already stored are replayed first, then new ones as they arrive; while nothing arrives a `: keepalive`
 comment is written every 15 s; after the `done` event the server closes the connection
And an unknown job id is 404 `unknown_job`; a stream of a finished job replays everything and closes
And the 10 s handler timeout bounds reading the request only: a stream that waits minutes for the next event is
 not cut off (test with an injected short timeout and a slow fake job)
And at most 10,000 events are kept per job; past that the job is ended with `error` `too_many_events` and `done`
```

## AC-5: Cancel a download
```gherkin
Given a running download job
When `POST /jobs/{id}/cancel`
Then 202, the `cancel` callable handed to `fetch.download` answers True from then on, and the stream ends with
 the module's own cancelled `error`/`done`
And cancel on an install or evict job is 409 `not_cancellable`; on a finished job 409 `job_finished`; unknown id 404
```

## AC-6: Shutdown does not abandon a job silently
```gherkin
Given a running job when stdin reaches EOF or SIGINT/SIGTERM arrives
Then a download is cancelled, an install or evict is waited for, for at most 120 s, and then the server exits 0
And each job start writes one stderr JSON line {"job": id, "kind", "name", "time"} (never a token or header)
```

## AC-7: Nothing weakens 04-01
```gherkin
Given any request to a job route
Then the 04-01 guard runs first, unchanged; job routes add no CORS header and no new way past the token
```
