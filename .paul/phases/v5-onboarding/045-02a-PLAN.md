<objective>
## Goal
Fix eight findings approved at the 045-01 triage (Jason, 2026-11-03), each test-first:

- T-02 (medium): an interrupted app leaves the machine in a state that nothing reports or recovers.
- T-03 (medium): the backend writes inside its own package tree.
- T-04 (medium): the job slot can leak for the life of the process.
- T-05 (medium): an Osaurus pin clobbered mid-cell is still reported as pinned.
- T-08 (low): unbounded handler threads and SSE streams.
- T-09 (low): bare command names on a lab-prefixed PATH, and no timeout on the hardware scan.
- T-10 (low): Application Support is created with umask modes.
- T-11 (low): the refusal log writes the raw path.

Each fix commit moves that finding's withheld detail from `045-01-findings-private.md` into
`docs/threat-model.md` §7.

## Purpose
These are the server and app-lifecycle half of plan 045-02. The installers and fetch half is 045-02b; Jason chose
the two-plan split on 2026-11-03. Phase 5 wraps this backend in a double-click app for users who never open a
terminal, so every way it can leave their Mac wrong without saying so has to be closed first.

## Output
Code and tests for the eight findings; a §9 row recording the residual availability risk of the thread cap (a local
account filling the 32 slots delays the app's own requests until the 10 s timeouts free them; the slot leak T-04 is
what made that permanent, and it is closed) <!-- audit-added: strongly-recommended -->; `docs/interfaces.md` updated for every changed contract;
`docs/threat-model.md` §7.3 rows for T-02, T-03, T-04, T-05, T-08, T-09, T-10 and T-11 marked fixed, with
their detail published.

## AC-1: One writable root, outside the package tree for an installed app (T-03, T-10)
```gherkin
Given `ohyesmlx/__init__.py` defines, once, `app_support_dir(home=None)` (`~/Library/Application Support/OhYesMLX`)
 and `writable_root()` (the repo root when `<package parent>/.git` exists, else `app_support_dir()`)
And `engines`, `fetch` and `quickbench` derive every Application Support path from `app_support_dir`, while
 `osaurus_settings.BASELINE_PATH` and `runtimes.LOGS_DIR` derive from `writable_root()` (the same relative
 subpaths, `config/osaurus-settings-baseline.json` and `results/logs`)
When the package is run from this repo checkout
Then both paths are byte-identical to today's, so no harness run, canary or published table changes
When the package tree is not a checkout (a test simulates it by monkeypatching the `.git` probe and making the tree read-only)
Then an Osaurus pin round-trip and an engine spawn write only under the scratch Application Support
And `ensure_app_support()` creates the directory with mode 0700, or tightens an existing one to 0700, and both
 `ohyesmlx app` and `ohyesmlx quickbench` call it before their first write
```

## AC-2: The job slot cannot leak (T-04)
```gherkin
Given a `POST /jobs` that has claimed the slot
When anything raises before the job's thread is running (the start log line, or `Thread.start`)
Then the job stores `error` (code `internal`) and `done`, which frees the slot, and the response is 500
And the next valid `POST /jobs` is accepted (202), not `409 busy`
```

## AC-3: Threads and streams are bounded (T-08)
```gherkin
Given `MAX_HANDLER_THREADS` (32) and `MAX_STREAMS_PER_JOB` (4), each named once in server.py
When a connection arrives while the handler-thread limit is reached
Then it is closed at once without a response and without starting a thread, and the server keeps serving
And the slot is released when a handler ends by any path (normal, exception, socket timeout); a test drives
 MAX_HANDLER_THREADS + 1 connections, lets them time out, and then gets a 200 <!-- audit-added: strongly-recommended -->
When a fifth `/events` stream is opened on one job while four are open
Then it gets `429 too_many_streams`, and the four keep streaming
And `docs/interfaces.md` lists the new code and both limits
```

## AC-4: The refusal log never writes a raw path (T-11)
```gherkin
Given a refused request
Then its stderr line carries the path only when it is a served route (`/hardware`, `/engines`,
 `/recommendations`, `/quickbench/plan`, `/jobs`, or the `_JOB_PATH` pattern), and `<unknown>` otherwise
And a test sends a refused request whose path segment is the token and asserts the token is not on stderr
```

## AC-5: System tools are called by absolute path, and the scan has a timeout (T-09)
```gherkin
Given `ps`, `sysctl`, `sw_vers`, `ioreg` and `open` calls in runtimes, quickbench, hardware and engines
Then each argv[0] is the absolute macOS path (`/bin/ps`, `/usr/sbin/sysctl`, `/usr/bin/sw_vers`,
 `/usr/sbin/ioreg`, `/usr/bin/open`), each spelled once and imported by the other callers
And `hardware._run` has a timeout (10 s, named once); a hung call raises, and `/hardware` answers 500 rather than hanging
And a test with a PATH holding a fake `ps` shows the fake is never executed by `_resident_osaurus_pids`
```

## AC-6: An interrupted app is recovered at the next launch (T-02)
```gherkin
Given `ohyesmlx app` starting up, before it prints the launch line
Then, only when the Osaurus app is not running (`quickbench._osaurus_app_running()`, the same check a cell uses,
 because a running Osaurus app may rewrite the files being restored), it calls `osaurus_settings.recover` with
 quickbench's backup directory and baseline path; a recovered pin writes one stderr line
 ({"recovered": "osaurus", ...}) and no stdout; with the app running and a backup present it writes
 {"recovery_pending": "osaurus", "backup_dir": ...} and leaves the backup for the next start or Osaurus cell
 <!-- audit-added: must-have -->; a recover that raises or does not verify is one stderr line and never stops the
 server from starting
And it stops engine processes a previous harness process started and left behind: `runtimes` records each
 spawned pid with its port, argv and process start time (`/bin/ps -ww -o lstart=,args= -p <pid>`) in one file per
 owner process, `<writable_root>/results/running-engines/<owner pid>.json` (written atomically, entry removed on
 stop, file removed when empty), so two harness processes never read-modify-write one file
 <!-- audit-added: strongly-recommended -->; at startup a file whose owner pid is dead is read, and an entry whose
 pid is alive with the SAME start time and argv has its process group stopped (TERM, then KILL after the existing
 grace); a file whose owner is alive (a grid running from the CLI) is never touched; an entry whose start time or
 argv differs (a reused pid, or the user's own identical command started later) is dropped and never signalled
 <!-- audit-added: must-have -->
And the ledger is written AFTER `cold_load_s` is computed (`runtimes.py:2012`), never between spawn and
 readiness, so no measured load time includes it; a test asserts the write happens after the timestamp is taken
 (e.g. a fake clock and a fake ledger writer recording call order) <!-- audit-added: must-have -->
And an install's pip step runs in its own process group (`Popen(start_new_session=True)`, registered while it runs);
 when `cancel_and_wait` passes its 120 s bound, the server kills the registered groups and waits at most
 `JOB_KILL_GRACE_S` (15 s) more for the job's own rollback and `done`
And `.incomplete` download files are NOT swept: they are fetch's resume state (045-01 T-02(d) is withdrawn; recorded in the SUMMARY)
```

## AC-7: A mid-cell Osaurus change fails the cell and keeps both copies (T-05)
```gherkin
Given an Osaurus quickbench cell that pinned successfully
When, after `run_cells` and before `restore`, `diff_against_baseline(capture_osaurus_settings(), load_baseline(baseline_path))` reports drift
Then the cell is FAIL with reason "Osaurus changed its settings during the run: " + `describe_drift(...)`
And the two current config files are copied byte-exact into `<backup_dir>/during-run/` (0700) before `restore` runs,
 and the summary names that directory, so a change the user made mid-run is not lost
And with no drift, nothing changes from today's behaviour (the existing quickbench tests pass unmodified)
```
