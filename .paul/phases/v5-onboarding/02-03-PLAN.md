<objective>
## Goal
`engines.install(engine, confirmed, ...)` takes an engine NAME, derives the Plan itself via 02-02, and executes it only after explicit consent, emits progress events, and reports failure without leaving silent partial state.

## Purpose
Seam S3. The consent gate is the safety property: no step runs before `confirmed` is true.

## Output
Installer in `engines.py`, tests with a fake runner, per-engine smoke notes.
</objective>

<acceptance_criteria>
## AC-1: Consent gate
Given `confirmed=False`
Then zero steps run, zero events except an error `consent_required`

## AC-2: Ordered execution with progress
Given a two-step command plan and a fake runner
Then steps run in order, a progress event with a fraction follows each, and `done` is last

## AC-3: Failure stops and reports
Given step 2 fails
Then step 3 never runs, an `error` event carries the step id and output tail, and a venv created by step 1 is removed

## AC-4: Guided download
Given a `guided_download` plan
Then the installer opens `source_url` through the injected opener, then polls detection (02-01) until installed or a timeout, and emits `result`

## AC-5: Bundled-Python venvs
Given command plans
Then the interpreter used to create venvs is injected (the bundled Python per D6; sys.executable in dev), never the system python3

## AC-6: The caller cannot supply commands <!-- audit-added: must-have -->
Given the signature `install(engine: str, confirmed: bool, ...)`
When a caller passes anything that is not one of the five engine names
Then it raises before any step runs; no `Plan`, argv or URL from the caller is ever executed (a local web page POSTing to the localhost API must not be able to run arbitrary commands)

## AC-7: Never touch what it did not create <!-- audit-added: must-have -->
Given an engine already detected as installed (02-01), or an engines-dir venv that existed before the call
When `install` runs
Then an already-installed engine is refused with `already_installed` (no overwrite, no reinstall), and rollback (AC-3) removes only paths this call created, only inside the engines dir, never following a symlink out of it

## AC-8: Bounded steps and bounded output <!-- audit-added: must-have -->
Given a step that hangs or prints without end
Then each step has a timeout (default 900 s) after which it is killed and reported as an `error` with step id; captured output is capped (tail 4 KB) in events; guided-download polling has its own timeout and ends in `result` with `installed: false`, not an error

## AC-9: URLs and argv are constrained <!-- audit-added: must-have -->
Given a plan
Then `open_url` is called only for an `https` URL whose host is on a short allowlist in `engines.py` (github.com, pypi.org, docs/vendor hosts named in the research), steps are argv lists (never a shell string), and no step uses sudo

## AC-10: Local install log <!-- audit-added: strongly recommended -->
Given any install attempt (allowed, refused, failed or done)
Then one JSON line per event is appended to `~/Library/Application Support/OhYesMLX/install-log.jsonl` (injected path in tests) with engine, UTC time, consent flag, step id and exit code; the log is local only and never uploaded (D8). A plain append-only file, not a governance layer.

## AC-11: One install per engine at a time; disk checked first <!-- audit-added: strongly recommended -->
Given a second `install` for the same engine while one runs
Then it is refused with `busy`. Given free disk (hardware.scan) below 2x `size_bytes_estimate`, then it is refused with `low_disk` before any step runs; an unknown estimate uses a 2 GiB floor.

## AC-12: pip runs hermetically <!-- audit-added: strongly recommended -->
Given the pip engines' steps
Then they run with `--no-input --disable-pip-version-check`, an env that drops PYTHONPATH/PIP_* inherited values, and install only into the new venv
</acceptance_criteria>
