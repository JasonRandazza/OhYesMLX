# Enterprise Plan Audit Report

**Plan:** .paul/phases/v5-onboarding/055-02-PLAN.md

**Verdict:** conditionally acceptable (upgrades applied)

## 1. Executive Verdict

The plan is conditionally acceptable. All three items copy patterns the codebase already has:
- `consentRequest`, for the evict request.
- `anotherInstanceIsRunning`'s pid filter, for the second launch.
- `disk_bytes_at`'s probe, for the volume field.

Each fix has a pure, testable core. The gaps were edge states (a failed disk probe, a job already running) and constructor churn.

## 2. What Is Solid

- **The evict request goes through the same sheet and `evicting` state as Remove.** So Retry cannot become a second, unconfirmed evict path, and S3-F15 holds.
- **"Other instance" has one definition**, which both the held-lock outcome and the activation use.
- **`disk_volume` is derived from the same probe path as `disk_free_bytes`,** so the label cannot name a different volume from the number beside it.
- **"/" keeps today's copy exactly,** so a standard Mac shows no change.

## 3. Enterprise Gaps Identified

1. **The probe-failure path was unspecified.** On the `except OSError` path in `scan` (free = total = 0), a naive implementation would report "/" or raise.
2. **Constructor churn.** A new required field breaks 4 Python `Hardware(...)` call sites in tests and the Swift `Hardware.init` call sites. The plan's "edit no existing test" rule would then be violated, or the worker would block.
3. **A request arriving while an evict is already active** could open a confirm sheet that the Remove button would refuse (other job controls are greyed, Q1).
4. **"Free disk after" assumed the same volume without saying so.** It was verified: `quickbench.py:309` uses `free_bytes_at(cache)`.

## 4. Upgrades Applied to Plan
