<objective>
## Goal
Write `docs/threat-model.md`: an inventory of every way into or out of the v5.0 backend, the assets and actors
it defends against, a ranked list of findings each verified against the code, a disposition for each of the
eight items carried in from Phase 4, and the checklist the Phase 5 packaging must keep. **No code changes.**
The fixes are plan 045-02, written after this plan unifies so its tasks are concrete.

## Purpose
Phase 4.5 (Decision 140): v5.0 is the first time OYMLX runs installers, downloads models and holds a localhost
server open on the Mac of a user who does not use a terminal. Phase 5 wraps it in a double-click app, so this is
the last point at which the backend is reviewed as an attack surface rather than as a feature. Plan split
chosen by Jason on 2026-11-03: model first (045-01), then fixes (045-02), then the clean-account smoke (045-03,
a human-action checkpoint at a time Jason chooses).

## Output
- `docs/threat-model.md`, a full document (the terseness contract's documentation exception applies).
- Two review orders in `.paul/orders/`, kept as the pattern for later security passes.
- `045-01-SUMMARY.md` listing the findings that go to 045-02.
</objective>

## AC-1: Every entry point is listed, and a grep proves none is missing
```gherkin
Given the v5.0 modules (server, engines, fetch, quickbench, osaurus_settings, hardware, catalog, recommend, cli)
 and the harness code the app reaches through quickbench (runtimes, measure) <!-- audit-added: must-have -->
When docs/threat-model.md section "Entry points" is written
Then it lists, each with file:line: every HTTP route and method; every job kind with its accepted args;
 every subprocess call with its argv source and environment; every outbound network request with how the URL
 is built; every location written on disk (path, mode, who else can write there, symlink handling); every
 file read that a caller can influence
And a recorded grep over those modules (`subprocess|Popen|urlopen|HTTPSConnection|os.replace|os.symlink|
 os.open|open\(.*["']w|chmod|rmtree|unlink|def do_|write_text|write_bytes|makedirs|mkdir|shutil\.|os\.rename|
 http\.client|socket|os\.environ|os\.kill|execv`) over those modules yields no hit that is absent from the
 inventory <!-- audit-added: strongly-recommended (the original pattern missed pathlib writes, copies, renames,
 http.client and environment reads) -->
```

## AC-2: Assets, actors and trust boundaries are explicit, including what is out of scope
```gherkin
Given the inventory
Then the document names the assets (the per-launch token; the user's files and HF cache; Osaurus config and
 the drift-guard baseline; installed engines and lab-paths.json (it decides which binaries every runtime start executes, so whoever can write it chooses the code that runs); the ledger and logs; the user's consent)
And the actors, each marked in or out of scope with the reason: a web page in the user's browser (incl. DNS
 rebinding); another process running as the same user; another local account; a LAN or Tailscale peer; a
 compromised or spoofed upstream (PyPI, Hugging Face, GitHub releases); root or physical access (out)
And each trust boundary states the assumption it rests on (e.g. "loopback bind plus token")
```

## AC-3: Every finding is verified against the code before it is recorded
```gherkin
Given findings from the coordinator's own pass and from the two review workers
When a finding is recorded
Then it carries a verdict CONFIRMED, REJECTED or ACCEPTED, the file:line that proves it, a severity
 (high/medium/low) with the actor that can exploit it, using one rubric written once in the document
 <!-- audit-added: strongly-recommended -->: high = an in-scope actor without the token can change the
 machine, run code, read the user's files or delete data; medium = needs the token or a same-user process, or
 leaves the user's state wrong without saying so; low = defence in depth, no exploit path shown, and a proposed disposition (fix in 045-02, Phase 5
 checklist, or accepted with reason)
And a worker's report alone never makes a finding CONFIRMED (AGENTS.md delegation contract); REJECTED
 findings stay in the document with the reason, so the next review does not re-raise them
```
