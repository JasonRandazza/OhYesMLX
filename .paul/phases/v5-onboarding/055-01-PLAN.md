<objective>
## Goal
Close Phase 5.5 items 4, 6 and 7 (ROADMAP "Phase 5.5"), each with a red-first test:
- **4:** a malformed `lab-paths.json` no longer breaks `ps`/`lsof` helper calls.
- **6:** a cancel takes effect during the hash of one large file, not only between files.
- **7:** a legacy bare-pid `download.lock` whose pid has been recycled no longer wedges the downloader.

## Purpose
All three are failure modes a user meets with no workaround. A broken lab file disables stop and
recovery for every engine. A cancel on a 20 GB file hangs for about 10 s. A recycled pid blocks every
future download until someone deletes the lock by hand.

## Output
Two source edits (`runtimes.py`, `fetch.py`), one new test file, and `055-01-SUMMARY.md`.
</objective>

## AC-1: System helpers never read the lab files (item 4)
```gherkin
Given the lab-paths file and manifest that `runtimes._lab_paths` reads are replaced by a scratch file containing "{"
  (patch `_lab_paths`'s inputs, NOT `_engine_env`, so the read inside `_engine_command` is exercised)
When `runtimes._listener_pids(<free port>)` and `runtimes._process_identity(<own pid>)` run
Then both answer normally (`()` and a tuple respectively) and no ValueError escapes
And when a command whose program is an absolute path inside a recorded lab directory is resolved by
  `_engine_command(None, ...)` with a well-formed lab file, its directory is still prefixed to PATH (unchanged)
And an engine START (`_engine_command(<engine>, ...)`) under the malformed file still raises (a broken lab
  file must refuse a start, never fall back to the global install)
```

## AC-2: A cancel interrupts a hash mid-file (item 6)
```gherkin
Given a planned file being verified (either the pre-existing blob at :936 or the finished `.incomplete` in `finish`)
When `cancel()` turns true while that file is being hashed
Then hashing stops within one check interval (no more than 64 chunks after the cancel; CHUNK_SIZE is 256 KiB, so
  about 16 MiB) <!-- audit-added: corrected from 64 MiB -->, and the download ends through the existing `cancelled()` path ("cancelled" code, "done" event)
And the `.incomplete` file is kept (not removed, not renamed into the blob) so a resume re-verifies it
And a pre-existing blob is neither removed nor marked for repair because of the cancel
And with `cancel` never true, `_verify`'s True/False results are byte-for-byte what they are today (existing tests unmodified)
```

## AC-3: A legacy bare-pid lock held by a non-ohyesmlx process is stale (item 7)
```gherkin
Given `download.lock` contains a bare integer (the legacy format) naming a live pid owned by this user
When that process's argv (from `_process_identity`) does not contain "ohyesmlx"
Then `_acquire_lock` reclaims the lock and returns True
And when the argv does contain "ohyesmlx", `_acquire_lock` returns False (still busy)
And when the argv cannot be read (`_process_identity` returns None), it returns False (fail closed: busy)
And locks with an identity (the current JSON format) behave exactly as today
And a bare-pid lock naming THIS process stays held (returns False), with no argv check: `same_process` answers
  the own pid from its cache, and a test runner's or app's own argv need not contain "ohyesmlx" <!-- audit-added -->
And `_release_lock` is unchanged: it still removes only a lock naming this pid <!-- audit-added -->
```
