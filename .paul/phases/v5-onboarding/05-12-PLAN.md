## Purpose
AGENTS.md lets any run pin Osaurus only if Jason's settings are restored byte-exact and the report says so. Today there
are four ways the run ends on a false or silent verdict:
- a crashed shell run makes the app back up the pinned state as the original;
- a failed restore check exits 0;
- the drift gate compares the host with itself;
- a raised restore is recorded as `None`.

## AC-1: One backup location (S5-F6)
```gherkin
Given the shell wrapper, quickbench and the app's launch recovery
Then all three use one backup directory, defined once in osaurus_settings (BACKUP_DIR, ~/.osaurus/config.ohyesmlx-backup)
And recover() also finds a backup in the two legacy dirs (~/.osaurus/config.phase4-orig, quickbench's old
  <app support>/quickbench/osaurus-backup), restores from it and removes it only after a byte-exact restore
And pin() refuses while a backup exists in BACKUP_DIR or either legacy dir
And if more than one of those dirs holds a backup, recover() refuses and names every one; it never picks or merges <!-- audit-added -->
And BACKUP_DIR keeps BACKUP_DIR_MODE (0700) <!-- audit-added -->
And the shell trap includes EXIT
```

## AC-2: A failed restore is never success (S5-F7)
```gherkin
Given scripts/osaurus-pin.sh
Then exactly one shell function restores and prints the verdict (RESTORED byte-exact / RESTORE FAILED <dir>)
And it returns non-zero on failure and leaves the restoring trap armed
And the INT/TERM/HUP/EXIT trap calls that same function
And scripts/run_canary.sh (the pattern caller) exits non-zero after a failed restore <!-- audit-added: file added -->
```

## AC-3: The pin cannot overwrite the baseline it is checked against (S5-F8)
```gherkin
Given a baseline file already exists at baseline_path
When pin() runs with the default rebaseline=False (shell wrapper, CLI harness)
Then the baseline becomes that file with only the pinned keys overridden, and is not re-read from the live host
And a host that differs from it on any other tracked key is still refused by check_host_state
Given quickbench (the app; other Macs have no committed baseline)
Then it passes rebaseline=True, which keeps today's live-host baseline
And it records the captured snapshot in its summary.json under osaurus.snapshot
```
No run-header field is added: a header pin needs Jason's yes (AGENTS.md). The committed baseline, versioned by the
header's harness revision, already identifies what a harness run ran under. The same deferral is recorded in the SUMMARY.

## AC-4: Key edits are atomic and owned by osaurus_settings (S5-F12)
```gherkin
Given osaurus_set_seqs in the shell wrapper
Then it calls one osaurus_settings function (set_key style): atomic write via _write_atomic, read back, baseline updated
  under AC-3's rule
And it rejects 0 and any non-positive integer
And the wrapper no longer writes JSON itself
```

## AC-5: A raised restore is recorded (S2-F10)

```gherkin
Given quickbench attempted a pin, whether or not it took effect, and restore() then raises
Then summary.osaurus records restored: false, the reason and backup_dir, and the same restore_failed error event is sent
```
