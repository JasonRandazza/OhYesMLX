<objective>
## Goal
A Swift package in `app/` that builds with `swift build`, tests with `swift test`, and runs with `swift run
OhYesMLX`: it spawns `ohyesmlx app`, reads the launch line, talks to the API with the token, streams job
events, and drives a screen-flow `AppModel` whose behaviour is fully tested against a stub backend. The
screens are placeholders (plain SwiftUI lists); their design lands in 05-04/05-05.

## Purpose
T5.1, seam S7. Everything the screens need — the link to the backend, the one job slot, refusals routed to the
right screen, the interrupted-job banner, both cancel modes, the absolute unsupported gate — is decided here
once, in a testable model, so the screen plans are views only. Threat-model §10 items P5-1, P5-2, P5-3 (argv),
P5-5, P5-7, P5-8, P5-9, P5-10 are this plan's to keep.

## Output
`app/` (Package.swift; library `OhYesMLXKit`; executable `OhYesMLX`; tests `OhYesMLXKitTests`),
`scripts/dev_backend_venv.sh`, `.gitignore` entries for `app/.build/`.
</objective>

## AC-2: The launcher keeps the packaging rules
```gherkin
Given `BackendLauncher` with an injected process factory (tests) or Foundation `Process` (live)
Then the argv is exactly `[python, "-I", "-m", "ohyesmlx.cli", "app"]`, the environment is exactly the v5-app.md list with PATH `/usr/bin:/bin:/usr/sbin:/sbin`, the cwd is App Support created 0700 if absent
And the launch line is read only from the stdout pipe; 30 s with no line, or EOF/exit first, yields `.couldntStart(stderrTail)`
And `BackendToken`'s description and debugDescription are "<redacted>"; `grep -rn "rawValue\|\.raw" app/Sources` for the token's accessor shows it only in the Authorization header builder (P5-1) — the test asserts the String(describing:) and dump() output contain no token
And quit closes stdin then waits; with a job running it never signals; with none it escalates 10 s -> SIGTERM -> 5 s -> SIGKILL (tested with a fake process)
And a second launcher in the same test that cannot take `app.lock` reports `.alreadyRunning` without spawning (P5-7)
```

## AC-2b: The child's pipes cannot wedge it, and its death is noticed <!-- audit-added: must-have -->
```gherkin
Given a spawned backend
Then stdin is a pipe the launcher holds open until quit (never /dev/null, which `ohyesmlx app` treats as parent death and exits at once)
And stderr is drained continuously from spawn on a background reader into the 200-line ring, so a chatty backend never blocks on a full pipe (test: a fake child writing 1 MB to stderr before its launch line still yields the launch line)
And stdout after the launch line is drained and discarded the same way
And when the child exits while the app is running (crash), the launcher reports `.exited(status, stderrTail)` and AppModel moves to a "The backend stopped" state with **Relaunch** (the prototype's `crash` -> `relaunch`); a running job is marked interrupted and its `inflightJob` entry is kept, so the Q2 banner shows after Relaunch
```

## AC-2c: A wedged backend cannot hold the app hostage <!-- audit-added: strongly-recommended -->
```gherkin
Given quit while a job runs
When the backend has not exited 150 s after stdin was closed (its own bound is 120 s + 15 s grace)
Then the app shows "The backend did not stop" with a **Quit anyway** button; only that explicit click sends SIGKILL (P5-8 forbids an automatic SIGKILL while a job runs, not a user's choice)
```

## AC-4: The client decodes every pinned shape and the SSE stream
```gherkin
Given the fixtures
Then Hardware, [EngineStatus] (with Plan), Recommendations (picks, excluded, unsupported_reason), QuickPlan and BackendError decode, with byte counts as Int64
And the SSE parser turns download_events.sse into four JobEvents in seq order, ignores the `: keepalive` comment, and records the last id
And a stream that drops after seq 2 is resumed with `Last-Event-ID: 2` and yields seq 3 and 4 once each (tested with a fake transport)
And `HTTPBackend` sends `Authorization: Bearer <token>` and no `Origin` header (asserted on the built URLRequest)
```

## AC-5: AppModel carries the flow and Jason's seven answers
```gherkin
Given `AppModel` (@MainActor, @Observable) over `StubBackend`
Then the prototype's scenarios a-i each have a test: happy path; pip install fails with output tail then retry; a download while an install runs is disabled with "Busy: install <engine> is running" (Q1); quickbench refused before the model is downloaded shows the backend's message; busy port / missing binary rows; unsupported Mac shows only `.unsupported` with the reason and no navigation out (Q6); quit mid-download then relaunch shows the interrupted banner with Retry and Dismiss and no automatic retry (Q2); excluded model shows its reason; Osaurus pin declined sends `"osaurus": false`
And a `low_disk` on a download is stored against that repo and refreshes hardware (Q4); `needed_bytes - free_bytes` is exposed as the amount to free
And `appBecameActive()` and the Engines screen's appear both call engines() again, and `checkEnginesAgain()` exists (Q5)
And `cancelJob(now:)` sends `cancel(now:)` and the job state reads "Stopping after this cell…" or "Stopping…" (Q3)
And every job start writes the `inflightJob` UserDefaults entry (injected UserDefaults suite in tests) and `done` clears it
```

## AC-6: The app runs
