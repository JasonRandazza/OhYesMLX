# S3-F4 — `cancelJob` writes back a pre-await snapshot, re-pinning a finished job

**Claim (one line):** `cancelJob` snapshots `job` before awaiting `backend.cancel` and writes
that snapshot back afterwards, so a `done` processed during the await is overwritten and the
finished job is restored as active, with no further event to clear it.

**Verdict:** reproduced with a deterministic stub. The stale write re-pins `.stoppingAfterCell`
after `done` set `.finished`, drops the `done` event, and leaves the one job slot Busy.

## Code path

- `app/Sources/OhYesMLXKit/AppModel.swift:517-529` — `cancelJob`:
  `guard let current = job, current.state.isActive` (`:518`) takes the snapshot; `try await
  backend.cancel(jobID: current.id, now: now)` (`:520`) suspends; then `var status = current;
  status.state = now ? .stoppingNow : .stoppingAfterCell; job = status` (`:521-523`) writes the
  pre-await copy back.
- `AppModel.swift:668-711` — `apply` is the only other writer of `job`. `done` sets
  `.finished` (or `.failed` for a restore-failed quickbench) at `:675-682` and assigns
  `job = status` at `:683`. `error`, `result` and `progress` also assign at `:695` / `:710`.
  Nothing guards those writes against the snapshot `cancelJob` is holding.
- Interleaving: while `cancelJob` is suspended at `:520`, the `start` task's event loop
  (`AppModel.swift:650-654`) delivers `done` to `apply`; `apply` sets the job finished. When
  `backend.cancel` returns, `:521-523` restores state `.stoppingAfterCell` and the
  pre-await `events` array.

Downstream consequences, read from source (not observed in a GUI run):

- `AppModel.swift:263-270` — `oneSlotReason` returns `"Busy: … is running"` whenever
  `job.state.isActive`, and `canStartJob` is `oneSlotReason == nil`. The restored
  `.stoppingAfterCell` is `isActive` (`:39-41`), so every control gated on `canStartJob`
  disables: `BenchmarkView.swift:249`, `ModelsView.swift:224` and `:240`,
  `EnginesView.swift:170` and `:194`.
- `BenchmarkView.swift:15` — the stop toolbar is shown while `job.state.isActive` and the kind
  is `.quickbench`; `:95-98` defines `stopping` as `.stoppingAfterCell`/`.stoppingNow`, and both
  stop buttons are `.disabled(stopping)` (`:80`, `:89`). So after the stale write the buttons
  are visible and both disabled. For a download or install the same state pins the slot with no
  stop control on that screen at all.
- `AppModel.swift:562-577` — `requestQuit` computes `let jobRunning = job?.state.isActive ==
  true` (`:569`) and passes it to `runner.quit`. `BackendLauncher.swift:380-387` then takes the
  `jobRunning` branch: it waits `timing.jobBound`, which is 150 s (`QuitTiming.standard`,
  `BackendLauncher.swift:28`), instead of the 10 s grace. That is a bound rather than a
  guaranteed wait — `quitWait` closes stdin first (`:376-379`) and returns as soon as the
  backend exits — but the quit takes the job path for a job that has already finished.

## Reproduction

New file `app/Tests/OhYesMLXKitTests/FableS3F4Tests.swift`, test
`testACancelThatReturnsAfterDoneDoesNotReactivateTheJob`. It wraps `StubBackend` in a backend
whose `cancel` sets a flag and suspends until the test releases it (bounded at 5 s so a failed
test cannot hang), queues a download job with its stream held open, starts `cancelJob(now:
false)`, waits for the cancel to be in flight, delivers `done`, waits until `job.state ==
.finished`, and only then lets `cancel` return.

The race's premise is asserted before the cancel is released: the `XCTAssertEqual` at
`:100-104` (state is `.finished` after `done` and before `cancel` returned) passes, so the failure
above is produced by the stale write and not by a missing event. The milder half of the claim —
the write drops the events that arrived during the await — is the `:116` failure; the snapshot
also restores the pre-await `fraction`, which the test's earlier progress had already set to
0.9, so a fraction arriving during the await would be discarded as well.
