# S5-F9 — verified

**Claim, one line:** two host settings that change what an Osaurus cell measures sit outside the
attestation — `concurrency.smeltMode` is not in `osaurus_settings.TRACKED_KEYS` and is read only
inside a refusal that returns early on an unpinned cell, and the app plist's per-model
`disableThinking` is read by nothing at all — so a row can move its decode rate, TTFT, token
count and timed channel with the drift gate green and no field in the artifact naming why.

Both halves reproduce. (b) is the sharper of the two and is a real defect in the attestation.
(a) is real as an absence and is a violation of AGENTS.md:92, but the runtime doc's own probe
contradicts the mechanism the finding attributes to it — see "Not verified" — so the *magnitude*
claimed for (a) is not established.

## What is NOT implied

- **The `smeltMode` defect needs a host away from `disabled` to bite.** At `disabled` — the
  current value and the enum's default — no expert behaviour is being changed. The finding's
  framing ("a default MoE cell on a host at `ssdStreaming` is measured, published, and neither
  gated nor recorded") is accurate about the code and hypothetical about the host. I did not move
  the host setting to test it; that is Jason's configuration.
- **No number is claimed to have moved.** I did not measure anything.
- The finding's `grep smelt in measure.py` is true: `grep -c smelt ohyesmlx/measure.py` → `0`.

## Not verified

- **Whether `disableThinking` actually changes reasoning output on this Osaurus build.** The
  finding rates this 70 and says "the plist claim rests on the runtime doc, not on Osaurus source
  read here". The doc says so twice (`:523-528`, `:876-880`) — and then contradicts it at
  `:60-64`: a **0.25.18 probe on 2026-10-05** found the request-side thinking switches "inert for
  LFM2.5 (`enable_thinking` …, `reasoning_effort`, `modelOptions.disableThinking`: identical
  1,706-character reasoning)". That probe sent the switch as a *request option*
  (`modelOptions.disableThinking`) on LFM2.5, whereas the plist key is a per-model *stored app
  preference* read at load — different mechanisms, so the two are not strictly contradictory. But
  it is the only behavioural probe in the repo on this switch, it found no effect on the one
  model it tested, and the doc does not reconcile it with §3.6's claim. **The mechanism is
  therefore unestablished**, and a test cannot settle it without starting the app.
- **Which channel Decision 119 would time under either setting.** Depends on the mechanism above.
- **Whether the plist is even reachable from a measured cell.** The plist names models as
  `OsaurusAI/<repo>`; the harness requests `handle.model_id`, which `Osaurus.model_id_candidates`
  derives from the repo name lowercased, and `_record` does not store the resolved id. So a fix
  following the fix direction would need the resolved model id on the row to select the right
  plist entry — that id is currently on `Handle`, not on `CellResult`. I did not verify that
  `handle.model_id` to plist-key mapping is 1:1.
- **Whether `ssdStreaming` and `flashMoE` change decode rate or only residency.** The vMLX doc
  gives the analogue's magnitude for its own flag (`--smelt`: "~50% RAM reduction at ~97% speed",
  `docs/runtimes/vmlx.md:254`), which is enough to call the class "Medium" but is not a
  measurement of Osaurus's.
- **Whether the finding's citation `docs/runtimes/osaurus.md:298` supports the enum.** It does
  not — line 298 is inside the `osaurus bench` usage block; the enum is at `:375`. The same stale
  citation is in `runtimes.py:2648`, so the code and the finding share the error. Small, but it is
  a docstring citing a line that does not say that.
- The full-suite failure count is not stable across runs: 70 → 75 → 76 → 78 with the same code.
  `tests/test_fable_s5_f9.py` itself is deterministic (2 failed, 7 passed on every one of four
  runs). The drift comes from parallel verifiers in this worktree, and was observed directly:
  `ohyesmlx/runtimes.py` carried a one-line edit to `_run` (`env = _engine_env()` →
  `env = dict(os.environ)`) at 17:58 — another finding's red-check in progress, not mine — and was
  reverted again by the next check. That explains the two transiently failing
  `test_runtimes.py` tests (`test_run_hands_the_engine_env_to_the_process`,
  `test_run_execs_the_bundle_executable_when_the_name_is_not_on_the_engines_path`). Both pass when
  the source is unmodified and this file is present. I did not measure a stable baseline for the
  suite as a whole because the worktree is shared; the baseline I started from was 70 failed /
  1,391 passed, and every non-`test_fable_*` failure at that point was `tests/test_server.py`,
  which passes in isolation (124 passed) and is also an ordering artifact.
