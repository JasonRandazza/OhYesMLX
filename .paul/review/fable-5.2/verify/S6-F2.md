## The claim, in one line

`scripts/fetch_python_standalone.sh` re-verifies the cached *tarball* on every run but reuses the
*unpacked tree* beside it on the strength of one `-x` test, and `scripts/build_app.sh:55` copies
that tree into the signed bundle while `scripts/make_sbom.py:137-144` records the tarball's
sha256 — so the SBOM can describe an artifact the bundle no longer contains.

## The mechanism, quoted

`scripts/fetch_python_standalone.sh:70` — the whole of the tree's admission test:

```sh
if [ ! -x "${UNPACKED}/python/bin/python3" ]; then
```

There is no else branch, no checksum of the tree, no marker of which tarball produced it. The
tarball's digest is computed at `:50` and `:62`, and after `:68` it is never consulted again: the
unpack at `:73` is the last time the archive is read. `build_app.sh:24` captures the printed root
and `:25` captures `--identity`; `:55` dittos the first into the bundle and `:116` passes the
second's `sha256` to the SBOM. The two values are never compared to each other, because one is a
path and the other is a pin.

## The divergence, measured on this Mac

The finding says the cached tree "has already diverged from the tarball the SBOM names". That is
checkable without a build, so I checked it.

```
$ shasum -a 256 ~/Library/Caches/OhYesMLX/build/cpython-3.14.10+20261026-aarch64-apple-darwin-install_only.tar.gz
30a18bcb9ab75e485b4bf4e5d783dde165571e7e42c56dff47a2d2c5345183a4  …-install_only.tar.gz
```

That is byte-identical to `SHA256` at `scripts/fetch_python_standalone.sh:16`, so the cached
archive *is* the pinned artifact. I then extracted it to a scratch directory and diffed it against
the cached unpacked tree:

```
$ tar -xzf …-install_only.tar.gz -C fresh
$ diff -rq fresh/python ~/Library/Caches/OhYesMLX/build/cpython-3.14.10+20261026-aarch64-apple-darwin/python
Only in …/python/lib/python3.14: __pycache__
Only in …/python/lib/python3.14/collections: __pycache__
Only in …/python/lib/python3.14/compression: __pycache__
Only in …/python/lib/python3.14/compression/_common: __pycache__
Only in …/python/lib/python3.14/compression/zstd: __pycache__
Files fresh/…/encodings/__pycache__/__init__.cpython-314.pyc and …/encodings/__pycache__/… differ
Files fresh/…/encodings/__pycache__/aliases.cpython-314.pyc and … differ
Files fresh/…/encodings/__pycache__/utf_8.cpython-314.pyc and … differ
Only in …/python/lib/python3.14/importlib: __pycache__
Only in …/python/lib/python3.14/json: __pycache__
Only in …/python/lib/python3.14/pathlib: __pycache__
Only in …/python/lib/python3.14/re: __pycache__
Only in …/python/lib/python3.14/sysconfig: __pycache__
```

13 lines, all `__pycache__`; 10 directories added wholesale, 3 pycs rewritten in place. File
counts: the tarball ships 1692 files with 3 pycs, the cached tree carries 1740 with 51.

I attributed that mutation wrongly at first and had to correct it, which is worth recording
because the finding's own account ("the `ssl`/`socket`/`base64`/`threading` pycs there were
written by some run no build step performs") is also imprecise.

I cleared every pyc from a copy of the cache tree and ran `build_app.sh`'s version-read command
against it verbatim (`build_app.sh:33-34`). It wrote **42 of the 48** — `json`'s four, `re`'s
five, `shutil`, `tempfile`, `pathlib`, `compression.zstd`, `bz2`, `lzma` and the rest. That is
not a subset, as I first wrote: `import ohyesmlx` pulls in far more than `json`/`tempfile`/
`pathlib`, and `compression.zstd` is on 3.14's stdlib import path. So the finding's "some run no
build step performs" is wrong for 42 of the 48: **the build step performs it.**

Nine are not the version read's, and they are the residue that matters:

```
__pycache__/_osx_support, _sysconfigdata__darwin_darwin, base64, socket, ssl, struct,
threading, importlib/__init__, sysconfig/__init__
```

Those are `sysconfig`'s closure plus `ssl`'s. Creating one venv from the same tree writes exactly
those and more: `probe/bin/python3 -I -m venv <tmp>` produced a pyc set that is a **superset of
all 51** in the cache (`comm -23 cachepycs venvpycs` → empty). `_sysconfigdata__darwin_darwin`
plus `sysconfig` is the signature of a `venv` (`venv` calls `sysconfig.get_paths()`), and
`engines.py`'s `{python} -I -m venv` is the app's own path. So the whole cached tree is what
`tar -xzf` + one version read + one venv creation leaves behind — a sequence the project runs on
its own machines, not an intruder.

The 3 rewritten-in-place pycs are a separate and more interesting fact. The tarball's own
`encodings/__pycache__/*.pyc` are **already stale against the sources shipping beside them**:
their header records mtime `1793023270`, the source's is `1704067200`, so the first interpreter
run that is not `-B` rewrites them (`md5` before a plain `import encodings`: `30ed947c…`, after:
`67ac2887…`; a `-B` run leaves them alone). The cache's copies carry the source's mtime because
something already forced that rewrite. That is a fact about the pinned artifact itself, not about
the cache, and it makes S6-F1's concern structural rather than accidental.

None of this contradicts the finding. It sharpens it: the tree is not merely "reused without
verification", it is **guaranteed to differ from the tarball once the build has run against it
and any venv has been built from it**, because `build_app.sh:33-34` reads `__version__` with no
`-B` and `engines.py:797` creates venvs with no `-B`. The gate at `:48-68` verifies, on every run
after the first, a file that is no longer the source of what ships.

I also checked the specific things the finding lists as hypothetical-worse-than-pycs, since its
confidence statement leaves that open:

```
$ find <cache tree> -name '*.pth'  | wc -l     → 0      (tarball: 0)
$ find <cache tree> -name '*.py'   | wc -l     → 1061   (tarball: 1061)
$ diff -rq <tarball>/site-packages <cache>/site-packages   → (no output)
```

So today the divergence is bytecode only, in the stdlib tree, not in `site-packages`. The
`pip install`, the edited stdlib file and the planted `.pth` are latent capabilities of the
reuse test, not present facts on this Mac. That matches the finding's own "Confidence: 90 on the
mechanism … unproven is only whether anything worse than pycs is in the tree today" — and I can
now settle the second half: nothing worse is there today.

## The SBOM half

`build_app.sh:26-29` extracts `release`, `url` and `sha256` from `--identity`; `:113-116` passes
`--interpreter-sha256 "$INTERPRETER_SHA256"` to `make_sbom.py`; `make_sbom.py:137-144` writes it
into `interpreter.sha256` verbatim; `build_document` records `url`, `release_tag` and
`python_version` from the same pin and from asking the bundled interpreter its version. No
`hashlib`, `shasum`, walk or manifest over `Contents/Resources/python` appears in either script —
`make_sbom.py` imports `hashlib` at `:25`-ish only to digest its own output text (`main`'s final
print). So "the SBOM states the tarball's url and sha256 for a tree that is no longer that
tarball's" is true as written, and it is true *by construction*, not by accident: there is no
code path that could notice.

The finding also says the SBOM "lists no bundled package at all". Confirmed by reading
`build_document`: `engine_dependencies` comes from `ohyesmlx/constraints/*.txt`, which are the
pins for the *engine* venvs the app creates later, not for anything inside
`Contents/Resources/python`. The interpreter's own 3-file site-packages (`README.txt`, `pip`,
`pip-26.2.2.dist-info`) is not enumerated. Whether that matters is a separate question and is
not this finding's headline.

## Where I would put the boundary

fixes it:
