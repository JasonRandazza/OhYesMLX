# S2-F5 — the usage reasoning split is trusted against a stream that refutes it

**Claim:** when a runtime streams non-mirrored reasoning deltas and then content, and its
usage block reports `completion_tokens_details.reasoning_tokens: 0`, `transport.chat` takes
the usage split as `completion_tokens − 0` — every token as visible content — over a timing
window that covers the content deltas only, labelled `token_source: "usage"`; the
`reasoning_text` it already holds is never consulted on that branch.

**Verdict:** reproduced. The branch is reached with a real reasoning channel present, and
the observation it returns reports `completion_tokens=500, reasoning_tokens=0,
token_source='usage'` with `reasoning_text='think think'`, `text='one two three'` and
`content_event_count=3`.

## Code path

- `ohyesmlx/transport.py:387` — `reasoning_text = "".join(reasoning_parts)`, the
  contradiction is in hand from here on.
- `:401` — `mirrored = bool(reasoning_text) and reasoning_text == joined`; false for the
  scenario (the channels differ, so this is not the oMLX duplicate).
- `:407` — `reasoning_only = bool(reasoning_text) and not joined`; false (three content
  deltas arrived).
- `:415-426` — with neither flag set, the timing window and `content_event_count` are the
  **content channel's own**: the window excludes the reasoning deltas.
- `:442-444` — `accounting_reasoning_text` is the real `reasoning_text`, but it is only
  passed to `resolve_token_accounting` on the else branch.
- `:445-466` — the branch under test. The gate is
  `usage_reasoning_tokens is not None and completion_tokens is not None and not reasoning_only`.
  A reported `0` passes it; the only sanity checks are
  `usage_reasoning_tokens > completion_tokens` and `visible_exact <= 0`, neither of which a
  zero trips. `content_tokens = completion_tokens − 0`, `token_source = "usage"`.
- `:467-474` — `resolve_token_accounting` and its exclusion check are skipped entirely.

The counter path this pre-empts does make the check: `ohyesmlx/token_counter.py:107-112`
returns the split only when `reasoning + visible == completion_tokens` exactly, and
`INCOMPARABLE_TOKEN_ACCOUNTING` otherwise. A runtime that counts reasoning under content
but reports the breakdown as a constant `0` is exactly the case that sum test catches and
the usage branch does not.

Downstream, the count is what becomes the published rate:
`ohyesmlx/report.py:5` is `decode_tps = completion_tokens / (last_content_s − ttft_s)`, and
`report._token_source` (`report.py:1146-1155`) only prints the `"usage"` label — it does not
gate the figure. 400 reasoning + 100 content tokens over a content-only window therefore
publishes roughly the content window's rate against all 500 tokens, and the row names
`usage` as its source.

One related record-level symptom of the same silence: `reasoning_tokens` is written as `0`
while `reasoning_text` is non-empty. Even where the completion total happens to be
content-only (so the rate survives), the stored observation still contradicts itself.

## Runtime evidence (speaks to severity, not to the code claim)

`docs/runtimes/` was searched for captured usage blocks. Only OptiQ emits
`completion_tokens_details.reasoning_tokens` (`docs/runtimes/optiq.md:658-677`); it derives
the count from the tokens its own patch classifies as reasoning and adds the breakdown
without subtracting from `completion_tokens`. vMLX, oMLX and Osaurus emit no field at all
(`vmlx.md:961`, `omlx.md:711`, `osaurus.md:744`). So a non-empty reasoning stream paired
with `reasoning_tokens: 0` is **not observed on any runtime documented here** — which is
the finding's own Confidence 40, and it remains unobserved. The defect is latent: it costs
one comparison to close and it is the shape a new runtime would present. Conversely, no
runtime tested so far is affected, so no published number in the repo is retroactively
wrong.
