# S2-F8 — a hung engine is retried at 600 s per request with no consecutive-failure bailout

**Claim (one line):** `_request` passes no `timeout_s`, so `transport.chat`'s 600 s default
governs every request, and neither `_workload_visit` nor `_warmup_window` stops on repeated
`timeout` failures — a server that accepts the connection and never answers is asked 49 times
(the default run) or 11 times (quickbench).

**Verdict:** reproduced, and the request count is exactly the worst case the finding describes.

## Code path

- `ohyesmlx/transport.py:163` — `timeout_s: float = 600.0` is the default on `chat`.
- `ohyesmlx/measure.py:1160-1198` — `_request` calls `transport.chat(...)` with
  `handle.base_url, handle.model_id, messages, max_tokens, temperature, seed, token_counter,
  api_key`. There is **no `timeout_s` argument** and no other caller passes one: `grep -n
  "timeout_s" ohyesmlx/measure.py` returns nothing, and no `ohyesmlx/*.py` outside `transport.py`
  passes it to `chat`.
- `ohyesmlx/measure.py:1024-1038` — `_warmup_window`'s loop has exactly two exits: `fixed` and
  `len(rates) >= warmup` (`:1032-1033`), or `_settled(rates)` (`:1035-1036`), or
  `len(rates) >= WARMUP_CAP` (`:1037-1038`). Nothing inspects `observation.error`.
- `ohyesmlx/measure.py:1063-1070` — `_warmup_rate` returns `None` for a failed request (via
  `decode_tps` at N=1, `came_back` above it).
- `ohyesmlx/measure.py:1134-1139` — `_settled` returns `False` when any rate in either window is
  `None`. So a `None` series can never settle, and `WARMUP_CAP = 20` is the only exit.
- `ohyesmlx/measure.py:983-989` — after the warmup window, `for _ in range(quota):` issues the
  measured batches unconditionally. No failure check gates it.
- `ohyesmlx/measure.py:721-738` — the quota splits `measured` across `VISIT_ROUNDS = 2`, and both
  visits run the full warmup window again (`:978-982`), because `warmup` is per workload per
  visit.

There is no `consecutive` / `bail` / `abort` branch anywhere in `measure.py`
(`grep -n "consecutive" ohyesmlx/measure.py` finds only comments about the plateau rule's windows).

## Reproduction

New file `tests/test_fable_s2_f8.py`. The fake transport answers every request with the
observation `transport.chat` produces on its deadline (`ok=False`,
`error="TransportError: timeout after 600s"`, `total_s=600.0`, no token counts), so the test
never waits — the quantity under test is how many requests the loop is willing to make.

```
FAILED tests/test_fable_s2_f8.py::test_a_hung_engine_is_not_retried_to_the_end_of_the_run
```

Failure text:

```
AssertionError: a permanently hung engine was asked 45 times (20 warmup + 3 measured, then 20 +
2) -- at transport.py's default 600 s deadline that is ~7.5 hours per workload for a cell that
has already failed
assert 45 <= 10
```

Measured counts, one workload, one cell, every request a timeout:

| configuration | requests | wall clock at 600 s each |
|---|---|---|
| `measure.run_cells(warmup="plateau", measured=9)` (the default) | **49** (20+5, then 20+4) | **8.17 h** |
| `quickbench.run` (`warmup=3, measured=5`) | **11** (3+3, then 3+2) | **1.83 h** |

The default figure is 49, not the finding's "~25"; the finding's arithmetic undercounts because
both visits pay a full 20-step warmup window (the warmup cap is per workload per visit, not per
cell). The finding's quickbench estimate of "~80 min" is likewise low — 11 requests at 600 s is
1.83 h. Both are worse than claimed, not better.

The run in quickbench is against a `~90 s` per-cell estimate
(`quickbench.ESTIMATE_PER_CELL_S = 90`, `quickbench.py:73`), so one hung cell is ~73× its
estimate. With three to six cells planned (`quickbench.py:57-58`'s comment), a hung engine can
consume the app's `~10 minutes` budget many times over.

Every one of those requests is also a real 600 s wait on a live socket, so the grid's thermal
interleave (`measure.visit_plan`) is void for the duration and the grid's other cells are held.

## What I did not verify

- I did not cause a real engine to hang, so the 600 s per request is `transport.py`'s default
  read, not an observed wait. The failure shape is exact: `_clock`/`_call_before_deadline`
  (`transport.py:117-145`) raises `TransportError("timeout")` and `chat`'s failure branch
  (`:491-519`) returns the observation my fake produces.
- I did not confirm the finding's raise-it lead ("no caller passes a shorter `timeout_s` for
  `quick=True`"). I did confirm nobody passes any `timeout_s` at all, which is stronger.
- I did not evaluate the fix directions. Ending the visit after two consecutive timeouts is one
  line in `_workload_visit`; scaling the timeout from `max_tokens` is a policy change with its own
  risk (a legitimately slow long-prompt prefill could trip it), so it is not obviously better.
