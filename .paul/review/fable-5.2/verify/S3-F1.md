# S3-F1 — live event stream never dispatches

**Claim (one line):** `URLSession.AsyncBytes.lines` omits the blank line that `SSEParser.consume` uses as its only dispatch boundary, so `HTTPBackend.events` never yields a `JobEvent` for any live job; the parser only accumulates `dataLines`, and the client reconnects forever with no `Last-Event-ID`.

**Cited code:** `app/Sources/OhYesMLXKit/HTTPBackend.swift:38` (the `bytes.lines` loop), `:121-142` (the events loop), `app/Sources/OhYesMLXKit/SSE.swift:11-21` (blank-line dispatch). All verified at those line numbers in this tree.

## Method

The finding's own test idea, implemented without any fake transport:
`app/Tests/OhYesMLXKitTests/FableS3F1Tests.swift` (new file, two tests) installs a
`URLProtocol` on an ephemeral `URLSession` that serves the exact server framing
(`id: N\ndata: {...}\n\n`, `ohyesmlx/server.py:930-932`) and drives the production
`URLSessionTransport` → `HTTPBackend.events` path. This is the first test to exercise
`events` through a real `URLSession`; every existing `events` test injects `FakeTransport`
(`app/Tests/OhYesMLXKitTests/HTTPBackendTests.swift:187-258`), which yields `""`
explicitly and therefore cannot see this bug.

The shipping app builds `HTTPBackend(port:token:)` with the default transport
(`AppModel.swift:593`, default `URLSessionTransport()` in `HTTPBackend.swift:61`), so the
URLProtocol-backed session differs from production only in where the bytes come from; the
line-splitting code under test is Foundation's own.

Run:
`cd app && OYMLX_DEV_PYTHON=… swift test --filter FableS3F1Tests`

## Result: reproduced, both tests

**Mechanism** — `testRealURLSessionLinesKeepTheBlankFrameSeparator` failed; the real
`URLSessionTransport.lines` yielded four lines and no `""`:

```
XCTAssertEqual failed: ("["id: 1", "data: {…}", "id: 2", "data: {…}"]") is not equal to
("["id: 1", "data: {…}", "", "id: 2", "data: {…}" ]")
```

Foundation is consuming the `\n\n` pair and emitting nothing for the empty line (the
trailing empty line before EOF is dropped too). The bytes arrive through the actual
`URLSession.bytes(for:)` sequence, and `AsyncLineSequence` pulls bytes one at a time, so
this is independent of how the body is chunked on the wire.

**Symptom** — `testEventsOverTheRealTransportDispatchADoneEvent` failed; `events` produced
no event at all within 3 s:

```
error: … testEventsOverTheRealTransportDispatchADoneEvent : failed -
no JobEvent reached the client within 3 s through the real transport: expired
```

That is exactly the predicted loop: `parser.consume(line:)` returns nil for every line
(no blank line ever arrives), nothing reaches `continuation.yield`, the served body ends,
`finished` is still false (`HTTPBackend.swift:114`, set only at `:138-139` / `:146-147`),
`last` never moves (`:136-137` is unreachable), and the reconnect asks with
`Last-Event-ID: nil` (`:119`) every `retryDelay` (200 ms by default, `:62`) forever.
`SSEParser.dispatch()` (`SSE.swift:49-51`) is never called from `HTTPBackend` or anywhere
else in the app — the blank-line branch is the only dispatch path, and it is unreachable
on this transport.

## Not verified

I did not run a live job in the built app, start the backend, or observe the UI (the order
forbids starting the app/server). The on-screen and quit-wait consequences above are
code-path deductions from the reproduced absence of events; the event-stream failure
itself is directly observed through the production transport. The `URLProtocol` session
delivers the body in one `didLoad`; the empty-line omission is in the line iterator, not in
delivery, but a live socket was not exercised.
