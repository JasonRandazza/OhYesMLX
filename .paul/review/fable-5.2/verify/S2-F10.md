# S2-F10 — a restore that raises after a pin that did not take effect is swallowed without a trace

**Claim (one line):** `quickbench.measure_cell` computes `restored = False if pinned else None`
when `restore` raises; with `pinned` false (a `pin` that raised part-way) the result is `None`,
which matches neither the `is True` nor the `is False` branch, so nothing is written to
`summary["osaurus"]` and no `restore_failed` event is sent.

**Verdict:** reproduced, and the precondition — that `pin` can raise *after* it has changed the
settings files — is proven directly, not assumed.

## Code path

- `ohyesmlx/quickbench.py:646-668` — `measure_cell` sets `attempted = True` (`:657`), runs
  `recover` then `pin` (`:660-661`), and on an exception records `blocked = str(error)` without
  setting `pinned = True` (`:662-668`). The cell is then `SKIPPED` with the pin's reason.
- `ohyesmlx/quickbench.py:707-717` — the `finally`:

  ```python
  if attempted:
      raised = None
      try:
          restored = restore(backup_dir=backup_dir, baseline_path=baseline_path)
      except Exception as error:
          restored = False if pinned else None      # :716 -- the hole
          raised = str(error)
  ```

- `ohyesmlx/quickbench.py:718-740` — only two branches write anything:
  `if restored is True:` → `summary["osaurus"]["restored"] = True`; `elif restored is False:` →
  `restored = False`, a `reason` naming `backup_dir`, and (if `pinned`) a `restore_failed` error
  and a `restore_failure.append`. A `None` falls through both. `raised` is discarded with it.
- `ohyesmlx/quickbench.py:595` — the skeleton is
  `"osaurus": {"allowed": ..., "pinned": False, "restored": None, "reason": None}`, so a
  fall-through leaves exactly the initial `"restored": null, "reason": null`.

The precondition, read from `osaurus_settings.pin` (`osaurus_settings.py:227-286`): both configs
are parsed before either is replaced (`:267-268`), which protects against an unreadable file —
but the backup copies (`:270-278`), both settings writes (`:282-283`) and `write_baseline`
(`:285`) all happen afterwards. A failure in any of those leaves a partial pin on disk with the
originals in `backup_dir`.

## Reproduction

New file `tests/test_fable_s2_f10.py`. It drives the real `quickbench.run` with every side effect
faked through `test_quickbench.a_run`, using the fakes' existing `pin_error` and `restore_error`
hooks — the same fakes `test_a_restore_that_raises_ends_the_run_exactly_as_a_false_one` uses for
the *pinned* case.

```
FAILED tests/test_fable_s2_f10.py::test_a_raising_restore_after_a_failed_pin_names_the_backup_directory
```

Failure text:

```
AssertionError: a restore that raised is recorded as restored: None; Osaurus may still hold the
harness settings and the record says nothing about it
assert None is False
```

Observed, in full, for the scenario (`pin` raises, `restore` raises):

```
ok = True | ended = finished
osaurus = {'allowed': True, 'pinned': False, 'reason': None, 'restored': None}
restore_failed events = []
```

So the run reports `finished`, the `osaurus` block says nothing, and no event carries
`restore_failed`. The user gets no message naming `backup_dir`, and nothing in the summary records
that a `restore` was even attempted. The three calls did happen:
`fakes.osaurus.calls == [("recover", …), ("pin", …), ("restore", …)]`.

### The precondition, proven

`osaurus_settings.pin` against a scratch config directory, with `write_baseline` patched to raise
(the fifth of its five write steps, so both settings files are already rewritten):

```
pin raised: No space left on device
server.json now      : {"modelIdleResidencyPolicy": {"seconds": 900}}
server-runtime.json  : {"cache": {"prefix": {"enabled": false}, "blockDisk": {"enabled": false}}}
backup dir holds     : ['baseline.absent', 'server-runtime.json', 'server.json']
```

That is exactly the finding's failure scenario: the host is left on harness settings (idle 900,
both caches off), the originals are in `backup_dir`, and `pin` raised. A later `restore` that
also raises is the case the test drives. I ran this against `tmp_path`-style scratch files only;
nothing touched `~/.osaurus`.

Note the asymmetry with the already-tested direction: with `pinned = True` and a raising
`restore`, the code is careful — `restored = False`, a reason, a `restore_failed` error, and the
run ends `restore_failed`. The `pinned = False` case, which is the one where the harness cannot
know whether the host was left pinned, is the one that records nothing.

## What I did not verify

- I did not run a real pin against a real Osaurus config, and I did not start any engine or the
  app.
- I did not decide whether the run should end `restore_failed` in this case as it does in the
  pinned one. The finding's fix direction says "record `restored: False`, the reason and
  `backup_dir`, and emit the same `restore_failed` error", which would end the run — but a pin
  that never took effect means the host may be untouched, and stopping a run over a no-op restore
  is a judgement. My test asserts the record and the event, but deliberately does **not** assert
  `ok is False`: the finding's own fix direction implies it, and the record is the part that is
  unambiguously missing. If the coordinator wants the run to stop, that is one more assertion.
- I did not check whether `restore` can raise after a *successful* `recover` in real life
  (`_put_back` raises on a missing backup directory, `osaurus_settings.py:357-360`), which is the
  other route into the same branch. It is the same code path either way.
