# S1-F2 — Owner liveness is decided by pid alone

**Claim (one line):** Both liveness probes treat `PermissionError` — and any other
non-`ESRCH` failure — as "alive", and neither the lock nor the ledger records any owner
identity beside the pid, so once a dead owner's pid belongs to another process its
`download.lock` blocks every download and eviction and its `running-engines/<pid>.json` is
skipped at every launch, permanently.

**Verdict:** confirmed, on both halves, with two failing tests. Severity: the finding's Low is
right, but its "no wrong number" parenthetical is not — see the severity check.

## The code, at the cited lines

`ohyesmlx/fetch.py:354-363` — `_pid_alive`:

```python
try:
    os.kill(pid, 0)
except ProcessLookupError:
    return False
except PermissionError:
    return True
except OSError:
    return True
return True
```

`PermissionError` is `EPERM`, which is exactly what `kill(pid, 0)` raises for a process this
user may not signal — a root-owned daemon, not a dead process. It is read as alive, and so is
every other `OSError` that is not `ESRCH`. The function has no way to say "alive but not
verifiable", and its callers have no way to ask.

`ohyesmlx/fetch.py:366-390` — `_acquire_lock`. On `FileExistsError` it reads the file as an
`int` and:

```python
if pid is not None and _pid_alive(pid):
    return False
```

The lock file's whole content is `str(os.getpid())` (`:387-388`); no start time, no
boot identifier, no process identity. Both production call sites use the same persistent
`DEFAULT_LOCK_DIR = <app support>/locks` (`fetch.py:90-93`), whose parent is
`~/Library/Application Support/OhYesMLX` (`ohyesmlx/__init__.py:27-30`) — it survives a
reboot. The two consumers are:

- `fetch.py:706-708` — `download`, `_refuse(send, "busy", "another download is already running")`
- `fetch.py:1216-1220` — `evict`, `_refuse(send, "busy", "a download or eviction is running; nothing was removed")`

(The finding quotes the download message for both; evict's wording differs. The state is the
same: both answer `busy` and do nothing.)

`ohyesmlx/runtimes.py:612-631` — `_process_alive`, the same rule after a `waitpid(...WNOHANG)`
reap of our own children:

```python
except PermissionError:
    return True
```

`ohyesmlx/runtimes.py:1890-1891` — `stop_orphaned_engines` decides the whole file by its
owner pid alone:

```python
if _process_alive(int(owner)):
    continue
```

The filename is the entire owner record (`_ledger_path`, `:1686-1690`); the entries inside
record the *engine's* `(lstart, argv)` (`:1747-1783`) but nothing about the owner. The sweep
has exactly one caller, `cli.py:1078` in `_recover_startup`, so "every launch" means every
app launch. No other code removes a stale lock or ledger file (grep: `LOCK_NAME`,
`stop_orphaned_engines`).

Consequence beyond stuck state: `Runtime.start` only refuses a listener on **its own** port
(`runtimes.py:2295-2299`), so a skipped orphan holding another runtime's port (say mlx-lm on
8081) does not stop the next cell from starting Osaurus on 1337 — two models resident, which
the project's rules make a void run, with nothing in the artifact saying so (scenario (b)).

## The mechanism, measured

On this host (uid 501):

```
os.kill(1, 0)            -> PermissionError (EPERM)
os.kill(999999, 0)       -> ProcessLookupError (ESRCH)
fetch._pid_alive(1)      -> True
runtimes._process_alive(1) -> True
```

Pid 1 is launchd, owned by root: it is alive, it is not a process either module could have
written into a lock or ledger, and it is exactly the shape of a low pid a dead backend leaves
behind once a reboot hands that number to a system daemon.

## Reproduction — two tests, both red on this code

`tests/test_fable_s1_f2.py`:

1. `test_a_lock_whose_owner_pid_belongs_to_another_process_is_reclaimed` — the finding's own
   test idea: write `download.lock` naming pid 1, assert `_acquire_lock` reclaims it. Fails:

   ```
   AssertionError: a lock naming pid 1 -- alive, but not the process that wrote it -- is
   never reclaimed, so every later download and eviction answers busy with
   'another download is already running'
   assert False is True
   ```

2. `test_a_dead_owners_ledger_file_is_swept_when_its_pid_is_alive_again` — a
   `running-engines/1.json` holding one dead engine entry (pid 999999, a recorded identity
   that cannot match), with `_listener_pids` returning none and `_shutdown` recorded. Asserts
   nothing is signalled and the file is removed once handled. Fails:

   ```
   AssertionError: running-engines/1.json is skipped at every launch because its owner pid
   is alive again; the engine it records keeps its port and its weights forever
   assert not True
    +  where True = exists()
   ```

Both failures are the reported symptom, not an artefact of the fixtures: `_shutdown` is never
called in (2), so the only thing standing between the file and the sweep is the owner gate.

**Green-direction check (no repo edit).** In a throwaway interpreter I replaced only the two
probes so pid 1 reads dead, and re-ran the same scenarios:

```
unpatched _acquire_lock(pid 1) -> False
patched   _acquire_lock(pid 1) -> True          (lock then named 5979, this process)
unpatched sweep: file exists -> True
patched   sweep: file exists -> False
```

That pins the cause to the liveness decision itself. The unpatched sweep ran and left the
file in place, and the sweep is the only caller-side attempt at recovery, which is the
"skipped at every launch" claim made concrete.

## What I did not verify

- No real crash, reboot or pid reuse was staged. Pid 1 is a proxy for "the owner pid now
  belongs to a process this user cannot signal"; a same-uid recycled pid hits the same owner
  gate without needing `PermissionError`, and I did not stage that either.
- The "two models resident" end state was reasoned from `Runtime.start`'s per-port guard
  (`runtimes.py:2295-2299`), not observed — no runtime was started.
- Pid-reuse frequency was not measured. The permanent-file half only needs any live process
  to hold the number when the sweep runs; the voided-measurement half additionally needs no
  reboot, a crash that left an engine, and the next cell on a different runtime's port.
- The lock half reproduced on `_acquire_lock` directly; both `download` and `evict` reach it
  through the same fixed `LOCK_NAME` in the same `lock_dir`, and I did not drive either
  through the refusal path.
- No fix was applied, per the order.

SEVERITY-CHECK: agree — Low fits a stuck state with a manual recovery (delete `download.lock` or the stale ledger file), but the finding's "no wrong number" parenthetical is wrong: scenario (b) can leave a skipped orphan resident on another runtime's port and void a run silently; that needs pid reuse on the same boot plus a crash plus a different-port next cell, a longer chain than F1's unrelated-process kill (Medium), so the rating still holds.
