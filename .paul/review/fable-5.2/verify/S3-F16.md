# S3-F16 — `kill()` signals a pid without checking the child is still that process

**Claim (one line):** `FoundationLauncherProcess.kill()` calls `Darwin.kill(process.processIdentifier,
SIGKILL)` unconditionally, so if the child has already been reaped and its pid reused, the signal
lands on an unrelated process.

## Evidence (no test possible)

This is a TOCTOU race against process reaping; it has no deterministic trigger, and there is no
injection point to observe the syscall — `kill()` is on the concrete `FoundationLauncherProcess`,
which is not abstracted from `Darwin.kill`, and `LauncherProcess` (the protocol the tests fake) is
the *caller* side, not the syscall. A test would have to either instrument production code (not
my remit: "Never fix the code") or win a pid-reuse race on a shared machine.

The unguarded call:

- `app/Sources/OhYesMLXKit/BackendLauncher.swift:99-101` —

  ```swift
  public func kill() {
      Darwin.kill(process.processIdentifier, SIGKILL)
  }
  ```

  No `process.isRunning` test, no comparison against the `exited` flag `LaunchSession` keeps, no
  return value inspected (`ESRCH` is discarded).

The call sites, all reachable after the child may have exited:

- `BackendLauncher.swift:380-397` — `quitWait`: `process.terminate()` at `:391`, then
  `process.waitForExit(timeout: timing.terminateGrace)` at `:392`; if that returns false the code
  calls `process.kill()` at `:395`. `waitForExit` polls `process.isRunning` (`:103-110`), so the
  gap between its last poll and the `kill()` call is the race window.
- `BackendLauncher.swift:400-403` — `forceKill()`, the "Quit anyway" path (`AppModel.quitAnyway`
  at `AppModel.swift:579-582`). It closes stdin and calls `process.kill()` with no prior check at
  all. This is the widest window: the button exists precisely for a backend that was still alive
  150 s after stdin closed, but by the time the user clicks it the child may have exited on its
  own.
- `BackendLauncher.swift:405-415` — `abandon()` checks `process.isRunning` before `terminate()`
  (`:407-409`) and only kills after `waitForExit(timeout: 0.5)` returns false (`:410-412`), so the
  same race exists in a narrower form.
- The information needed for a guard is already in hand on the wrapper: `isRunning` at `:62` reads
  `process.isRunning`; `LaunchSession.handleTermination` (`:501-516`) records `exited` under its
  own lock. Neither is consulted by `kill()`.

Android/Foundation detail this does not depend on: after Foundation's `Process` reaps the child,
`process.processIdentifier` still returns the old pid, so the argument is a live integer that the
kernel is free to assign elsewhere. That is the finding's premise, and it is sound; the confidence
of 40 is about whether reuse actually happens in the window, not about whether the call is
unguarded.

## What I did not verify

- That a pid is actually reused inside the window. That would need a pid-churn harness and a
  privileged amount of luck; the finding's own confidence (40) is about exactly this.
- I did not run the app's quit path, so I have not observed the race or a stray SIGKILL.
- The "same pattern on the Python side" (S1) is out of this finding's cited range and was not
  re-checked here.

VERDICT: CONFIRMED (no test: the window is between Foundation reaping the child and `Darwin.kill`, which has no deterministic trigger and no syscall seam to inject; the evidence is the unguarded call at `BackendLauncher.swift:99-101` and its forceKill/quitWait callers)
SEVERITY-CHECK: agree — Low. Pid reuse inside a sub-second window is rare and the fix is a one-line `isRunning` guard; what keeps it from being informational is the blast radius if it does land: SIGKILL to whatever now owns the pid.
