# S5-F5 — no ledger entry exists for the engine's entire load

**Claim.** `Runtime.start` writes the running-engines ledger entry only after `await_ready`
returns, so for the whole load — the longest phase of a start, up to `READY_TIMEOUT_S` = 900 s —
the spawned engine is in its own session with nothing on disk naming it. A harness that dies in
that window leaves an engine that `stop_orphaned_engines` cannot find at the next launch and
that "Stop now" (`stop_own_engines`) cannot reach.

## Code

`ohyesmlx/runtimes.py:2317-2350` (`Runtime.start`):

```
2317:  started = _now()
2318:  pid = None
2319:  try:
2320:      pid = _spawn(command, log_path)
2321:      resolved = self.await_ready(          <- up to 900 s
...
2344:  cold_load_s = _now() - started
2345:  stop_command = self.stop_command()
2346:  try:
2347:      _record_running_engine(pid, serving_pid, self.port, stop_command)   <- first and only write
```

`_record_running_engine` has exactly one call site in the package (`:2347`) and
`_forget_running_engine` exactly one (`:1987`, `Handle.stop`). `_spawn` (`:588-609`) sets
`start_new_session=True`, so the engine outlives the harness.

The two readers both read the ledger and nothing else:

- `stop_orphaned_engines` (`:1867-1905`) globs `<root>/results/running-engines/*.json` and acts
  only on files it finds; its one caller is `cli._recover_startup` (`cli.py:1078`), i.e. the next
  launch.
- `stop_own_engines` (`:1908-1937`) reads `_ledger_path()` only. Its caller is the app's
  `{"now": true}` abort (`server.py:805-808`).

So the window between `_spawn` (`:2320`) and `_record_running_engine` (`:2347`) is a hole in both
recovery paths, not just one.

The comment at `:2342-2343` and `_record_running_engine`'s docstring (`:1758-1761`) name the
reason: AC-6 requires that no measured `cold_load_s` contain the ledger's `ps` calls, and
`tests/test_runtimes.py:3713` (`test_the_running_engine_is_recorded_after_the_cold_load_time_is_taken`)
pins that ordering. The trade is real and deliberate — and it is exactly what opens the window.

## Reproduced

`tests/test_fable_s5_f5.py::test_the_ledger_names_the_engine_before_readiness_is_awaited`

The test fakes every seam `Runtime.start` leaves the module through (`_spawn`, `_now`, `_sleep`,
`_run` — which is how `ps`/`lsof` are reached — `_port_is_free`, `_listener_pids`,
`_process_alive`, `_shutdown`, `writable_root`, `_log_path`) and patches `await_ready` to record
the ledger and then raise, standing in for the harness being killed while the model loads. No
process, port or model is touched.

```
FAILED tests/test_fable_s5_f5.py::test_the_ledger_names_the_engine_before_readiness_is_awaited
E  AssertionError: no running-engines ledger entry existed while the engine was loading:
E  nothing on disk named pid 4243 on port 8081
```

The assertion is reached with `seen["pid"] == 4243`, so the start had spawned and was inside
`await_ready` — the exact phase the finding names.

Two companion tests in the same file, both passing today:

- `test_a_load_interrupted_before_readiness_leaves_an_engine_no_launch_recovers` — follows the gap
  through: after the abort, with the owner pid dead and the spawned engine alive,
  `stop_orphaned_engines()` finds no file and signals nothing. Its control then writes the entry a
  start-early fix would have left, and the same sweep stops the same engine through `_shutdown`.
  So the sweep is not inert; the absent entry is the whole difference.
- `test_the_observation_point_sees_a_ledger_written_right_after_the_spawn` — sensitivity check on
  the rig: `_spawn` is wrapped to call `_record_running_engine` straight after the spawn, against
  otherwise unmodified source, and the first test's assertion goes green. The red is caused by the
  missing write and by nothing else in the fixture.

Red-check: the primary test fails on unmodified `ohyesmlx/runtimes.py` with the message above, and
passes only when a ledger write is injected before `await_ready`. No source file was changed.

## Scope notes on the claim

- **The trigger is wider than "Quit anyway".** `quitAnyway()` SIGKILLs the backend
  (`AppModel.swift:579-582` → `BackendLauncher.forceKill`), but an ordinary quit also reaches it:
  `cancel_and_wait` (`server.py:261-292`) sets `cancel_requested` and waits `JOB_SHUTDOWN_WAIT_S`
  = 120 s. A cell's start is not cancel-aware — `run_cells` has no cancel/abort parameter at all
  (`measure.py:834` starts the runtime and `quickbench.run`'s `cancel`/`abort` are only the
  between-cells probes, `quickbench.py:510-511`). So a 35B load that runs past 120 s + 15 s of
  `JOB_KILL_GRACE_S` and is then abandoned is the same orphan. A crash is the third trigger.
- **"Stop now does nothing before the entry exists" is pinned; the crash orphan is not.**
  `docs/interfaces/v5-app.md:33-35` states the "Stop now" degradation (and `05-01-AUDIT.md:25`
  records it as documented and acceptable). Nothing in `docs/` pins that the *crash* case leaves
  an engine no launch recovers — I searched `docs/` for the wording and found no entry.
- **The "next run is refused (same port)" half is right.** `_port_is_free` (`:678-688`) is checked
  first in `start` (`:2295-2299`) and reads `lsof` only, so a leftover engine on 8081 or 8100
  refuses the next cell. The "other port" half is F3's ground, not this finding's.

I did not verify, and the report should say so: no test here proves a real process survives — the
engine is a number. The survival rests on `start_new_session=True` at `:605`, which is the
dossier's own citation and is what `Handle.stop`'s group signalling already depends on.

Severity: Medium is right. The harm needs a harness death inside the load window to happen at all,
and when it does the engine holds ~20 GB and a port with no recovery short of a manual `lsof`/kill.
