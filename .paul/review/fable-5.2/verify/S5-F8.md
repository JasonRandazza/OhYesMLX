# S5-F8 — every pin re-records the baseline from the live host, so the drift gate compares the host to itself and no snapshot is kept with the results

**Claim, one line.** `pin` ends by writing the *live host's* 23 tracked values as the drift baseline, so for the whole pinned run `check_host_state` compares the host to a copy of itself — the 20 keys the pin does not set bind to nothing — and after `restore` puts the previous baseline file back, no results directory holds the values the run actually measured under.

**Verdict: reproduced, both halves.**

## 1. The gate is a tautology for the pinned run

`osaurus_settings.pin` (`ohyesmlx/osaurus_settings.py:227-286`) edits exactly three of the 23 `TRACKED_KEYS` (`:64`) — `cache.prefix.enabled`, `cache.blockDisk.enabled` (`:280-281`), `modelIdleResidencyPolicy.seconds` (`:282`) — and then, as its last act, calls:

```python
write_baseline(baseline, root)          # ohyesmlx/osaurus_settings.py:285
```

`write_baseline` (`:149-161`) is `capture_osaurus_settings(config_dir)` (`:103`) written out verbatim. So the baseline that `Osaurus.check_host_state` (`ohyesmlx/runtimes.py:2694-2712`) reads at every cell start — `runtimes.py:2306` — is the post-pin host itself. `diff_against_baseline(capture_osaurus_settings(), baseline)` (`:2706`) is empty by construction, and the `RuntimeStartError` at `:2707-2712` is unreachable for the remainder of a pinned run.

The 20 keys the pin never touches — `generation.streamInterval`, `numberOfThreads`, `performance.compiledDecode`, `mtp.mode`, `concurrency.maxConcurrentSequences`, `memorySafety.*`, `backlog`, and the rest — are copied into the new baseline from whichever state the host happened to be in that day. The previous baseline is first backed up (`:274-275`) and `_put_back` writes it back over the pin's at `restore` time (`:310`), so even the file the run overwrote is gone afterwards.

The wrapper states the mechanism in its own header, `scripts/osaurus-pin.sh:7`:

> the baseline is re-recorded so the guard passes

and `osaurus_set_seqs` does the same again for the concurrency pin, `scripts/osaurus-pin.sh:65` (`s.write_baseline()`), after confirming the edit landed (`:62-64`).

This is the normal path, not an edge: `scripts/run_grid_35b.sh:45` (`[ "$r" = osaurus ] && osaurus_pin`), `scripts/run_canary.sh:37`, and quickbench's own run (`ohyesmlx/quickbench.py:661`) all go through it.

The run header is built in `measure.run` (`measure.py:578-620`) and written by `write_jsonl` (`:1439`); it carries `temperature`, `seed`, `warmup`, `measured`, `concurrency`, `prompt_tokens`, `cache_state`, `kv_quant`, `mtp_depth`, `stream_experts`, `quick`, `cooldown_s`, `workloads`, `harness` — no Osaurus field.
- `grep -c osaurus ohyesmlx/report.py` → **0**.
- quickbench's `summary["osaurus"]` is initialised as `{"allowed", "pinned", "restored", "reason"}` (`quickbench.py:595`) — statuses only, no values. `during_run` (`:689`) is a path to a byte copy of the two host files, but it is written **only inside `if drift is not None`**, i.e. only when a mid-run change was already detected. A clean run records no settings at all.
- Checked the record on disk in the main checkout: `grep -rl numberOfThreads /Users/jrazz/Dev/active/OhYesMLX/results/` → no file. `find …/results -name '*baseline*'` → only `results/canary/first-baseline.log`, which is a canary log, not a settings snapshot.
- `config/osaurus-settings-baseline.json` is tracked (committed in `b1fc311`) and carries 23 keys with the host's own `numberOfThreads: 12`, `streamInterval: 1`, `mtp.mode: "auto"`, `compiledDecode: false`. Nothing compares a run against it once `pin` has run.

So after a pinned run: the Thursday values were real, were written to a file, and that file was then overwritten by Tuesday's; the results directory never saw them.

## What I did not verify

- **The inter-run scenario itself.** I proved the gate is empty after a pin, not that a real Tuesday/Thursday pair of grids was ever joined under different settings. That needs two grids against a host that changed, which I did not run and could not run.
- **`pin` in the app path** (`quickbench.py:661`) end-to-end — the pin call site is read, not exercised.
- **Whether the committed baseline is *meant* to bind across runs.** The module's docstring says its scope is "drift, not correctness" (`osaurus_settings.py:10-13`), and the reviewer was right to flag that as the open question. My reading: that sentence scopes *what the values ought to be* (it declines to say the caches should be off), which is a different claim from *whether they may change between runs*. Binding across runs is drift, so the docstring does not excuse this. But that is a judgement, not evidence — if Jason confirms the baseline is deliberately per-run, this finding's severity drops to Low and the fix direction changes to "record the snapshot with the results" alone.

## One thing the finding understates

For **grid** runs the gate has no second chance: `measure.run` calls `check_host_state` once per cell start (`runtimes.py:2306`) and never after, so a host that moved mid-run is not detected at all in the `measure.py` path. quickbench's `_osaurus_drift` (`quickbench.py:208-225`, called at `:685`) is the only post-cell check in the codebase, and it guards only quickbench runs. That makes the grid path — the one that produces the published tables — the path with zero attestation of any kind.
