# S3-F10 — the free-disk figures never re-read after a download or evict, and "Free disk after" is client arithmetic

**Claim (one line):** `AppModel.hardware` — the only source of the Models toolbar's "Free disk"
and the Benchmark plan's "Free disk after" — is fetched at launch, on "Scan Again", and after a
`low_disk` refusal only, so a finished download or evict leaves the screen quoting the
launch-time free space and overstating what is left; the plan's figure is computed in the client
(`free − downloadBytes`) rather than sent by the backend.

## Reproduction

New file, `app/Tests/OhYesMLXKitTests/FableS3F10Tests.swift`, two tests, one stub trick: a
`Hardware` whose `diskFreeBytes` is 40 GB at launch, then `setHardware` to 20 GB before the job
runs — which is exactly the state a 20 GB download leaves behind. The test drives the job to
`done` through `AppModel.download` / `AppModel.evict` and asserts `model.hardware.diskFreeBytes`
is the post-job value.

```
$ cd app && swift test --filter FableS3F10Tests
Test Case ... testDownloadCompletionRefreshesFreeDisk started.
FableS3F10Tests.swift:69: error: XCTAssertEqual failed: ("Optional(40000000000)") is not equal
  to ("Optional(20000000000)") - a finished download leaves the free-disk figure re-read, not
  the launch-time one
Test Case ... testEvictCompletionRefreshesFreeDisk started.
FableS3F10Tests.swift:89: error: XCTAssertEqual failed: ("Optional(20000000000)") is not equal
  to ("Optional(25000000000)") - a finished evict leaves the free-disk figure re-read, not the
  launch-time one
Executed 2 tests, with 2 failures (0 unexpected) in 0.050 seconds
```

Both jobs genuinely reached `done`: the tests assert `model.job?.state == .finished` before the
free-disk assertion, and it holds. The displayed value is the launch-time one.

## Code path, as cited — every line number verified

**`hardware` is written in exactly two places, and neither is a job's completion.**

- `AppModel.swift:410-435` — `reload()` is the only place that calls `backend.hardware()`
  (`:414`). It is called from `launch()` (`:383`), from `adopt(running)` at launch (`:406`), and
  from `RootView.swift:62-64` ("Scan Again").
- `AppModel.swift:762-766` — `refreshHardware()` wraps the same call and is invoked from exactly
  one site: `:696-698`, the `low_disk` error branch of `apply`.
- `AppModel.swift:663-665` — the post-job refresh re-reads recommendations only. This is the
  AC-6 block, and its own comment says why it exists: "a download or an evict changes what is on
  disk". It refreshes the step ticks and the picker, not the number that describes what changed.
- `AppModel.swift:446-449` (`go(to:)`), `:451-453` (`appBecameActive` → engines),
  `:459-461` (`checkEnginesAgain` → engines) — navigation and app activation refresh engines
  only. `ModelsView.swift:64-66` re-reads recommendations on appear, and `Recommendations`
  (`Models.swift:384-400`) carries no disk figure, so re-entering Models cannot fix the number.

The only recovery is the "Scan Again" button, which `RootView.swift:60-65` shows only when the
screen is `.welcome` or `.yourMac`. A user on Models or Benchmark has no control that re-reads
the disk.

**Both screens read that stale value.**

- `ModelsView.swift:72-76` — the toolbar is `DiskMeter(hardware: model.hardware, …)`.
- `ModelsView.swift:280-295` — the meter prints `Format.size(hardware.diskFreeBytes)` and draws
  its gauge from the same field.
- `BenchmarkView.swift:201-206` — `LabeledContent("Free disk after")` over `diskAfter(plan)`.
- `BenchmarkView.swift:255-258` —
  `let free = model.hardware?.diskFreeBytes ?? 0; return Format.size(max(0, free - plan.downloadBytes))`.
- `YourMacView.swift:30` — a third reader of the same field, also stale until Scan Again.

**"Free disk after" cannot come from the backend today.**

- `Models.swift:435-452` — `QuickPlan` decodes `repo`, `format`, `stage_a`, `stage_b`,
  `download_bytes`, `osaurus`, `estimate_s`. There is no free-space field to display.
- `ohyesmlx/quickbench.py:137-139, 255-313, 577` — the backend's plan carries the same six
  fields and nothing about the disk. So the fix direction's second half ("have the plan carry
  `free_after` from the backend") is a backend shape change, not a client tweak; the interface in
  `docs/interfaces/` would need it first.

**The file says it computes no number, and this is the one it does.**
`BenchmarkView.swift:5` — "Nothing here computes a number: the plan, its estimate, the progress
and every cell row are the backend's." `diskAfter` is a local subtraction the sentence denies.

**The harm really is display-only.** `ohyesmlx/fetch.py:816-830` re-reads `hardware().disk_free_bytes`
immediately before a download's requests and refuses with `low_disk` when the room is not there,
so the stale screen cannot cause a full disk. The finding's confidence-80 caveat is right.

## One inaccuracy in the finding, not in the defect

The finding says "With `hardware == nil` it prints 0." It prints **"0 MB"** — `Format.size(0)`
falls below the GB branch (`Format.swift:13-19`). The branch is also unreachable in the real app:
`reload()` publishes a screen only after `hardware` is non-nil (`AppModel.swift:435` — welcome if
`hardware?.supported == true`, otherwise unsupported), and `hardware` is never set back to nil.
So the `?? 0` is dead, not a live second symptom. The stale-value defect is unaffected.

## What I did not verify

- **The rendered screen.** The view target is not a test dependency, so no `Form` or `DiskMeter`
  was instantiated. The stale value is proven at the model level; that both views render
  `model.hardware` (and nothing else) is proven by reading their bodies, not by pixels.
- **A real download's effect on `disk_free_bytes`.** I changed the stub's value around the job
  rather than downloading, per the order's no-download rule. The test asserts the refresh path,
  which is the defect; it does not assert how much space a real 20 GB fetch frees.
- **Whether any refresh happens on a job that ends in `error` (not `low_disk`).** `apply` handles
  only `low_disk`; a cancelled or failed download leaves the figure stale too. I did not add a
  test for it, since the finding's scenario is a completed download.
- **The `YourMacView` reader's behaviour** beyond noting it reads the same field and is refreshed
  by Scan Again.

## Severity

The finding says Medium, confidence 80. I agree with Medium, and the defect is real on both
screens the finding names.

Not High: no data is lost, no job proceeds on the wrong number (the backend's own guard at
`fetch.py:816-830` re-reads the disk and refuses), and the stale figure is recoverable by
returning to "Your Mac" and pressing "Scan Again".

Not Low: the number is wrong in the direction that matters — it overstates free space by the whole
size of the model just fetched, on the screen where the next download is chosen, and the
Benchmark screen presents a client-computed figure under an "estimated" badge while its own
header claims the screen computes no numbers. A user is given no cue the value is from launch,
and the one control that would re-read it lives on a different screen. Display-only is still the
app's verdict to the user, and it is wrong.
