# S3-F15 — Retry from the interrupted banner skips the install/evict gates, and the banner only appears for crashes

**Claim (one line):** (a) the interrupted banner's Retry calls `retryInterrupted`, which for an
install runs `start(.install(engine:))` directly — no consent sheet, no listing of the steps — and
for an evict re-runs it without its confirmation sheet; (b) on a normal quit mid-job the backend
cancels the job, its `done` reaches the app's still-running event loop, `apply` clears
`inflightJob`, and the next launch shows no banner at all.

## Reproduction

(a) is testable and reproduced. `app/Tests/OhYesMLXKitTests/FableS3F15Tests.swift` seeds the
persisted record a crash leaves (`inflightJob = {kind: install, name: optiq, started: …}` —
`writeInflight`'s exact dictionary, `AppModel.swift:775-780`), launches, checks the banner state
is live, confirms `installConsent` is false, and calls `retryInterrupted()`.

```
$ cd app && OYMLX_DEV_PYTHON=…/app-dev-venv/bin/python swift test --filter FableS3F15Tests
FableS3F15Tests.swift:36: error: XCTAssertTrue failed - Retry started an install with
  installConsent false: the consent sheet was skipped
Test Case '-[OhYesMLXKitTests.FableS3F15Tests testRetryOfAnInterruptedInstallDoesNotStartWithoutConsent]' failed (0.002 s).
```

`XCTAssertEqual(model.interruptedJob?.kind, .install)` passed first: the banner was up and Retry
started a job anyway. (b) is not testable without a real child process — see below.

## Code path, as cited — every line number verified

**(a) two gates, one of them bypassed.**

- `RootView.swift:42-54` — the banner's Retry is `{ Task { await model.retryInterrupted() } }`
  (`:51`).
- `AppModel.swift:546-560` — `retryInterrupted` switches on the record's kind and calls
  `start(.install(engine: interrupted.name))` (`:551-552`), `start(.download(...))` (`:553-554`),
  `start(.evict(...))` (`:555-556`). It never touches `installConsent` and never re-fetches the
  engine's install plan.
- `AppModel.swift:463-469` — `install(engine:)`, the gated entry, is the one that checks
  `guard installConsent else { refusal = …; return }`. Retry does not go through it.
- `Screens/EnginesView.swift:66-80` — the sheet and `startInstall`: the consent sheet shows
  `engine.install` (the step plan), and only its confirmation sets `model.installConsent = true`
  (`:74-80`). `:169` is "Install…" and `:193` "Try Again"; both route to `startInstall` via the
  same closure (`:86-89` says so in a comment: "The one install-start path, shared by Install… and
  Try Again"). The banner's Retry is a *third* path to the same backend call, and it has no sheet.
- `Screens/ModelsView.swift:67-70` — evict has its own confirmation sheet whose confirmation runs
  `model.evict(repo:)`; `retryInterrupted`'s `.evict` branch calls `start` without it.
- Spec tension, stated plainly: `docs/interfaces/v5-app.md:89-92` (Jason's answer 2) pins Retry as
  "re-sends the same job after a fresh user click" and says nothing about re-consenting. The code
  does exactly that. So (a) is partly by design; what the finding adds is that the thing consented
  to is the *plan*, and the plan can differ on a later version or after lab paths change.

**(b) the record is cleared by a quit the banner should report.**

- `AppModel.swift:674-688` — on `.done`, `apply` sets the state and calls
  `defaults.removeObject(forKey: inflightKey)` (`:684`). This runs for any `done`, whether the job
  finished, failed or was cancelled.
- `AppModel.swift:689-699` — an `.error` alone would keep the record: a cancel sets `.cancelled`
  at `:690-691` and removes nothing. Only the `done` branch's `:684` removes it, and the backend
  appends that `done`: `ohyesmlx/server.py:752-763` — the runner's `finally` appends
  `_event("done", "the job ended without a done event", None)` whenever the module did not emit
  one, for every job kind.
- The quit is what triggers that cancellation, and the app is still listening:
  `BackendLauncher.swift:380-387` closes stdin as the first act of `quitWait`; `cli.py:1157` runs
  `_stop_at_eof`, and `:1164-1168` shuts the server down and calls
  `listener.jobs.cancel_and_wait(server.JOB_SHUTDOWN_WAIT_S)`. On the app side `requestQuit` only
  awaits the runner's quit (`AppModel.swift:569-575`); it does not cancel or disconnect the
  `start()` event loop (`:650-660`), and `RunningBackend.quit` runs on a global queue
  (`BackendLauncher.swift:550-556`) so the main actor — and that loop — stay live during the wait.
- Next launch: `loadInflight()` (`AppModel.swift:782-790`) reads the key, finds nothing, and
  `launch()` leaves `interruptedJob` nil (`:382`), so `showsInterruptedBanner` (`:190`) is false.
- The test that pins the banner does not cover this: `AppModelTests.swift:554-580`
  (`testQuitMidDownloadLeavesTheBannerAndNoAutomaticRetry`) simulates a **crash** by calling
  `backendExited(status: 1, …)` (`:567`) in the middle of a held stub stream. It never runs a
  quit, so it never exercises the `done`-during-quit path.

## What I did not verify

- (b)'s flush. Whether the backend's `done` reaches the client before the child process exits is a
  timing question (the finding says so at confidence 50); I did not start a backend to watch it.
  The *reachability* of the path is certain: the event loop is still attached, and the backend
  writes a `done` for every job.
- The exact consent-sheet contents on a re-plan; I did not run the app or the engines endpoint.
