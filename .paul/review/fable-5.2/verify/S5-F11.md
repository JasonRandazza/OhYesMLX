# S5-F11 — verification

**Claim, restated in one line:** `_process_alive` reaps a `osaurus serve` launcher pid during
`await_ready`, the handle keeps that number for the whole cell, and at stop `_process_alive`
reads the freed number as alive through the `os.kill(pid, 0)` fall-through — so `_signal_tree`
sends SIGTERM and then SIGKILL to `os.getpgid(pid)`, the process group of whatever same-user
process was handed the reused pid.

## What the code does (line numbers verified in this worktree)

- `ohyesmlx/runtimes.py:612-631` `_process_alive` — `os.waitpid(pid, WNOHANG)` at `:619` reaps
  the child when it has exited and returns `False` (`:623-624`). On a *later* call the same
  `waitpid` raises `ECHILD` (caught at `:620-621`), so control reaches `os.kill(pid, 0)` at
  `:626`, which succeeds for any same-user process now holding the number, and the function
  answers `True` at `:631`. Nothing records that the pid was reaped.
- `ohyesmlx/runtimes.py:2197-2251` `await_ready` — `if not _process_alive(pid) and
  _listener_pids(self.port) == ()` at `:2220` is the poll. For `osaurus serve` — a launcher that
  exits once the app is listening — the launcher is alive long enough to answer, so the poll
  that reaps it is the one after hand-off, and the handle still holds that pid.
- `ohyesmlx/runtimes.py:1941-1988` `Handle` — `pid` is a field the handle keeps for its whole
  life (`:1953`); `Handle.stop` at `:1981-1988` passes it to `_shutdown` at `:1983`.
- `ohyesmlx/runtimes.py:1656-1684` `_shutdown` — `if _process_alive(pid): _signal_tree(pid,
  signal.SIGTERM)` at `:1676-1677`, then after `TERM_GRACE_S` `_signal_tree(pid, signal.SIGKILL)`
  at `:1678`.
- `ohyesmlx/runtimes.py:651-659` `_signal_tree` — `os.killpg(os.getpgid(pid), sig)` at `:653`.
  The group is whatever `getpgid` answers for the reused number.
- `ohyesmlx/runtimes.py:1827-1864` `_stop_orphan` — this is the contrast the finding draws and
  it is correct: `_process_identity` is compared against the recorded identity at `:1850-1852`
  and `:1856`, so the orphan path proves identity before signalling. The live `Handle.stop` path
  (`:1983`) has no such check.

The finding's "distinct from S1-F1" is also correct: S1-F1 is a stale ledger *file*; this is the
in-memory handle's pid.

## Reproduced

New file `tests/test_fable_s5_f11.py`, one test. It spawns a real short-lived child, polls
`runtimes._process_alive` exactly as `await_ready` does until it answers `False` — so the module's
own `waitpid` is what reaps it — then fakes `os.kill`/`os.getpgid`/`os.killpg` to answer for the
reused number and calls a real `Handle.stop()`.

On unmodified code:

```
E       AssertionError: stop signalled process group(s) [(777, <Signals.SIGTERM: 15>),
        (777, <Signals.SIGKILL: 9>)] for pid 50115, which this process reaped while waiting
        for the runtime to become ready; the group belongs to whoever inherited the number
```

That is both escalation steps, in order, against a pid this process had already reaped.

## The mechanism, without pytest

The decisive half is that a reaped pid reads as alive on the second call. Run against the real
function:

```
first _process_alive (reaps): False pid 85419
second _process_alive: False   <- (see note)
```

The second call prints `False` here only because nothing had yet been handed that number: the
`waitpid` raises `ECHILD`, control falls through to `os.kill(pid, 0)`, and the kernel answers
`ProcessLookupError` for an unused pid. Reuse is the whole precondition, and the test supplies it
by patching `os.kill` to succeed — which is exactly what the kernel does once the number belongs to
another same-user process. The fall-through itself is proven by the second line reaching `os.kill`
at all: had the reap been remembered, the function would have returned at `:624`.

Corroboration that the pid is genuinely free after the reap:

```
os.getpgid(pid) on the reaped number: ProcessLookupError: [Errno 3] No such process
```

The process is gone and its number is available for allocation — which is the finding's premise.

## Red-check (performed)

Applied the finding's own fix direction, minimally: a module-level `_REAPED_PIDS` set, added to
when `_process_alive` reaps (`:623`), and an early `if pid in _REAPED_PIDS: return False` before the
`waitpid`. Result: **1 passed**. Reverted with `git checkout -- ohyesmlx/runtimes.py`
(`git status --short ohyesmlx/` empty): **1 failed**, same assertion.

## Severity

The finding says Low, with confidence 60 on the logic, and that is right on both counts. The code
path is unambiguous — no identity is carried and the reap is not remembered — but the trigger needs
the kernel to hand one specific number back to a same-user process inside one cell's window
(minutes, two visits), on a quiet benchmark Mac running nothing else (AGENTS.md forbids anything
else running). If it does fire, the damage is not a measurement error: it is SIGTERM then SIGKILL
to a process group the harness has no claim on, which can kill a user's unrelated work. Low is
correct — the probability is small and unmeasured, and the finding says so rather than inflating
it.

## What is not verified

- The reuse itself. No same-user process was handed the number and no real pid's group was
  signalled; `os.kill`/`os.getpgid`/`os.killpg` are faked, and the child is the test's own.
- The `osaurus serve` hand-off was not exercised: the test reproduces the *reap* (`_process_alive`
  polls a launcher that exits), not the hand-off semantics of the real app. No engine was started.
- `_await_exit` (`:1608-1614`) polls the same `_process_alive`, so a fix that only guards
  `_shutdown` would leave the second half of the ladder on the same footing. Not asserted here.
- Whether the same hole is reachable through `_kill_resident` (`:1617-1635`) was not examined;
  that path signals by single pid, not by group, so the blast radius differs.
