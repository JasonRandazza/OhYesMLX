# S3-F17 — a plan fetch that fails without a `BackendError` leaves the previous model's plan under the new picker selection

**Claim (one line):** `planBenchmark` clears `quickPlan` only in its `BackendError` branch; any
other failure (timeout, decode) returns false and leaves model A's plan on screen while the
picker shows B, with Start enabled; `startBenchmark` then runs `quickPlan.repo`, which is A.

## Reproduction

`app/Tests/OhYesMLXKitTests/FableS3F17Tests.swift`, one test. A backend wrapping the stub serves a
good plan for `mlx-community/Qwen3.5-2B-4bit` and throws `URLError(.timedOut)` for
`mlx-community/Elsewhere-4bit` — the shape a non-`BackendError` failure takes. The test fetches A,
then fetches B, then checks what is on screen.

```
$ cd app && OYMLX_DEV_PYTHON=…/app-dev-venv/bin/python swift test --filter FableS3F17Tests
FableS3F17Tests.swift:72: error: XCTAssertNil failed: "QuickPlan(repo: "mlx-community/Qwen3.5-2B-4bit", …
  estimateS: 630)" - the plan for mlx-community/Qwen3.5-2B-4bit is still the one on screen under the new pick
FableS3F17Tests.swift:76: error: XCTAssertNotNil failed - the failed plan for the new pick was reported nowhere
Test Case '-[OhYesMLXKitTests.FableS3F17Tests testPlanFailureClearsThePreviousModelsPlan]' failed (0.001 s).
```

`XCTAssertTrue(first)` and `XCTAssertFalse(second)` both passed — the second fetch genuinely
failed — so the stale plan is the whole remaining state.

## Code path, as cited — every line number verified

- `AppModel.swift:490-509` — `planBenchmark`:
  - `:493` clears `benchmarkRefusal`, `:494` sets `planningRepo = repo`.
  - `:496-499` on success replaces `quickPlan`.
  - `:500-505` on `BackendError` clears `quickPlan = nil` and sets both `refusal` and
    `benchmarkRefusal`.
  - `:506-508` — `} catch { return false }`. No clear, no refusal, no message. `planningRepo` is
    already B, so nothing downstream distinguishes "the plan for A" from "the plan for B".
- `AppModel.swift:511-515` — `startBenchmark` runs `guard let quickPlan else { return }` then
  `start(.quickbench(repo: quickPlan.repo, …))`. The repo comes from the plan, not from the
  picker. So Start after a failed fetch runs A.
- `Screens/BenchmarkView.swift:24-31` — the picker's setter stores `selectedRepo` and calls
  `model.planBenchmark(repo: value)`; the picker's own label is `pick.title` (`:33-35`), so it
  shows B while `quickPlan` still names A.
- `BenchmarkView.swift:39-46` — the body renders `refusalSection(model.benchmarkRefusal)` when one
  exists, else `planSections(model.quickPlan)`. The generic failure sets no `benchmarkRefusal`, so
  the stale plan renders in full.
- `BenchmarkView.swift:244-250` — "Start Benchmark" is `.disabled(!model.canStartJob)` only;
  `canStartJob` is `oneSlotReason == nil` (`AppModel.swift:269-271`), which knows nothing about
  whether the plan matches the selection. So it is enabled.
- The stale plan is legible as A — `BenchmarkView.swift:135-138` prints
  `model.displayName(for: plan.repo)` and the callout says "Every cell uses …" — which is why the
  finding calls this detectable but unreported.
- How the generic catch is reached in production: `HTTPBackend.get` (`HTTPBackend.swift:164-169`)
  and `URLSessionTransport.data` (`:15-21`) let `URLError` (timeout, connection lost) and
  `DecodingError` (a plan body this client cannot read) propagate unchanged — `quickbenchPlan` at
  `:82-88` adds only its own `URLError(.badURL)` for a bad query. None of these is a
  `BackendError`, so all land at `:506`.

## What I did not verify

- The SwiftUI rendering (picker label next to the stale plan, Start enabled). The test covers the
  model state; the view lines are cited, not exercised.
- A real timeout against the backend (forbidden to start one). The `URLError` path is the same
  type a timeout produces, which is what the transport throws.

The plan on screen names its own repo, so an attentive user sees it, and the run that does happen is a correct run of model A; but "Start Benchmark" beside a picker showing B silently starting A is the kind of mismatch this app's one-thing-at-a-time promise exists to prevent.
