# S2-F3 — `runtime_version` is stamped on the first started visit only

**Verdict: CONFIRMED.** A cell whose nine batches straddle a runtime update publishes `PASS`
stamped with the cold visit's build; the hot visit's build is read by nobody and no downstream
guard can see it.

## The claim, restated

`measure._visit` assigns `result.runtime_version = handle.version` inside
`if result.cold_load_s is None` (`measure.py:861-865`). Every later visit starts the runtime
again and gets a fresh build — `Runtime.start` calls `self.version()` on each launch
(`runtimes.py:2327`) and passes it into `runtimes.Handle(version=...)`
(`runtimes.py:2355`) — but nothing reads `handle.version` after the first visit. A row's samples
can therefore come from two builds while the row names one, and guard 4
(`report._check_one_value_per_key`, `report.py:543-550`) compares one string per row, so it
cannot notice.

## Evidence — the source

- `measure.py:861-865`, the whole assignment block, indentation included:

  ```python
  for result in results:
      result.request_seed = seed
      if result.cold_load_s is None:
          result.cold_load_s = handle.cold_load_s
          result.runtime_version = handle.version
  ```

  `runtime_version` is two levels deep: the `for`, then the `if`. `request_seed` above it is
  outside the `if` and is stamped on every visit — the contrast is deliberate in this file and
  is exactly the shape the finding describes.

- `grep -n "handle.version" ohyesmlx/*.py` → one hit: `measure.py:865`. There is no other
  reader anywhere in the package. `FakeHandle`/`FakeRuntime` aside, the only consumer of a
  handle's version is this one line.

- The real handle *does* carry a per-visit build. `runtimes.py:2327` (`version = self.version()`)
  runs inside `start()`, and `runtimes.py:2355` passes it to the `Handle`. So the defect is not
  "the runtime reports a stale version"; it is "the loop keeps only the first one".

- `measure.py:854` computes `cold_visit = all(result.cold_load_s is None for result in results)`
  and `_visits` (`measure.py:721-738`) splits the budget across `VISIT_ROUNDS = 2`, so at the
  default `measured=9` every cell is started twice (5 batches, then 4).

## Evidence — the reproduction

`tests/test_fable_s2_f3.py`, two tests, driven through the real `_visit` loop and the existing
`test_measure` fakes. A `FakeRuntime` subclass answers version `0.25.6` on start #1 and
`0.25.18` on start #2 — the exact pair the project has already watched Osaurus cross, and the
pair guard 4's own docstring cites for its 1.15× step (`report.py:1633-1636`).

1. `test_an_update_between_visits_cannot_leave_a_pass_row` —
   `AssertionError: a row measured across 0.25.6 and 0.25.18 published PASS stamped '0.25.6':
   samples from two builds are one row`.
   The premises assert first: two starts happened, the handles carry `[0.25.6, 0.25.18]`, and
   the single row holds all nine samples.

2. `test_the_persisted_record_cannot_present_two_builds_as_one` —
   `AssertionError: the record publishes status PASS stamped '0.25.6' while the hot visit ran
   0.25.18`. This test also *runs* both version-reading guards over the record and shows they
   accept it: `_check_known_runtime_versions` (`report.py:1481-1494`) only refuses an `unknown`

**Control.** The same setup with `["0.25.6", "0.25.6"]` yields `PASS` stamped `0.25.6` with the
same two starts and nine samples, so the build change is the discriminating variable and not a
broken harness.

**Satisfiability.** Applying the finding's fix direction out of process (wrap `_visit`, compare
every started handle's version, mismatch → FAIL naming both) turns both assertions green:
`SIMULATED FIX -> FAIL | runtime build changed between visits: 0.25.6 then 0.25.18`. The test
is falsifiable, not one that can only ever fail.

## What the reproduction adds to the finding

The fix direction as written — "on mismatch set the row FAIL with both versions in the reason"
— is not sufficient on its own. `run_cells` calls `_set_status(result)` after **every**
`measured` visit (`measure.py:663`), and `_set_status` rewrites `status` and `reason` from the
samples. A FAIL set inside `_visit` that still returns `"measured"` is erased on the way out.
My first simulated fix did exactly that and the row came back `PASS`. The fix must return
`"skip"` (the shape `stream_experts_missing` already uses at `measure.py:870-874`) or record the
mismatch somewhere `_set_status` does not overwrite — a new field, or checked in `run_cells`
after the loop. That is a correction to the *remedy*, not to the claim.

## What I did not verify

- **A real Osaurus update mid-run.** No server, engine or app was started, per the rules; the
  version change is driven through the fake handle. That the fake matches the real handle's
  lifecycle is argued from `runtimes.py:2327, 2355`, not observed live.
- **Whether a mid-run update is reachable without a human.** Osaurus updates via its own
  updater or a user install; whether either can land between two visits of one cell (a cooldown
  is `cooldown_s`, default 30 s, between visits) is a timing question I did not test. It is
  clearly possible for a user who updates while a long grid runs, and the project has watched
  Osaurus move 0.25.6 → 0.25.18, so the window is real but not measured.
- **The other four runtimes.** The mechanism is runtime-agnostic (`handle.version` is the base
  `Handle` field), but I only exercised the fake.

## Why I agree with Medium

- Not Low: the row's published figures are attributed to a build that produced only the cold
  half of them, and the same project refuses the identical condition *between* run directories
  (guard 4, `report.py:1633-1636` — "the grid's held-constant variable moving"). The
  inconsistency is inside one row, where nothing looks.
- Not High: it needs an update to land inside the ~30 s cooldown between two visits of one
  cell. When it does, the row is not merely mislabelled — it is a mixed-build average, which is
  the "varied two things" failure this project is defined against; but the trigger is narrow and
  the raw samples survive, so the record can be re-read once a fix lands. Medium is right.
