# S4-F2 — verified

**Claim, one line:** a pip engine that `detect_all` reports as `installed: true` can be
unstartable from the app (no lab path recorded, app PATH is launchd's, no bundle-executable
fallback) while `install` refuses `already_installed` for ever — so the app shows
"Installed, tested" for a build no start can reach and offers no repair.

## Read

`ohyesmlx/engines.py:541-563` (`_detect_mlxlm`: lab copy → app venvs → harness venv),
`:526-538` (`_detect_optiq`: lab copy → app venvs → `~/.local/bin/optiq` → Dev checkout),
`:584-619` (`detect_all`), `:1242-1245` (the refusal), `:987-996`
(`start_new_session=True`), `:1294-1295` (`record_lab_path` as the last act);
`ohyesmlx/runtimes.py:163-172` (`ENGINE_BUNDLE_EXECUTABLES` is omlx/vmlx/osaurus only),
`:471-532` (`_engine_env`), `:534-580` (`_resolve_program`), `:588-608` (`_spawn` →
`RuntimeStartError` on `OSError`), `:2401-2430` (`MlxLm.start_command` →
`("python", "-m", "mlx_lm.server", …)`), `:2929-2930` (`Optiq.start_command` →
`("optiq", …)`); `ohyesmlx/server.py:536-552` (`/engines` hands `install: null` for an
engine already installed) and `:731-738` (the install job passes no `detect` override);
`app/Sources/OhYesMLXKit/BackendLauncher.swift:116-117` (child `PATH` is
`/usr/bin:/bin:/usr/sbin:/sbin`, only HOME/USER/LOGNAME/TMPDIR/LANG inherited);
`app/Sources/OhYesMLX/Screens/EnginesView.swift:152-174` (an installed engine renders a
status line and **no** Install button).

The mechanism, in order: `_detect_mlxlm`/`_detect_optiq` accept any existing console script
as evidence of installation; `install` gates on exactly that answer
(`if _installed(detect(), engine): return refuse("already_installed", …)`);
`_engine_env` adds PATH prefixes only for lab paths that are **recorded**, and
`record_lab_path` has exactly one caller — the install that just refused
(`grep -rn "record_lab_path" ohyesmlx/` → `engines.py:1295` only);
`_resolve_program` falls back only through `ENGINE_BUNDLE_EXECUTABLES`, which has no entry
for `python`, `mlx_lm.server` or `optiq`; `_spawn` turns the resulting `OSError` into
`RuntimeStartError("could not start <name>: … No such file or directory")`.

## Two corrections to the finding (the defect stands; the wording is off)

- For mlxlm the unresolvable token is `python`, not `mlx_lm.server`
  (`runtimes.py:2421-2424`). `/usr/bin/python` does not exist on this machine, so the
  ENOENT conclusion holds; it is raised on `python`.
- On a machine with **any other** pip engine's lab record the mlxlm start does not ENOENT —
  it resolves `python` and `mlx_lm.server` from that other venv. Here:
  `shutil.which("python", path=env["PATH"]) == …/engines/optiq-0.5.13/bin/python`, i.e.
  the control engine runs from OptiQ's interpreter, not from the harness venv detection
  reported (both carry `mlx_lm` 0.31.3 here, so no version divergence is visible today).
  The precise statement is therefore "the detected path is never used", whose two symptoms
  are ENOENT (nothing recorded) and aliasing to another engine's venv (something recorded).

## Not verified

- No app, engine or server was started and no process was spawned; the start failure is
  established from `_engine_env`'s PATH, `_resolve_program`'s fallback table and
  `_spawn`'s `OSError` → `RuntimeStartError` mapping, not from an observed ENOENT.
- How often the hard-kill-mid-pip state (route (a)) occurs is a launcher/runtime property,
  not code. The code part is confirmed: pip runs with `start_new_session=True`
  (`engines.py:995`), so it outlives a SIGKILL of the backend, and `record_lab_path`
  (`engines.py:1295`) runs only in the killed process. Note a *graceful* shutdown is
  different — `server._wait_for_done` → `engines.kill_running_steps()` kills the step's
  group mid-pip, leaving no console script, so detection then says not installed and a
  reinstall is offered.
- The partial-closure variant (console script written, later wheels not → broken import
  instead of ENOENT) was not exercised.
- S1 F7 (a `record_lab_path` that raises after a good install) is not verified here; it is
  a third route to the same state, as the finding says.
- "No repair path" is true of the product surface, not of the filesystem: deleting
  `<engines>/<name>-<ver>/` by hand makes detection false again. For the global-install
  route that means deleting the user's own uv/pipx install, and there is no such edit an
  app user is offered (`/engines` returns `install: null` for an installed engine,
  `server.py:549`; the Engines screen shows no Install button).
