# S5-F12 — verification

**Claim, restated in one line:** `osaurus_set_seqs` (`scripts/osaurus-pin.sh:46-67`) rewrites the
live `~/.osaurus/config/server-runtime.json` with a truncate-then-write `json.dump(open(conf,'w'))`
instead of `osaurus_settings._write_atomic`, is a second definition of the edit `pin` owns, and
accepts `0` despite its own message promising "a positive integer".

## What the code does (line numbers verified in this worktree)

- `scripts/osaurus-pin.sh:46-67` `osaurus_set_seqs` — the whole function.
- `:47-49` — the only validation: `case ${1:-} in ''|*[!0-9]*) ... return 1`. `0` is all digits,
  so it passes. The message on the failing branch says "expected a positive integer"
  (`:48`) — a check and its own stated rule disagree.
- `:61` — `json.dump(runtime, open(conf, 'w'), indent=2)`. `open(conf, 'w')` truncates the user's
  file, then the dump writes it. A kill in between leaves `server-runtime.json` empty.
- `:62-66` — the read-back (`capture_osaurus_settings`) and `write_baseline()` run *after* the
  live file is already rewritten, so a value that then fails validation has already replaced the
  user's setting and a kill inside that window has already emptied the file.
- `ohyesmlx/osaurus_settings.py:178-200` `_write_atomic` — the module's own temp-file-and-
  `os.replace` write, docstring at `:180-184` naming exactly the "half-written Osaurus config is a
  host that will not start" hazard this path skips.
- `ohyesmlx/osaurus_settings.py:282-283` `pin` — writes the *same* `server-runtime.json` through
  `_write_atomic`. So the file has two writers, one atomic and one not.
- `ohyesmlx/osaurus_settings.py:64-88` `TRACKED_KEYS` — the one list of settings that can move a
  measurement, with `("server-runtime.json", "concurrency.maxConcurrentSequences")` at `:73`. The
  shell function sets that key by its own literal (`:58-60`), so the definition of "which keys
  this module edits" now exists in two places — which is the "one definition of everything" rule
  in AGENTS.md.

## Reproduced

New file `tests/test_fable_s5_f12.py`, three tests, measured against the shipped script with no
stubs inside it. `$HOME` is a scratch directory (so `CONFIG_DIR`, `BACKUP_DIR` and the subprocess's
`Path.home()` are all scratch), the subprocess runs from a scratch two-file copy of the package
with no `.git` (the installed-app shape `writable_root` describes, so the baseline lands under
scratch `$HOME` and never in this repo), and the live config is hard-linked so an in-place truncate
is observable.

On unmodified code:

| test | result on current code |
| --- | --- |
| `test_zero_is_refused_like_the_message_says` | `returncode == 0`; stdout `osaurus server-runtime.json:concurrency.maxConcurrentSequences = 0 (baseline re-recorded)` |
| `test_a_valid_value_is_written_atomically` | `assert b'{...8...}' == b'{...4...}'` at index 161 — the hard link followed the same inode, so the in-place rewrite destroyed the original bytes |
| `test_a_rejected_value_never_touches_the_live_config` | `the live server-runtime.json was rewritten for a value that was then refused: it now holds {'maxConcurrentSequences': 0, ...}` |

All three clauses the finding names are demonstrated: `0` is accepted, the write is in place, and
the write precedes the read-back.

## Red-check (performed)

Applied both halves of the finding's fix direction, minimally and inside the same two files:
`|0` added to the `case` at `:48`, and the body changed to `json.loads(conf.read_text())` then
`s._write_atomic(conf, json.dumps(runtime, indent=2).encode())`. Result: **3 passed**. Reverted
with `git checkout -- scripts/osaurus-pin.sh`: **3 failed**, same three assertions.
`git status --short ohyesmlx/ scripts/` is empty.

## One correction to the finding's fix direction

The finding proposes "a `set_key`-style function in `osaurus_settings` (atomic write, read-back,
baseline) that both `pin` and the wrapper call". That is the right shape, but note what the
red-check shows: the two defects are independent and a *minimum* fix does not need the new
function — `+ |0` and `_write_atomic` together turn all three tests green. The consolidation is
still worth doing for the "one definition" rule (the key list at `:73` vs the literal at `:58`), but
it is a structural argument, not a behavioural one, and the finding does not present it as
anything else.

## Severity

The finding says Low, with confidence 75, and that is right. Nothing here is reachable by a remote
party or by another user; the damage is a user's own host config emptied by a kill inside a
millisecond window, and the pin's byte-exact backup at `$BACKUP_DIR/server-runtime.json` heals it
*if* a restore then runs — which F6/F7 own, and which is exactly why this is not its own higher
severity. The `0` half additionally needs someone to pass `0`; its real cost is that the bad value
is then re-recorded as the baseline, so the drift gate would bless it.

## What is not verified

- No real `~/.osaurus/config` was read or written. The scratch `$HOME` is the test's; the shipped
  host's files were not touched.
- The kill-inside-the-truncate-window was not actually performed (that would need a signal at a
  chosen syscall boundary). The non-atomicity is shown by inode identity instead: the hard link
  provably followed the truncate.
- Whether `write_baseline()` failing after a successful live write leaves the host pinned-but-
  unbaselined was not tested; it is F6/F7's ground, not this finding's.
- `osaurus_set_seqs` was never called with a real Osaurus host, and no server was started.
