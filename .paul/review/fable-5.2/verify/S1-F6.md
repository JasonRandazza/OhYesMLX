# S1-F6 — The event cap frees the job slot while the job's worker keeps running

**Claim, one line:** when a job reaches `MAX_EVENTS`, `_Job.append` stores `too_many_events`
plus `done`, sets only `cancel_requested`, and calls `_registry.finished(self)` — so the one
job slot is free while the module call (for quickbench, the call that owns the engine) is still
running, and a second quickbench can start a second runtime beside the first.

Where the finding lives: `S1-findings.md:57-65`. Dossier: `dossier-S1.md:20` covers
`_Job.append` (`server.py:176-202`) and `_Jobs` (`server.py:235-304`); the caps are listed at
`dossier-S1.md:17` (`MAX_EVENTS` 10,000 at `server.py:70`).

The test builds the registry and job directly (`server._Jobs`, `server._Job`), appends
`MAX_EVENTS` progress events (the worker is "inside a cell" — the loop breaks when the cap
fires), then claims a second quickbench job. Today `claim` returns `None`: the second job is
accepted. It also asserts the stream's ending is `error:too_many_events` + `done`, which passes
today. Nothing is started; no thread, server or engine is involved.

## The code path, with line numbers

1. **The cap branch.** `server.py:185-195`: at `len(self.events) >= MAX_EVENTS - 2` it sets
   `self.cancel_requested = True` (`:186`), stores an `error` with `code: too_many_events`
   (`:188-193`) and a `done` (`:194`), and marks `terminal = True` (`:195`).
2. **The slot is freed on the event.** `server.py:198-202`: `self.done = True`, notify, then
   `self._registry.finished(self)`. `_Jobs.finished` (`:256-259`) clears `running` at once. No
   `abort_requested`, no `engines.kill_running_steps()`, and no join of the job thread: the
   thread is a daemon started at `server.py:688-690` and nothing tracks its return.
3. **The module never learns that the server is done with it.** After `done`, further
   `job.append` calls return immediately (`server.py:178-179`), so the worker's events are
   silently dropped — but the worker keeps executing, because the only signal it has is
   `cancel()`, which quickbench probes *between* cells: `quickbench.py:772` (stage A,
   between engine plans), `:809` (stage-B format loop boundary), `:845` (sibling download
   loop), `:891` (sibling cell loop). There is no in-cell cancel probe; a cell in flight
   finishes with its engine resident.
4. **A second quickbench claims the freed slot.** `_post_job` calls `self.server.jobs.claim(job)`
   (`server.py:682-685`) before starting the thread; with `running` empty it accepts. A
   quickbench run starts its own engine (one engine resident at a time is the project's rule),
   so the second runtime is started while the first job's cell still holds one — the condition
   `AGENTS.md` voids a run for, and the second run's numbers look normal.

## Reachability

The finding itself rates reachability low, and I agree: `MAX_EVENTS` is 10,000
(`server.py:70`); a download emits one progress event per file plus a handful of logs; an
install emits a few per step; quickbench's nested download/evict emissions go to `_discard`
(`quickbench.py:146`, used at `:865`, `:919`, `:946`). I did not find a module path that
produces 10,000 job events today. This is a defect in the guard's own failure mode, exercised
here by driving `_Job.append` directly.

## What I did not verify

- How many events quickbench actually emits per cell/run — not measured; no quickbench was run.
- The second runtime being started: no engine, server or thread was started. Steps 3-4 are read
  from the code and from `registry.claim`, not observed as two live processes.
- Whether a fixed server would hold the slot until `_run_job` returns or set `abort_requested`
  (the finding offers both); the test asserts only the invariant that the slot must not be free.
