# S2-F11 — `latest` picks by file mtime and keys only on winners, so a repo can show a superseded number

**Claim (one line):** `quickbench.latest` keys its map on `best.repo` alone and orders by
`path.stat().st_mtime`, so (a) a repo the newest run measured and lost keeps an older run's
winning number, and (b) a results directory whose mtime is newer for any reason outranks a newer
run.

**Verdict:** reproduced, both halves.

## Code path

`ohyesmlx/quickbench.py:1036-1059`:

```python
found: dict[str, tuple[float, dict]] = {}
for path in root_path.glob(f"*/{SUMMARY_NAME}"):
    ...
    best = payload.get("best")
    repo = best.get("repo")            # :1050 -- the only key
    ...
    modified = path.stat().st_mtime    # :1054 -- the only ordering
    if repo not in found or modified > found[repo][0]:
        found[repo] = (modified, payload)
return {repo: payload for repo, (_modified, payload) in found.items()}
```

Two properties follow directly:

1. **Only winners are keyed.** A finished run contributes exactly one `repo → summary` entry, the
   one in its `best` block. Every other repo that run measured — including the chosen row it
   compared against in stage B — contributes nothing. So a run that measured X at 48 and had Y
   win leaves no trace of X's 48 anywhere in `found`, and an older summary whose `best` was X
   survives untouched.
2. **The ordering is the file's mtime.** Each summary already carries `best.measured_at`
   (`quickbench.py:426`, written by `_best(summary, started_iso)` at `:995`, and pinned in
   `docs/interfaces/v5-quickbench.md:192`), and the run directory's own name is its start stamp
   (`_stamp(started)`, `:567`). Neither is consulted.

Consumer: `ohyesmlx/server.py:1013` wires `summaries=quickbench.latest`, and
`_get_recommendations` (`:560-600`) turns each `best` block into `measured_here` for
`recommend.pick` (`recommend.py:206`). `Pick.measured_here` is rendered by
`app/Sources/OhYesMLX/Screens/ModelsView.swift:127,254` and `ResultsView.swift:170,177`. Its
docstring (`recommend.py:66-69`) states the intent: "``measured_here`` is this user's own run on
this Mac: the newest finished ``quickbench`` summary's ``best`` block". So the field's own
documentation promises "the newest", which is what both halves break.

### Half 1 — a superseded number is served

Run `20260901T100000Z` finished with `best = {repo: org/x, decode_tps: 60.0, measured_at:
2026-09-01T10:05Z}`. Run `20261101T100000Z` chose `org/x`, measured it at **48.0** in stage A
(`decode_tps: 48.0` on the stage-A cell record, as `_cell_record` writes it), and stage B's
sibling `org/y` won at 72.0.

```
AssertionError: a repo the newest run measured at 48 tok/s is served at 60 from an older run:
{'engine': 'mlxlm', 'format': 'stock4bit', 'repo': 'org/x', 'decode_tps': 60.0, 'ttft_s': 0.2,
 'measured_at': '2026-09-01T10:05:00+00:00', 'quick': True}
assert 60.0 != 60.0
```

The map serves `org/y` at 72.0 (correct) and `org/x` at 60.0 from a run two engine versions back.
The newest measurement of X on this Mac is 48.0 and it is on disk in the newer summary's
`stage_a.cells`, unread.

### Half 2 — mtime outranks the run's own timestamp

Two finished runs of `org/x`: the older run (`20260901T…`, `measured_at` 2026-09-01) with its
summary file `os.utime`'d to a newer mtime (9 000), the newer run (`20261101T…`, `measured_at`
2026-11-01) with mtime 1 000 — the shape a restored-from-backup or `cp -p`'d results directory
produces.

```
AssertionError: the older run was served because its summary file has the newer mtime:
2026-09-01T10:05:00+00:00
assert '2026-09-01T10:05:00+00:00' == '2026-11-01T10:05:00+00:00'
```

### How far the tests constrain the fix

Both tests are written to accept the finding's two fix directions rather than one implementation:

- Half 1 asserts `found["org/y"]` is the newer run's winner **and** that `org/x`, if present, is
  not 60.0. Dropping X's entry entirely (the finding's "drop a repo's older entry when a newer
  finished run measured that repo as a non-winning cell") and re-keying X to the newer run's 48.0
  both pass.
- Half 2 asserts only that the summary with the newer `measured_at` wins, so ordering by
  `best.measured_at` — or by the directory stamp, which is the same fact — passes.

## What I did not verify

- I did not reproduce this through `GET /recommendations` or the app's screens; I verified the
  `latest()` map, which is the one input to `measured_here` (`server.py:1013`) and the only place
  the choice is made.
- I did not confirm how often a results directory's mtime moves in practice. `_write_summary`
  writes a temp file then `os.replace`s it (`:456-466`), so a summary's own mtime is its write
  time, which for a finished run is the run's end — newer than `measured_at` but in the same
  order. The hazard needs a copy, a restore, or an unrelated rewrite; the finding names those and
  I did not measure their frequency.
- I did not check whether dropping a superseded entry would leave a `Pick` with no
  `measured_here` where it currently has a stale one. That is the intended effect of the fix
  direction, and the screen already handles null (`ModelsView.swift:127` is an `if let`).
- I did not assess whether re-keying X's entry to the newer non-winning number is even desirable:
  a `measured_here` block is a **winner**'s block (it carries `quick: true` and a `format` from
  `_best`), and a stage-A cell record is not shaped like it. The "drop it" direction is the
  cheaper one, and the test allows it.
