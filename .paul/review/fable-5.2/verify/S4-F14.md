# S4-F14 — A verified partial is renamed into place without fsync, and nothing downstream re-checks bytes

**Claim, one line:** `fetch.py:891-904` (`finish`) verifies the partial and `os.replace`s it into
place at `:902` with no `os.fsync` on the file before the rename or on the directory after it, so
a power loss or kernel panic seconds later can leave a blob of the right length and the wrong
contents; `downloaded` (`:272-298`) is size-and-link only (UAT-001) and `quickbench.plan` gates on
it alone (`quickbench.py:283`), so nothing downstream re-checks the bytes before an engine is
started — and a later `download` refuses with `integrity_failed … nothing was overwritten`
(`:798-806`), so the app cannot repair it either.

This finding has two halves; the first cannot be a test, the second can.

## Half 1 — no flush: evidence from the source, not a test

A power loss cannot be staged in pytest, so this half is the code path and one command:

```
$ grep -n "fsync" ohyesmlx/fetch.py
$
(no output; exit 1)
```

No `fsync` appears anywhere in `fetch.py` — not in `finish`, not in `_fetch_file`
(`:906-1122`), not in the helpers it calls. The finish sequence is exactly:

```
    def finish(planned_file: PlannedFile, incomplete: str) -> bool:     # :891
        if not _verify(planned_file, incomplete):                       # :892
            _remove(incomplete)
            return _refuse(… "did not match the catalog's {checked}; "  # :895-901
                              "the partial file was removed and nothing was linked")
        os.replace(incomplete, planned_file.blob)                       # :902
        created["blobs"].append(planned_file.blob)                      # :903
        return True
```

`_verify` (`:605-621`) hashes the file, so the bytes are correct **at the moment of the rename**.
The rename is a directory-entry operation that the filesystem journals independently of the
file's data blocks; without an `fsync` on the partial before `os.replace`, and on the directory
after it, a crash can leave the entry pointing at blocks that were never written out. The
resulting blob then has the right length (the size `_verify` checked) and arbitrary contents.

The test builds the exact state a rename-without-fsync leaves — a blob, snapshot link and

then asks `quickbench.plan` for the row. On the current tree it returns two stage-A cells, i.e.
a run would start engines against the corrupt artifact.

## The gate that is missing, with line numbers

`quickbench.plan`'s only content question is `downloaded`:

```
    model = _catalog_row(repo, models)                  # :282
    if not downloaded(model, cache_dir):                # :283
        raise ValueError(… "download it first" …)
```

`fetch.downloaded` answers size and link presence only (`:285-298`), and its docstring says so
plainly (`:277-283`): "a file of the right size but the wrong bytes reads as downloaded here,
which is the price of the cheap check and why ``_verify`` still runs after a transfer". That
`_verify` runs only in the download path; nothing runs it on the measurement path. `run` calls
`plan` again at `:559-560`, so the same gate is the only one a confirmed run passes.

The repair path is closed too: a later `download` of that repo hits the present-blob pass
(`fetch.py:798-806`) and refuses with `integrity_failed … nothing was overwritten`, so the app
has no way to replace the bad blob it wrote.

## Red-check

Two red-checks, because the first fix direction I tried is not the shippable one.

1. **The gate is what the test hinges on.** Give `plan` a `downloaded` that also runs
   `fetch._verify` on every planned file, and the plan refuses — the test passes:

   ```
   $ ... -c "<plan with a downloaded() that verifies each planned file>"
   refused: org/corrupt-oq4 is not in this Mac's Hugging Face cache; download it first -- …
   ```

2. **A naive verify inside `plan` is not the fix.** Adding an unconditional
   `fetch._verify` loop to `quickbench.plan` makes the new test pass but breaks 48 existing
   quickbench tests, because the suite's hand-built rows carry fake hashes
   (`tests/test_quickbench.py:56` `sha256="b" * 64`). That was reverted. It means the fix has to
   be reachable through an injected seam, not a hard call inside `plan` — a design note for
   whoever fixes this, not something I changed.

The source tree is unmodified (`git diff ohyesmlx/` empty), and all five files revert to failing.

## What I did not verify

I did not stage a power loss, a kernel panic or an actual `fsync` ordering — half 1 is evidence
from the source and a `grep`, and the report says so. I did not verify that macOS's APFS makes
the window narrower or wider than the finding assumes; the claim does not depend on that. I did
not test the app's Remove/Re-download path, only the backend refusal that closes it. I did not
try the finding's other fix direction (letting `download` replace a non-verifying blob it
ledgered) — that is a design change to the integrity rules, not a verification.

## Verdict

VERDICT: CONFIRMED (test: tests/test_fable_s4_f14.py::test_a_wrong_bytes_blob_of_the_right_size_is_planned_for_measurement)

SEVERITY-CHECK: agree — Low. The finding's own confidence is 55 and the reason is visible: both
halves need something unusual — a crash inside a few milliseconds of a completed download for
half 1, or an already-corrupt blob for half 2 — and the number it produces is a quick-run FAIL
labelled "quick: measured on this Mac", which `report._check_not_quick` keeps out of the
published tables (`quickbench.py:6-8`). What lifts it above cosmetic is that no path re-checks
the bytes and the repair path refuses, so the state is sticky; that is a real integrity gap
worth the `fsync` and a plan-time verify, but its trigger keeps it Low.
