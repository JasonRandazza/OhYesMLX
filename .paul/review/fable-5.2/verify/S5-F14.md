# S5-F14 — verification

**Claim, restated in one line:** the Osaurus app is recognised only at the two `/Applications`
spellings, so an install in `~/Applications` is invisible to `_resident_osaurus_pids` (the
stale-app refusal and the post-`osaurus stop` kill both miss it) and to
`ENGINE_BUNDLE_EXECUTABLES` (the CLI fallback under launchd's PATH).

## What the code does (line numbers verified in this worktree)

- `ohyesmlx/runtimes.py:149` — `OSAURUS_APP_BUNDLES = ("/Applications/osaurus.app",
  "/Applications/Osaurus.app")`. Two absolute paths, both under `/Applications`. No
  `os.path.expanduser`, no `env.home`, no probe of `osaurus doctor`.
- `ohyesmlx/runtimes.py:150-152` — `OSAURUS_APP_EXECUTABLES` is derived from that tuple
  (`Contents/MacOS/osaurus`), so it inherits the assumption.
- `ohyesmlx/runtimes.py:634-648` `_resident_osaurus_pids` — the match is
  `argv0[0] in OSAURUS_APP_EXECUTABLES` at `:644`, an exact full-path comparison against the
  derived tuple. An app at `~/Applications/...` has an argv0 that is not in it, so the pid is
  never returned.
- `ohyesmlx/runtimes.py:163-172` — `ENGINE_BUNDLE_EXECUTABLES["osaurus"]` is derived from the
  same tuple (`Contents/Helpers/osaurus`), so `_resolve_program` (`:563-565`) has no
  `~/Applications` candidate either.
- `ohyesmlx/runtimes.py:2300-2305` `Runtime.start` — this is what the miss costs: the pre-start
  refusal only fires on what `_resident_osaurus_pids` returned.
- `ohyesmlx/runtimes.py:1617-1635` `_kill_resident` — the post-`osaurus stop` sweep, also fed by
  `_listener_pids`, so an invisible app is not swept.

Three more consumers of the same table, which the finding names only partly:

- `ohyesmlx/engines.py:49` imports `OSAURUS_APP_BUNDLES`; `:499-505` `_detect_osaurus` calls
  `_first_existing(env, OSAURUS_APP_BUNDLES)` at `:501`. This answers the finding's own open
  question (confidence 50, "not checked how `/engines` detection locates the bundle"): it uses
  the *same* tuple, so an app in `~/Applications` reads as **not installed**, exactly as the
  finding's worst case guessed. The exposure is narrower than "the sweep misses it" — a user with
  that install cannot start an Osaurus cell at all through the app, because the engine is never
  offered.
- `ohyesmlx/quickbench.py:202` iterates `runtimes.OSAURUS_APP_EXECUTABLES` in
  `_osaurus_app_running` (`:178-207`), so quickbench's "is the app already running" check misses it
  too.

The asymmetry that makes this a defect rather than a platform assumption: the two sibling
detectors *do* consult the home directory.
`engines.py:512` `_detect_omlx` includes `os.path.join(env.home, ".omlx", "bin", "omlx")`, and
`engines.py:568` `_detect_vmlx` includes `os.path.join(env.home, ".local", "bin", "vmlx")`.
Osaurus is the one engine whose detection consults no user-scoped path.

## Red-check (performed)

Applied the finding's first fix direction — add the `~/Applications` spellings to the one tuple —
minimally, as two `os.path.expanduser(...)` entries appended to `OSAURUS_APP_BUNDLES`. Because both
`OSAURUS_APP_EXECUTABLES` and `ENGINE_BUNDLE_EXECUTABLES["osaurus"]` are *derived* from that tuple
(`:150-152`, `:168-171`), one edit turns both tests green. Result: **2 passed**. Reverted with
`git checkout -- ohyesmlx/runtimes.py` (`git status -- short ohyesmlx/` empty): **2 failed**, same
assertions.

That derived-tuple behaviour is itself the argument for the fix direction: the finding's "add to
the one tuple" works in one edit precisely because the table already has one definition.

## Severity

The finding says "Low on this Mac; Medium for the shipped app on other Macs". I agree with the
first half and would **lower** the second, because the finding's own unresolved question resolves
in the direction that shrinks the exposure.

- On *this* Mac: Low, and arguably below the threshold for this review at all — Osaurus is at
  `/Applications` here (AGENTS.md's sweep pattern and `docs/runtimes/osaurus.md` both assume it),
  so no behaviour changes.
- On *another* Mac: the finding's Medium rests on "the stale-app refusal never fires and the app
  stays resident at ~900 MB plus weights through every later cell". But `engines.py:501` uses the
  same tuple, so such a Mac reports Osaurus as **not installed** and no Osaurus cell is ever
  scheduled — there is no cell for a stale app to corrupt. That is the finding's own conditional
  ("the exposure shrinks to a CLI user"), and it is the branch that holds.
- The residual case is real but narrow: a **CLI** user who runs `ohyesmlx measure` (rather than the
  v5 app) on a Mac with Osaurus in `~/Applications`. Their stale app is invisible to the refusal
  and to the sweep. That is a genuine two-models-resident path, which is the rule AGENTS.md calls
  void-making — but it requires a non-default install *and* a CLI run.

So: Low stands for this Mac; I'd call the other-Mac case **Low**, not Medium, on the evidence that
`/engines` also misses it. If the intent was "Medium for a CLI user with a Homebrew `--appdir`
install", that is defensible — but the report should say that, not "the shipped app on other
Macs", because the shipped app cannot reach the state.

## What is not verified

- No real `ps` was read and no Osaurus app exists at `~/Applications` on this machine. The
  `ps` line is synthetic.
- The `engines.py:501` conclusion is read from the code (same imported tuple, `_first_existing`
  returning `None`), not exercised through the `/engines` endpoint — that would need the app or the
  localhost API, which the order forbids starting.
- A real Homebrew `--appdir` install was not performed, so the actual argv0 and bundle layout on
  such a Mac are assumed to match the `/Applications` shape (same bundle, different parent).
- `quickbench._osaurus_app_running`'s miss is read from `:202`, not tested.
- The case-insensitive-vs-case-sensitive volume interaction between `osaurus.app` and `Osaurus.app`
  in a user directory was not examined.
