# S2-F2 — the SSE loop waits on `select()` of the socket while reading through a buffered reader

## Claim

`transport.chat` reads the SSE body with `HTTPResponse.read1` (one HTTP chunk per call) but
waits on `select()` of the raw socket between calls, so bytes already sitting in the
`BufferedReader` are invisible until the socket delivers more: mid-stream, each delta is
stamped on the arrival of the *next* one; at the tail, the stream can appear not to have
finished at all.

## Code path (read, not inferred)

- `ohyesmlx/transport.py:241` — `stream_socket = connection.sock`.
- `ohyesmlx/transport.py:255` — `stream_reader = response`, an `http.client.HTTPResponse`.
- `ohyesmlx/transport.py:264` — `stream_socket.settimeout(None)`, so every read from here is
  blocking; the loop's only wait is the `select` below.
- `ohyesmlx/transport.py:265-292` — the loop: `select.select([stream_socket], [], [],
  min(1.0, remaining))` (270-275); on timeout `if not readable: continue` (278-279), which
  re-enters `select` without touching the reader; on readable, exactly one
  `chunk = stream_reader.read1(4096)` (280-281); empty chunk is EOF (290-291). There is no
  `peek`/`read`/drain of the reader before waiting again.
- The stdlib behaviour of that `read1` (inspected from this venv's Python 3.13.13,
  `http.client.HTTPResponse`):
  - `read1` → `_read1_chunked` → `_get_chunk_left`, whose first act on a new chunk is
    `_read_next_chunk_size` → `self.fp.readline()`. `self.fp` is the
    `BufferedReader` created from `sock.makefile("rb")`, so that `readline` performs one raw
    read of up to 8 KiB: it drains everything the kernel holds into user space.
  - `_read1_chunked` then caps `n` at `chunk_left`, so one call returns exactly one HTTP
    chunk's payload. Whatever else the fill captured stays in the `BufferedReader`, which
    `select()` cannot see.
- No `Connection: close` is requested. `chat` sends only `Content-Type` and optional
  `Authorization` (`transport.py:200-204`); captured on the wire, the request is
  `POST ... HTTP/1.1`, `Host`, `Accept-Encoding: identity`, `Content-Length`,
  `Content-Type`. HTTP/1.1 defaults to keep-alive, so a conforming server holds the socket
  open when the stream ends.
- The existing suite cannot see this: its only SSE server sends `Connection: close` and sets
  `close_connection = True` (`tests/test_transport.py:62-64`). EOF makes the socket
  permanently readable, which masks the wait by letting the loop walk the buffer one chunk
  per wake. All 43 tests in `tests/test_transport.py` pass on the current code.
- Blast radius when `total_s` / the stamps move: `report.py:806` (end-to-end percentiles),
  `report.py:861` and `1185-1228` (`aggregate_tps` divides completion tokens by summed
  `total_s`), `report.py:864,888` and `measure.py:945` (`first_request_s` is the first
  warmup's `total_s`), `measure.py:989` (`batch_spans`). Timestamps themselves:
  `transport.py:327-334` (content) and `323-326` (reasoning), `385` (`ended`), `478-480`
  (`ttft_s`, `last_content_s`, `total_s`).

## Not verified

- The finding's two questions — whether this has moved a *published* number, and how much —
  remain unmeasured. I did not start any runtime (the order forbids it), so no current
  Osaurus/vMLX run was checked. What is proved is the mechanism and that it is deterministic
  for a response that lands in one buffer fill; how often a runtime's flush pattern produces
  a multi-chunk fill is open. The 2026-09-15 oMLX evidence in the finding (0.5 ms
  `total_s − last_content_s`) says the tail stall did not occur in that run.
- I applied no fix, so I have not watched the two failing tests go green. The fix direction
  is a drain of the reader before selecting again (read while `response.fp.peek()`/a
  non-blocking read still yields bytes); `Connection: close` would only address the tail and
  would leave the mid-stream stamping shift in place.
- The 1.0 s `select` granularity is not part of this defect (the loop recomputes `remaining`
  each pass and `read1` blocks only after select says readable); I mention it only because a
  buffered chunk is released on the *next* wake, which can be up to 1.0 s away under
  keep-alive, and at EOF immediately.
