# S4-F3 — verified

**Claim, one line:** both download guards ask `hardware().disk_free_bytes` — the free space of
`/` — so a cache on another volume (a symlinked `~/.cache/huggingface`, or `HF_HUB_CACHE`) is
judged against the wrong disk: a download that cannot fit is accepted, and one that fits is
refused `low_disk`. The same root-volume number feeds `recommend`, which excludes every row
with "this Mac has N GB free".

## Read

`ohyesmlx/fetch.py:816-827` — the guard before any request:
`missing_bytes = sum(remaining(...))`, `needed = disk_needed(missing_bytes)`,
`free = hardware().disk_free_bytes`, `if free < needed: refuse("low_disk", …, free_bytes=free,
needed_bytes=needed)`.

`ohyesmlx/fetch.py:1144-1155` — the same three lines re-run before each file
(`free = hardware().disk_free_bytes` again).

`ohyesmlx/hardware.py:144-153` — `scan` walks `volume_paths()` and sets
`disk_free_bytes = free_bytes` only inside `if path == "/":`; every other volume goes into
`volumes` and nothing else.

`ohyesmlx/fetch.py:137-149` — which cache is used is *not* the root volume's business:
`default_cache_dir(env)` returns `HF_HUB_CACHE` when set, else
`$HOME/.cache/huggingface/hub`, and `plan` (`:218`) takes `cache_dir or default_cache_dir()`.
`cache_dir` is never converted into a free-space query anywhere in the module (`fetch` does
not import `shutil`).

`ohyesmlx/server.py:579-604` — `hw = self.server.scan()`, then both
`recommend.pick(hw, models, statuses, hw.disk_free_bytes, …)` and
`recommend.exclusion_reason(model, hw, hw.disk_free_bytes, …)`;
`ohyesmlx/recommend.py:141-146` renders the shortfall as "this Mac has {_gb(free_disk)} GB
free".

So: the number is the root volume's in both places, the write goes to `planned.cache_dir`, and
the per-volume data (`Hardware.volumes`) is scanned and has **no consumer** in `ohyesmlx/`
outside `hardware.py` itself (grep: `volumes` appears in `hardware.py`, its tests, and
`scripts/smoke_clean_account.py` only). The app decodes it (`Models.swift:100-166`) and every
screen and decision still reads `diskFreeBytes` (`YourMacView.swift:30`,
`ModelsView.swift:286-295`, `BenchmarkView.swift:256`).

## Consequences, confirmed by reading (not simulated)

- **ENOSPC mid-body really does escape.** `handle.write(chunk)` (`fetch.py:1076`) sits inside
  the `try` whose only clause is `finally: _close(response)` (`:1121`); `_fetch_file` has no
  `except OSError` for the write, and `fetch_file` (`:1124-1135`) only adds a residue to
  `created["blobs"]` when `_fetch_file` *returns*. An `ENOSPC` therefore skips that
  bookkeeping and leaves `download`, where the `finally` (`:715-718`) records an entry without
  the `.incomplete`, so `evict` cannot remove it. The server's job runner catches it as
  `except Exception` → `error code=internal` (`server.py:754-758`): no `low_disk`, no
  resumable-partial record.
- **The over-refusal hits every row.** `server.py:594` and `:603` hand the root number to both
  `pick` and `exclusion_reason`, so on the reversed configuration the Models list is empty
  with a per-row reason quoting the wrong disk.
- **Which production paths can reach a non-default cache.** `~/.cache/huggingface` being a
  symlink needs no configuration at all: `default_cache_dir()` returns
  `$HOME/.cache/huggingface/hub`, `open`/`os.replace` follow the symlink, and the guard still
  asks `/`. `HF_HUB_CACHE` reaches the **CLI** (`quickbench` has no `--cache-dir` flag, so
  `cache_dir=None` → `default_cache_dir()`), not the app: `BackendLauncher.swift:117`
  inherits only `HOME USER LOGNAME TMPDIR LANG`, so the app process does not see the user's
  `HF_HUB_CACHE`. D8 (`PLAN.md:21`) says "models in the HF cache by default; the user may pick
  another volume", and the per-volume map is already scanned — the finding's fix direction is
  consistent with both.

## One precision for the finding (it stands)

- `Hardware.disk_free_bytes` being `/`'s free space is not an accident:
  `.paul/orders/v5-t1-2-disk-budget.md:7` says "`disk_free_bytes` = free bytes on \"/\"", and
  `tests/test_hardware.py:247` pins it. The defect is in the consumers, as the finding's fix
  direction already says — a fix must not redefine the field.
