# S1-F1 — "Stop now" signals a stale own-pid ledger with no identity check

**Claim, one line:** `stop_own_engines` hands every entry in `<own pid>.json` to `_shutdown` with no
`(lstart, argv)` re-check, so a ledger file a killed predecessor left under a pid this process now
holds stops whatever that entry's pid, port and recorded stop command name now.

**Test:** `tests/test_fable_s1_f1.py::test_stop_now_does_not_signal_a_stale_own_pid_ledger_entry` —
**fails on unmodified `714e8f6`**.

```
$ /Users/jrazz/.local/share/ohyesmlx/test-venv/bin/python -m pytest -q tests/test_fable_s1_f1.py
E   AssertionError: Stop now signalled an entry this process never recorded: [(39197, 59999,
    ('osaurus', 'stop'))], with no identity check against 'Mon Jan  1 00:00:00 2024' /
    'not the process this pid names now'
FAILED tests/test_fable_s1_f1.py::test_stop_now_does_not_signal_a_stale_own_pid_ledger_entry
1 failed, 3 passed
```

The test writes the file a same-pid predecessor would leave at
`<root>/results/running-engines/<os.getpid()>.json`, containing an entry whose pid is a live,
unrelated process (`os.getppid()`) and whose recorded identity deliberately does not match it,
patches `_shutdown` so nothing is signalled, and calls `stop_own_engines(root)`. It asserts
`_shutdown` is never called. Today it is called with the stale pid, port and stop command.

## The code path, with line numbers

1. **A ledger file is keyed only by owner pid.** `_ledger_path` (`runtimes.py:1686-1690`) is
   `<writable_root>/results/running-engines/<os.getpid()>.json`. The JSON holds `pid`, `lstart`,
   `argv`, `serving_pid`, `serving_lstart`, `serving_argv`, `port`, `stop_command`
   (`:1747-1783`) — no boot id, no process-start-of-owner, nothing that distinguishes a prior
   boot that used the same pid from this one.
2. **Stale files are a supported condition.** An entry leaves the file only through
   `_forget_running_engine` (`:1786-1801`), which runs from `Handle.stop`. A SIGKILL of the
   backend skips it. The app itself can SIGKILL the backend on quit
   (`app/Sources/OhYesMLXKit/BackendLauncher.swift:99-100` and the grace→terminate→kill ladder at
   `:395-411`), and power loss / panic / forced restart do the same.
3. **Startup never cleans the own-pid file.** `cli.py:1151` calls `_recover_startup`
   (`cli.py:1064`), which calls `stop_orphaned_engines` (`runtimes.py:1867-1905`). Any file whose
   owner pid is alive is skipped outright — `runtimes.py:1890-1891`
   (`if _process_alive(int(owner)): continue`). When the pid has been recycled to the backend
   itself, the file that needs the orphan treatment is the one file the sweep refuses to look at.
4. **The next engine start merges the stale entry forward.** `_record_running_engine` rewrites the
   whole file, dropping only entries whose `pid` equals the new engine's —
   `runtimes.py:1770`: `entries = [entry for entry in _ledger_entries(path) if entry.get("pid") != pid]`.
   A stale entry for any other pid is written back unchanged.
5. **"Stop now" applies no gate.** `server.py:1012` wires `stop_engines=runtimes.stop_own_engines`.
   `stop_own_engines` (`:1908-1937`) iterates every entry and calls
   `_shutdown(pid, port, _entry_stop_command(entry))` (`:1930`). It never calls
   `_recorded_identity` (`:1800-1811`), which is the exact check `_stop_orphan` uses
   (`:1846-1863`) to drop a reused pid instead of signalling it. The docstring's premise — "Each
   entry goes through `_shutdown` with the pid this process spawned" (`:1914-1915`) — holds only
   for a file this process wrote; the code never establishes that the file is one.
6. **What `_shutdown` then does** (`:1656-1683`): runs the recorded stop command unconditionally
   (`:1672-1673`) — for an Osaurus entry that is literally `("osaurus", "stop")`
   (`:2556-2557`), i.e. the user's own server, not a process this run started; if the pid is
   alive, SIGTERM then SIGKILL its whole process group via `_signal_tree` (`:651`,
   `:1675-1681`); SIGKILLs every *other* listener on the recorded port via `_kill_resident`
   (`:1617`, `:1682`); then blocks until the port is free.

## The three checks that pass today (they document the mechanism, not the defect)

- `test_the_orphan_path_drops_the_same_entry_the_own_path_signals` — the same entry placed under
  a dead owner's file is dropped by `_stop_orphan` and never signalled. This isolates the defect
  to the missing gate on the own path.
- `test_a_stale_own_pid_entry_survives_the_next_engine_start` — shows step 4 concretely: after
  `_record_running_engine(5555, …)`, the file holds `[os.getppid(), 5555]`.
- `test_the_startup_orphan_sweep_skips_the_backends_own_pid_file` — shows step 3: the sweep
  neither signals the entry nor removes the file.

## What I did not verify

- **Pid reuse itself was not reproduced.** No reboot, no real collision. The test plants the file
  a same-pid predecessor would leave and asserts on the missing gate. That the collision is
  *possible* follows from the ledger carrying no boot identity and macOS restarting pid
  allocation at boot; that it is *frequent* is unmeasured, and the finding already says so
  (Confidence 70).
- **No real process was signalled.** The kill chain in `_shutdown` is cited from code and is
  already covered by `tests/test_runtimes.py::test_stop_kills_the_process_the_launcher_left_holding_the_weights`
  and `::test_stop_escalates_to_sigkill_when_sigterm_is_ignored`.
- **No fix was applied or validated**, per the order. The finding's fix direction (treat a
  pre-existing own-pid file as orphans at backend start; optionally gate `stop_own_engines` with
  `_recorded_identity`) is untested here.
