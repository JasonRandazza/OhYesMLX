# S4-F4 — Cancel and "Stop now" are not observed during a stage-B sibling download

**Claim, one line.** `quickbench.run` fetches a missing stage-B sibling with no cancel
callable and `emit=_discard`, so a Stop or Stop now pressed during a multi-GB fetch is not
observed until the transfer ends, and the caller receives no progress for it.

**Verdict: reproduced.** Three tests in `tests/test_fable_s4_f4.py` fail on the current code
with exactly the reported symptom, and all three pass when the call site is given a cancel
callable and a forwarding emitter in a throwaway copy (the repo's code was not touched).

## What the code does

- `ohyesmlx/quickbench.py:510-511` — `run` takes `cancel=_never_cancelled` and
  `abort=_never_cancelled`; the server hands it the job's real probes at
  `ohyesmlx/server.py:749-750`.
- `ohyesmlx/quickbench.py:853-866` — the stage-B sibling path sends one `progress` event
  naming the repo and its byte count, then calls

  ```python
  fetched = download(sibling.repo, True, cache_dir=cache_dir, emit=_discard) is True
  ```

  No `cancel=`. `emit` is `_discard` (`quickbench.py:146-152`), a function with an empty
  body.
- `ohyesmlx/fetch.py:662-677` — `download` accepts `cancel=_never_cancelled`
  (`fetch.py:482-483` returns False), and probes it at `:878`, `:923`, per chunk at `:1068`,
  per file at `:1139`, and at `:1167`. A wired probe would end the fetch within one
  `CHUNK_SIZE` read; the default one never does.
- `ohyesmlx/fetch.py:707`, `:718` — the cross-process lock is acquired before the transfer
  and released in the `finally`, so it is held for the whole of it. The server's job slot is
  equally held: `job.finished` runs only after `quickbench.run` returns
  (`server.py:743-751`).
- `ohyesmlx/quickbench.py:891-893` — the first look at `cancel()` after the download, and
  only when it succeeded. A failed download `continue`s at `:889` without reading it, so the
  next look is the next sibling's check at `:845` (or the run's tail).
- `ohyesmlx/quickbench.py:758-761` — `abort()` ("Stop now") is only read inside `measured`,
  i.e. around a cell, never around a download.

The only `cancel()` probes in the module are `:772` (stage A), `:845` (stage-B loop top) and
`:891`; the finding names the latter two correctly.

## Reproduction

`tests/test_fable_s4_f4.py` drives `quickbench.run` with the fakes `tests/test_quickbench.py`
already uses (no runtime, model, network or app) over a cache missing both stage-B siblings.
Its downloader records the keywords it is handed and, inside the call, does what a stop
landing mid-transfer would require the run to notice.

On the unmodified code:

```

FAILED tests/test_fable_s4_f4.py::test_a_stage_b_sibling_download_hears_stop_now
FAILED tests/test_fable_s4_f4.py::test_a_stage_b_sibling_downloads_progress_reaches_the_caller
```

- `…hears_stop` — `AssertionError: quickbench.run called the stage-B sibling download without
  a cancel callable, so a Stop pressed while it fetches is not observed until the transfer
  ends (quickbench.py:864-866; keywords handed in: ['answered_after_stop', 'cache_dir',
  'confirmed', 'emit', 'repo'])`. The recorded `emit` is `<function _discard at …>`.
- `…hears_stop_now` — the same assertion for the abort probe.
- `…progress_reaches_the_caller` — the download's emitted progress event never reaches the
  caller's emitter. The reproduced event list for two siblings is exactly the finding's "one
  downloading event and nothing after":

  ```
  ["stage B: downloading org/two-b-oq4 (3000000000 bytes)",
   "stage B: downloading org/two-b-jang (4000000000 bytes)"]
  ```

The tests assert behaviour, not mechanism: a `cancel` callable must be handed in and must
answer True once the run's own probe flips, and the download's progress must be visible to
the caller between the "downloading" event and the sibling's cell.

**Green direction, repo untouched.** A throwaway copy of the package at
`$COMMANDCODE_SCRATCHPAD/s4f4-green` was given exactly the finding's fix direction — the
download call gains `cancel=lambda: cancel() or abort()` and an `emit` that re-emits through
quickbench's own `send` — and `pytest -q tests/test_fable_s4_f4.py` run against that copy
reports `3 passed`. So the tests fail for the reported reason and are satisfiable by the
named fix, not vacuous.

## Shutdown claim in the scenario

`ohyesmlx/cli.py:1168` calls `listener.jobs.cancel_and_wait(server.JOB_SHUTDOWN_WAIT_S)`.
`server.py:277-292` sets `cancel_requested`, waits 120 s (`server.py:76`), calls
`engines.kill_running_steps()` — engine process groups, not a download thread — waits a
further 15 s (`server.py:81`), then emits `shutdown_abandoned`. A quickbench thread blocked in
`fetch.download`'s body read has no probe that reads `cancel_requested`, so the flag cannot
end it: the bound expires with the thread still in the transfer, as the finding says.

## The honest counterweight

The between-cell granularity is documented, not accidental: `quickbench.py:521-522` says "a
cancel is observed between cells and the harness's own stop path still runs for the cell in
flight", and `server.py:265-267` repeats it. A download is not a cell, so the code matches
that sentence. What the sentence does not cover is the cost: minutes of a fetch the user has
already stopped, the download lock and the job slot held throughout, and a shutdown that can
only abandon the thread. `_discard` also has a stated reason (`quickbench.py:147-152`: the
download's default emitter prints to the app's launch-line pipe), so the fix is to re-emit
its events through quickbench's `send`, not to hand it the default printer.
