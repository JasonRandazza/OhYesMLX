# S5-F3 — the one-model-resident check looks at one port and the Osaurus app only

**Claim restated:** `Runtime.start` refuses only when *its own* port is held or a *non-run-started*
Osaurus app is resident, so an engine still holding weights on any other runtime's port — a stop
that raised before it signalled anything, or a foreign listener quick-bench never claimed — is
invisible to the start that loads the next model beside it.

**Verdict: confirmed, on both halves, by test for (a)+(b) together and by code path for the
quick-bench consequence.** One item in the finding's evidence chain is mis-cited: `measure.py:843`
is the *start*-failure re-raise, not the stop one; the CLI abort on a failed stop comes from
`_visit`'s `finally` plus `run_cells`' re-raise. The conclusion it is used to support holds.

## The code, as shipped

The whole of the pre-flight, `ohyesmlx/runtimes.py:2295-2305`:

```

2296            raise RuntimeStartError(

2298                f"start; refusing to start {self.name} over it"
2299            )
2300        resident_osaurus = _resident_osaurus_pids()
2301        if resident_osaurus:

```

`RUNTIMES` (`:3804-3811`) names six ports: osaurus 1337, vmlx 8000, optiq 8080, mlxlm 8081,
omlx 8100, mtplx 8200. A start asks about exactly one of them.

`_resident_osaurus_pids` (`:634-648`), the exclusion at `:646`:

```
644        if pid_text.isdigit() and argv0 and argv0[0] in OSAURUS_APP_EXECUTABLES:
645            pid = int(pid_text)
646            if pid not in _RUN_STARTED_PIDS and _process_alive(pid):
647                pids.append(pid)
```

So an Osaurus app this run spawned is never "resident", alive or not:

```

not run-started -> (9191,)

```

`Handle.stop` (`:1981-1988`) — the shutdown first, the bookkeeping after:

```
1981    def stop(self) -> None:
1983        _shutdown(self.pid, self.port, self.stop_command)
1984        _RUN_STARTED_PIDS.discard(self.pid)
1985        if self.serving_pid is not None:
```

`_shutdown` (`:1656-1683`) raises **before** it signals anything on two paths, and it is the first
statement of the stop:

```
1665    listeners = _listener_pids(port)
1666    if listeners is None and stop_command:
1667        raise RuntimeStopError(
1668            f"cannot identify listeners on port {port}; refusing handoff cleanup"
1669        )
```

(`_listener_pids` returns `None` when `lsof` cannot be run at all — `:703-705` — and `_run`
returns `None` on `OSError`/timeout, `:569-585`.) The same early-raise shape exists at
`_signal_tree`'s `PermissionError` (`:656-659`) and `_signal_process`'s (`:674-675`). In all of
them the engine keeps its weights, keeps its port, and keeps its entry in `_RUN_STARTED_PIDS` —
which is exactly the set `:646` uses to decide the app is not resident.

Nothing between cells heals this. `_record_running_engine` is only written by a start
(`:2347`); `running-engines/` is read only by `stop_orphaned_engines` (`:1867`), whose one caller
is the app's launch recovery, `cli.py:1078` inside `_recover_startup`. A run in progress never
sweeps.

## The quick-bench half — code path, not a test

`RuntimeStopError` is a `RuntimeError` (`:451-460`), so it is an `Exception`:

- `measure._visit`'s `finally: handle.stop()` (`measure.py:917-920`) lets it out.
- `run_cells` writes the partial rows and re-raises: `except BaseException: write_jsonl(...);
  raise` (`measure.py:651-653`).
- `quickbench.measure_cell` catches it as one cell's failure (`quickbench.py:703-706`):
  `except Exception as error: return _cell_record(..., status="FAIL", reason=str(error))`.
- The loop appends that FAIL record and goes on: `summary["stage_a"]["cells"].append(record)` then
  `step(...)`, and the only breaks are `restore_failure`, `ABORTED`, and `cancel()`
  (`quickbench.py:792-811`). Stage B is the same (`:894-914`; its `try/finally` evicts and does
  not catch).
- No other port check happens at a cell boundary: `_skip_reason` (`:431-447`) probes **one** port,
  the cell's own engine's, and only at plan time (`:776`).

No test is offered for this half: driving `quickbench.run` needs the whole plan/catalog/engines
harness, and the finding's own test idea does not ask for it. The chain above is line-exact and
each link is a single statement.

**Correction to the finding's evidence:** `measure.py:843` `except RuntimeStopError: raise` is in
the **start** call's `try` (`:828-843`, the call at `:834`), i.e. it re-raises a runtime that
*failed to start*. The
CLI-vs-quickbench contrast the finding draws is real but runs through `_visit`/`run_cells` as
above, not through `:843`. This does not change the conclusion: an ordinary run ends, quick-bench
records a FAIL and proceeds.

## Why this is a defect and not a chosen scope

`docs/interfaces/measurement-core.md:375-378` pins the rule absolutely — *"**Exactly one runtime
may hold weights at any moment.** `run_cells` stops the current runtime and confirms its port is
free before starting the next."* — and its stated consequence is the one AGENTS.md repeats: the
run still completes and still looks plausible. The implementation confirms *a* port, not the
invariant. The two existing guards are per-engine, not global: quick-bench skips an engine whose
own port answers (`:439-447`), and `Runtime.start` refuses over its own (`:2295`). Neither can see
the other five ports.

## What I did not verify

- **No live two-model run.** The survivor and the failed stop are simulated at the seams the code
  itself uses (`_listener_pids` → `None` is the exact condition at `:1665`; a ps line plus
  `_process_alive` is what `:644-646` reads). I did not make `lsof` fail for real, and I did not
  measure the memory consequence — AGENTS.md and the predecessor record cover that.
- **No quick-bench end-to-end.** The FAIL-and-continue behaviour is read, not executed (see
  above). I did not verify the summary's `ended` field on that path, only that the loop does not
  break on a FAIL record.
- **The ledger consequence of a failed stop is left where it belongs.** The same early raise also
  skips `_forget_running_engine` (`:1987`), so the entry survives to the next app launch; that is
  S5-F4's ground and I did not test it.
- **Whether a *stop* failure can also occur after signalling** (the `SIGKILL` ladder at
  `:1679-1681` and `_kill_resident` at `:1632-1635`): those raise too, and my test does not
  exercise them. They would leave the same bookkeeping un-done and the same engine possibly alive.
