# S6-F5 — the clean-account smoke runs a wheel, not the bundle

**Verdict: CONFIRMED.** The committed smoke spawns `<venv>/bin/ohyesmlx app`, a console
script under the Homebrew CPython that installed a wheel built from `git archive HEAD`.
It never touches `dist/OhYesMLX.app`, passes none of the launcher's interpreter flags,
and inherits the client's environment instead of building one. 05-06-PLAN AC-6 asks for
the opposite in as many words.

Test: `tests/test_fable_s6_f5.py` (new file, 5 tests, all passing on the current code).
No product file was modified; the red-check was made and reverted (see §7).

---

## 1. The claim, in one line

05-06-PLAN AC-6 is the clean-account checkpoint meant to close threat-model P5-5's
"clean account pending", and it requires the built app's backend "via the bundled
interpreter, exactly the launcher's argv and env"; the committed smoke instead runs a
wheel console script under Homebrew's CPython, so the evidence it produces is about an
artifact no user receives.

## 3. What the smoke actually spawns

`scripts/smoke_clean_account.py:843` and `:850-855`:

```python
binary = os.path.join(sys.prefix, "bin", "ohyesmlx")
...
process = subprocess.Popen(
    [binary, "app"],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    stderr=log,
)
```

Four properties follow directly, and each is pinned by a test:

| Property | Where | Test |
|---|---|---|
| Child argv is `[<sys.prefix>/bin/ohyesmlx, "app"]` | `:843`, `:851` | `test_the_smoke_spawns_the_venv_console_script_with_no_interpreter_flags` |
| No `-I`, no `-B`, no `-m ohyesmlx.cli` | `:851` | same |
| No `env=` / `environment=`: the child inherits | `:850-855` | `test_the_smoke_inherits_the_client_environment_instead_of_building_the_launchers` |
| No flag can redirect it to a bundle | `:825-834` | `test_the_client_has_no_flag_that_could_point_it_at_a_bundle` |

`sys.prefix` is the interpreter running the *client*. The driver sets that interpreter
(`scripts/smoke_clean_account.sh`):

- `:20` — `PY=/opt/homebrew/bin/python3.14`
- `:145-154` — `git -C "$REPO" archive --format=tar HEAD` into a mktemp dir, then
  `uv build --wheel --out-dir "$SMOKE/dist"` from that extracted tree
- `:161-163` — `as_test_user "$PY" -I -m venv "$TEST_HOME/oymlx-venv"` then
  `pip install --no-deps --no-index "$SMOKE"/dist/*.whl`
- `:252-255` — the client itself runs as `"$TEST_HOME/oymlx-venv/bin/python" -I`
  (so `sys.prefix` is that venv)
- `:205` — the AC-6 sweep already expects `"$TEST_HOME/oymlx-venv/bin/ohyesmlx app"`,
  so the driver's own cleanup codifies the wheel spawn as the thing being run

`<venv>/bin/ohyesmlx` is the console script `pyproject.toml:34-35` declares
(`ohyesmlx = "ohyesmlx.cli:main"`). It is a shebang wrapper over the venv's
site-packages copy of the package — the `pip install` of a wheel built out of
`git archive HEAD`. It is not `Contents/Resources/python/bin/python3`, and the package
tree it imports is the wheel's, not the `ditto` of the working tree that
`scripts/build_app.sh:68` puts inside the bundle.

`test_the_driver_builds_a_wheel_from_git_archive_and_runs_it_under_homebrew_python`
asserts exactly that shape on the `.sh`, including the negative halves: the driver
contains no `dist/OhYesMLX.app` and no `Resources/python` anywhere.

## 4. The contrast the finding rests on

`app/Sources/OhYesMLXKit/BackendLauncher.swift:185`:

```swift
let argv = [interpreter.path, "-I", "-B", "-m", "ohyesmlx.cli", "app"]
```

`:212-220` builds the child's environment rather than inheriting it: `PATH` fixed to
`/usr/bin:/bin:/usr/sbin:/sbin` (launcherd's default, P5-9) plus `HOME`, `USER`,
`LOGNAME`, `TMPDIR`, `LANG` from the parent and nothing else. `:149-156` resolves the
production interpreter to `<Bundle>/Contents/Resources/python/bin/python3`.

`test_the_launcher_spawns_a_different_argv_than_the_smoke` reads that argv out of the
Swift source (rather than restating it) and asserts the smoke's argv does not match it.

## 5. Consequences, each with its evidence

**The engine venvs descend from Homebrew's CPython, not the bundle's.**
`ohyesmlx/engines.py:1173` defaults `python=sys.executable`; `ohyesmlx/server.py:732-738`
calls `self.server.install(job.name, True, macos_major=..., emit=..., cancel=...)` and
passes no `python=`, so the default holds; `ohyesmlx/engines.py:797` then runs
`["{python}", "-I", "-m", "venv", root]`. Under the smoke, `sys.executable` is the
Homebrew-built venv python; under the app it is the bundle's interpreter. The AC-4/AC-5
installs the smoke drives therefore produce a different kind of venv than a user gets —
same package set, different base interpreter, different `pyvenv.cfg`, different
`home =` line.

**The trust-store path exercised is Homebrew's, not macOS's.** Measured on this host:

```
$ /opt/homebrew/bin/python3.14 -c 'import ssl,sys; print(sys.executable); \
    print(ssl.OPENSSL_VERSION); print(ssl.get_default_verify_paths().cafile)'
/opt/homebrew/opt/python@3.14/bin/python3.14
OpenSSL 4.1.0 23 Oct 2026
/opt/homebrew/etc/openssl@4/cert.pem
```

The bundle ships python-build-standalone, and the threat-model's P5-4 evidence
(`docs/threat-model.md:601`) records that it verifies "using macOS's
`/etc/ssl/cert.pem`; no CA file is bundled". Two different CA bundles. A clean-account
green on the smoke says nothing about the one that ships — this is the finding's
"bundled OpenSSL/trust-store path is not exercised", and it is exact, not a hunch.
(`scripts/check_bundle.sh:105-133` does test the bundled interpreter's HTTPS under
`env -i`, so the property is not untested anywhere; it is untested *on a clean account*.)

**P5-3 is not exercised, and is inverted.** The launcher's `-I` is what P5-3 requires.
The smoke's child has no `-I` at all, so `PYTHONPATH`, `PYTHONHOME` and any user
site-packages would be honoured by the process whose behaviour is being recorded. Under
`env -i` (`smoke_clean_account.sh:38-41`) none are set, so the run happens to be clean —
but the property "the backend is started with `-I`" is not what is being demonstrated.

**P5-6's "nothing is written inside the bundle" has no implementation at all.** The
client never mentions a bundle:

```
$ grep -nE 'OhYesMLX\.app|codesign|Resources|bundle' scripts/smoke_clean_account.py
(no matches)
```

So the AC-6 "Then" clause about the bundle has no check behind it either, on any
artifact. That is beyond the finding's list and reinforces it.

**P5-9's PATH value coincides, by accident.** `smoke_clean_account.sh:38-41` runs
everything through `env -i` with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`, which is the same
value the launcher sets, so the engine-bundled-CLI property P5-9 protects does get
exercised (AC-5's quickbench drives real engines). What is not exercised is that
property *as produced by the launcher's own environment builder*, and `TMPDIR`/`LANG`
are absent where the launcher passes them. This is the one part of the finding that is
weaker than its wording implies, and it belongs in the report rather than being
argued away.

**The results cannot say which artifact ran.** `_finish` (`:930-936`) writes exactly
`head`, `started`, `ended`, `checks`. `--head` names the git revision the *wheel* was
built from. Nothing in the JSON names an interpreter, a bundle path, or an artifact kind,
so a results file from this smoke is indistinguishable from one that did test the
bundle. The finding's "Record in the results which artifact was run" is therefore a real
absence, not a stylistic preference.

## 6. Why the dossier's Q6 does not already settle it

`dossier-S6.md` §7 Q6 asks the same question and answers it as an open question:
"Is AC-6 meant to be a hand-run variant of the client against the bundled interpreter
(the scripts have no flag for it), or is the wheel smoke considered sufficient?"

This verification converts that to a defect. Q6's framing is what the scripts do; AC-6's
text is what was accepted. Where the two disagree, the plan is the specification and the
scripts are wrong. Q6 also notes the client would then run under the bundled python and
`parse_launch`/the `tests/` loader assume the repo checkout — a real constraint on the
fix, but it is a reason to give the client a `--python` flag (the fix direction the
finding names) rather than a reason the current behaviour is correct.
