# S1-F8 — Evict deletes `refs/main` because it once created it, even after another tool rewrote it

**Claim, one line:** `evict` removes every path in the ledger's `created_links` with a bare
`os.remove`, including `refs/main`, with no check that the file still holds the revision this
app wrote — while blobs get a "still referenced" test — so a `refs/main` that another tool
(`huggingface-cli download`) has rewritten to a newer commit is deleted, and the user's own copy
stops resolving by name offline.

Where the finding lives: `S1-findings.md:75-84`. Dossier: `dossier-S1.md:113` for `evict`
(`fetch.py:1186-1310`); the ref creation and ledger entry are in `_download`, mapped at
`dossier-S1.md:107` (`fetch.py:842-875`).

## Reproduction — the failing test

`tests/test_fable_s1_f8.py::test_evict_keeps_a_refs_main_that_no_longer_holds_the_ledger_revision`,
run against unmodified `714e8f6`:

```

E       AssertionError: evict removed refs/main, whose content is no longer what this app wrote
E       assert False
E        +  where False = exists()
1 failed in 0.26s
```

The test downloads `org/name` through the fake transport from `test_fetch` into a `tmp_path`
cache, then — as the other tool would — overwrites `refs/main` with a different 40-hex commit
and adds a snapshot for that commit pointing at the shared blob. The assertions before the
failing one already pass: the shared blob is kept (the reference scan found the other snapshot)
and the foreign snapshot directory is left alone. Only the ref is removed. No socket is opened
and no real cache is read or written.

## The code path, with line numbers

1. **The ref is created only when absent, and ledgered as a created link.** `fetch.py:871-874`:
   `make_dirs(planned.refs_dir, ...)`; `if not os.path.lexists(planned.ref_path):` writes
   `revision + "\n"`; `created["links"].append(planned.ref_path)` at `:874`. Because of the
   `lexists` guard, this app never rewrites a ref that already exists.
2. **The ledger keeps the revision.** `download`'s `finally` calls `_record` (`fetch.py:716-717`),
   which merges the created links in and writes the entry with `"revision": planned.model.revision`
   (`fetch.py:733`). The value the finding's fix direction needs is already there.
3. **Evict removes the link unconditionally.** `fetch.py:1250-1258`:
   `for path in entry["created_links"]: if not (os.path.islink(path) or os.path.lexists(path)):
   continue; try: os.remove(path) ...`. There is no read of the file, no comparison with the
   entry's `revision`, and no distinction between a symlink snapshot link and the regular
   `refs/main` file.
4. **Everything else in the same eviction is more careful.** Blobs are removed only when no
   snapshot anywhere still resolves to them (`_referenced_blobs`, `fetch.py:1261-1277`);
   directories are removed only when empty (`:1280-1288`). The `_inside` guard
   (`:1236-1244`) only refuses a ledger path outside the repo's own directory — the ref is
   inside it, so nothing stops this.

Note on the fix direction: because `_record` merges into an existing entry without refreshing
`revision` (`fetch.py:726-733` uses `ledger["repos"].get(repo) or {...}`), the ledger's revision
is what this app recorded first, and the app never rewrites an existing ref (`:872`). Comparing
the file's content against that revision therefore errs toward keeping a foreign ref, which is
the safe direction for this defect.

## What I did not verify

- A real `huggingface-cli download` run, or the user's offline resolution failure: the test
  models the tool's observable effect (a rewritten `refs/main` plus its own snapshot) and
  asserts the file survives; it does not resolve a model by name afterwards.
- A real cache or network path; the transport is the injected fake.
- Whether a fixed evict should also keep the `refs/` directory when it still holds the file —
  not part of the claim, and today the directory rmdir is guarded by emptiness anyway.
