# S5-F6 — the shell pin and the app pin keep "the only copy" in two different directories

**Claim (one line):** the shell runner backs Osaurus's originals up to
`~/.osaurus/config.phase4-orig` and traps only `INT TERM HUP`, while the app backs up and recovers
in `<Application Support>/OhYesMLX/quickbench/osaurus-backup`; because `pin` refuses only over a
backup in the directory it is handed, a shell pin that dies outside its trap leaves the host
pinned with the app's recovery blind to the backup — the app's `pin` then copies the *already
pinned* files as "the user's settings", its `restore` verifies byte-exact against that copy, and
the run records `restored: True` over idle 900 / caches off.

## What the finding gets right, and what it does not

Right, and sharper than stated:

- The two directories and the one-argument-shaped refusal are exactly as cited; the shell's backup
  path is not derivable from `quickbench` and `quickbench`'s from nothing in the shell.
- `restored: True` is reachable over the pinned state without any exception being raised
  (test 2, `quickbench.py:718-719`).
- The `INT TERM HUP`-only trap, with no `EXIT`, is real, and the shell has no `recover` call
  anywhere (`grep recover scripts/` finds none).

Where the finding is imprecise, in both directions:

- It says a shell run "dies outside the trap (SIGKILL, SIGQUIT, power loss, panic, a `set -u`
  abort)". In `run_canary.sh` the realistic trigger is narrower than that list suggests but not
  empty: `set -u` with **no** `set -e` (`:12`) means a failing command does not end the script, so
  `$PY -m ohyesmlx.cli canary` crashing at `:38` still reaches `osaurus_restore_check` at `:41` and
  the pin is put back. What is left after the pin (`:37`) is an unset expansion between `:37` and
  `:41` (`$ENGINES`/`$RECORD` are both set, so today nothing fires), and the signals neither trap
  can catch: SIGKILL, SIGQUIT, power loss, panic. So the window is real but is the kill/power one,
  not the ordinary-failure one. No test asserts it; it is read from `run_canary.sh:12,37,38,41`.
- The mirror case it mentions (backend killed mid-pin, then a shell run) heals only at the next app
  launch *and only while Osaurus is not running* (`cli.py:1089-1092` returns early with
  `recovery_pending`), so it too can persist across launches if the app is left open — the finding
  says this, and its `cli.py` citation supports it.

Nothing in the finding is wrong. The one thing it does not say, and which its own severity argument
should carry, is the baseline re-anchoring above: the state is not merely lingering, it is
*self-certified* by the guard that would otherwise notice.
