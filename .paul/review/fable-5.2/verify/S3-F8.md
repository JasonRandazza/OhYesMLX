# S3-F8 — the single-instance lock lives in the app, not the backend, so a crashed or force-quit app can be relaunched beside a backend that is still unwinding

**Claim (one line):** the `flock` on `app.lock` is held and released only by the app
process, and no Python-side lock exists, so when the app dies its descriptor closes, the
lock is free at once, and a relaunch starts a second backend while the first is still in
`cancel_and_wait(120 s)` + 15 s with its engine holding the model.

## Code path, as cited

- `app/Sources/OhYesMLXKit/BackendLauncher.swift:260-269` — `acquireLock`:
  `open(app.lock, O_CREAT | O_RDWR, 0600)` then `flock(LOCK_EX | LOCK_NB)`, non-blocking.
  `start()` returns `.alreadyRunning` when it fails (`:170-172`).
- `:501-528` — `handleTermination` / `releaseLockIfNeeded`: the lock is released when the
  *child* is reaped. A crash or force-quit never runs that path; the kernel closes the
  app's descriptor instead. Either way the lock's lifetime is the app process's.
- `ohyesmlx/cli.py:1151` — the backend runs `_recover_startup()` before printing the launch
  line. `cli.py:1157`, `:1184-1202` — `_stop_at_eof`: stdin EOF calls `listener.shutdown()`.
- `cli.py:1168` + `ohyesmlx/server.py:76`, `:81` — the `finally` path is
  `listener.jobs.cancel_and_wait(JOB_SHUTDOWN_WAIT_S)`, which is 120 s, then
  `engines.kill_running_steps()` and `JOB_KILL_GRACE_S` = 15 s. With a quickbench (or
  install/download) in flight the old backend outlives the app by up to 135 s, and its
  engine keeps the model until the job's own cleanup runs.
- No Python-side lock: `grep -n 'flock\|app\.lock\|LOCK_EX' ohyesmlx/` has no match. Nor is
  `_recover_startup` a substitute: `runtimes.stop_orphaned_engines` skips a ledger whose
  owner pid is alive (`runtimes.py:1890`), and the old backend is alive — the old engine is
  deliberately not stopped, so the overlap is unconstrained rather than limited.

## Reproduction

Test: `app/Tests/OhYesMLXKitTests/FableS3F8Tests.swift::testAppDeathDoesNotFreeTheLockWhileTheBackendIsAlive`
(new file; no production code touched).

The test uses the real `BackendLauncher`, the real `acquireLock`, and the real
`FoundationLauncherProcess`. The only double is the interpreter: a `/bin/sh` script that
prints the launch line, writes its own descriptor table (`/dev/fd/*` plus
`lsof -p $$ -Ffn`, renamed into place when complete), then `sleep 5` — it ignores stdin
EOF, standing in for a backend in its shutdown wait.

1. Start the launcher. The child's table shows **no `app.lock` descriptor** (fds 0, 1, 2,
   10, 11 are pipes; 255 is the script). The child does not inherit the lock, so the
   lock dies with the app.
2. Control: the same second launcher returns `.alreadyRunning` while the app's descriptor
   is still held — the launcher really does refuse, so a later `.running` is caused by the
   descriptor's disappearance.
3. Model the app's death: `dup2` `/dev/null` over the test process's `app.lock` descriptor.
   That is the kernel's effect on a dying process (the open file description closes and the
   flock is released); the number stays occupied so the live `LaunchSession`'s later
   `close()` cannot land on the second launch's pipes.
4. A fresh `open` + `flock` on `app.lock` succeeds — the lock is free. The second launcher
   returns `.running` — a second backend, while the first is asserted alive immediately
   before.

Consequence after the second backend starts (read, not run):
- On launch it runs `_recover_startup()` (`cli.py:1151`). `stop_orphaned_engines` skips the
  live old backend's ledger, so the old engine is not stopped; and
  `osaurus_settings.recover` (`osaurus_settings.py:364-384`) puts back and removes a
  leftover Osaurus backup whenever the Osaurus app is not running (`cli.py:1084-1105`).
  If the old quickbench job had pinned the host, that backup is the one its `pin` still
  relies on, so the old cell's end-of-cell drift check sees a host that moved and its
  `restore` finds no backup — the cleanup race the finding names.
- The new app adopts the new backend, `loadInflight()` restores the interrupted job
  (`AppModel.swift:382`), `showsInterruptedBanner` (`:190`) shows `InterruptedBanner`'s
  Retry (`RootView.swift:42-52`), and `retryInterrupted()` (`AppModel.swift:546-559`)
  starts the same job on the new backend while the old backend is still running it — two
  engine servers and potentially two resident model loads, hotspot 5.
