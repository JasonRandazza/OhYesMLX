# S1-F7 — A lab-path refusal after the pip steps leaves a venv nothing rolls back or records

**Claim, one line:** `install.run_steps` calls `record_lab_path` after the step loop and outside
any handler, so a `ValueError` from it (a lab directory the check refuses, or an existing
`lab-paths.json` with an entry `lab_paths` refuses) unwinds after the install has already
succeeded: `created` is never rolled back, the installer emits no `error`/`done`, the venv stays
on disk unrecorded, and the server reports only an `internal` error.

Where the finding lives: `S1-findings.md:66-74`. Dossier: `dossier-S1.md:76` for
`record_lab_path` (`engines.py:465-496`) and `dossier-S1.md:84` for `install`
(`engines.py:1159-1340`, with `run_steps` at `:1250-1297`).

## The code path, with line numbers

1. **`record_lab_path` is after the loop and outside the failure branch.** `engines.py:1294-1295`:
   `if installed_bin is not None: record_lab_path(engine, installed_bin,
   path=_lab_paths_beside(engines_dir))`. The only `_rollback` calls are in `cancelled`
   (`:1235`) and the failed-step branch (`:1278`), each followed by its own `done`
   (`:1236`, `:1280`). A raise at `:1295` passes both.
2. **Both of its checks raise `ValueError`.** `record_lab_path` (`engines.py:465-496`) calls
   `check_lab_dir(bin_dir)` at `:493` — refusing a non-absolute, non-directory, other-owned, or
   group/other-writable `bin` (`:387-411`, the mode test is `S_IWGRP | S_IWOTH` at `:409-410`) — then
   `entries = lab_paths(path)` at `:494`, which refuses an unknown engine key, an app-engine
   key, a non-string path, bad JSON or an unreadable file (`:413-462`).
3. **No handler in `install`.** `run_steps` (`:1250-1297`) has no `try` around the step loop; the
   outer `try`/`finally` (`:1324-1340`) releases the engine lock only. The `ValueError`
   therefore leaves `install` as a raise, not a refusal.
4. **The server turns it into `internal`.** `_run_job` (`server.py:754-758`) catches any
   `Exception` and appends `error` code `internal` plus `done`; `_job_code` records `internal`
   in the end line. That is the only `error` the client ever sees, and it names neither the
   lab-path file nor a rollback.
5. **The leftover poisons a retry.** On a production install `engines_dir` is the app-support
   `engines/`, which is exactly what detection reads: `_app_engine_venvs` (`engines.py:340-347`)
   builds `engines/<name>-<version>`, `_app_engine_scripts` (`:350-351`) turns each into a
   `bin/` script, and detection uses those for optiq (`:530`) and mlxlm (`:548`). So the second
   attempt is refused `already_installed` at `:1242`, and the engine can never start from the
   unrecorded venv because no lab path names it.

The second trigger named in the finding — a `bin` left group-writable under `umask 002`, refused
by `check_lab_dir` — is the same `:493` raise and the same outcome. I read it; I did not exercise
it (the deterministic trigger above is enough to show the path).

## What I did not verify

- A real `python -m venv` / `pip install`: the subprocess seam fabricates the directory a real
  venv step creates, and both steps are replayed as exit 0. The ordering under test does not
  depend on how the venv was made.
- The `umask 002` branch of `check_lab_dir` with a real directory mode (asserted by reading
  `engines.py:409-410`, not by creating a 0775 dir).
- `detect_all` finding the leftover: the test injects `engines_dir=tmp_path/engines`, so the
  venv is not under the app-support path detection scans. Step 5 is read, not executed.
- Any real engine, download or install.
