# S6-F3 — check_bundle's P5-6 signature check cannot fail for the defect it was written for

Verified 2026-11-16 against `review/fable-verify` (base `714e8f6`). Nothing was built,
started, downloaded, installed or launched as an app. Evidence is read-only use of the
shipped artifact at `/Users/jrazz/Dev/active/OhYesMLX/dist/OhYesMLX.app` (built 2026-11-14
from `101df7c`, `codesign --verify --deep --strict` exits 0), scratch copies under the
session scratchpad, and commands whose output is quoted below.

## The claim, in one line

The P5-6 step runs the app only from a `UDRO` image, where a write into the bundle cannot
land, and then verifies the signature of that same immutable image — so the regression it
guards ("a child interpreter writes bytecode into the signed bundle") can never make it
fail, and the step never even causes a child interpreter to run.

## The code path, at the cited lines

- `scripts/check_bundle.sh:143-145` — `hdiutil create -quiet -srcfolder "$APP" -format UDRO`.
  The image is made from the bundle **before** the app is opened, and `UDRO` is read-only.
- `scripts/check_bundle.sh:147-150` — `hdiutil attach -nobrowse -readonly -mountpoint "$MOUNT"`.
- `scripts/check_bundle.sh:154-156` — the mount table must say `read-only`; this is the only
  property the step asserts about writability, and it asserts it in the direction that makes
  a write impossible.
- `scripts/check_bundle.sh:158` — `open "$MOUNT/OhYesMLX.app"`: the only process launched is
  the app, from the read-only mount.
- `scripts/check_bundle.sh:186-198` — the only HTTP request:
  `curl … "http://127.0.0.1:$PORT/hardware"`, no `Authorization`, and
  `case "$CODE" in 200 | 401) break` followed by a `pass` for each of `200` and `401`.
- `scripts/check_bundle.sh:252-254` — the only `codesign --verify` in the script (grep: one
  hit) is `codesign --verify --deep --strict "$MOUNT/OhYesMLX.app"`. `$APP` itself is never
  verified after the image is created, and nothing is written back to it by the run.

Two consequences follow mechanically:

1. Every write the run attempts under `$MOUNT` fails with `EROFS`. CPython ignores a failed
   bytecode write (`importlib._bootstrap_external._write_atomic` catches `OSError`), so the
   failed write is not even an error the check could observe. The image's bytes — and so its
   seal — are unchanged no matter what the app does.
2. The verify compares the read-only image with the signature embedded in it. For the
   property P5-6 names, that comparison can only fail if the original bundle's seal was
   already invalid, which `scripts/build_app.sh:107` verifies at build time and would have
   stopped the build.

## The other half: the check never reaches the write path

- `scripts/check_bundle.sh:186` is the only request the step makes, and it carries no
  `Authorization` header.
- `ohyesmlx/server.py:419-438`: `do_GET` → `_guarded("GET")` → `_route()` only if `_guard()`
  returns true. `server.py:440-458` compares the bearer token and calls
  `_refuse("unauthorized")`; `server.py:460-464` writes the 401. `_get_hardware`
  (`server.py:532-534`) is never entered. `tests/test_server.py:238-246` already pins the
  401 for a missing token, and `:259-265` that the guard runs before the router.
- Even a hypothetical `200` would only reach `hardware.scan`, which shells out to
  `sysctl`, `sw_vers` and `ioreg` (`ohyesmlx/hardware.py:132-142`) — no Python child.
- The only Python process the step starts is the backend, and it is `-I -B`
  (`app/Sources/OhYesMLXKit/BackendLauncher.swift:183-185`); the check asserts that argv at
  `scripts/check_bundle.sh:201-207`. The interpreter that writes pycs is the child
  `{python} -I -m venv` at `ohyesmlx/engines.py:797`, reached only by an engine install,
  which needs a user action the check never takes. Launch-time engine detection
  (`engines.py:584-624`) reads `pyvenv.cfg`/version files only.
- The app's own authenticated requests on launch (`app/Sources/OhYesMLXKit/HTTPBackend.swift:71,75`)
  hit `/hardware` and `/engines`; neither handler spawns an interpreter. So the claim that
  the step never causes a child interpreter to run holds.

## What this means

P5-6 as implemented proves "the app works where it cannot write", not "nothing is written
inside the bundle". The threat-model status row (`docs/threat-model.md:603`) cites this run
as evidence that "`codesign --verify --deep --strict` still passes"; that sentence is true
and carries no information about child-interpreter writes, which is the regression the row's
own known-fix history names ("before that fix, child interpreters wrote stdlib bytecode into
the bundle"). The F1 condition passes this gate, a no-precompile build passes this gate, and
the only remaining failure mode is a bundle that was already invalid before the image was
made — a build-time error `build_app.sh` already refuses.
