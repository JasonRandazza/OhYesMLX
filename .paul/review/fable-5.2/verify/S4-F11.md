# S4-F11 — Quick-bench deletes the user's own partial download of a sibling

**Claim, one line:** stage B gates on `if not sibling_plan.downloaded:` (`quickbench.py:852`),
and `downloaded` is a whole-repo, size-and-link question (`fetch.py:272-298`, UAT-001), so a
sibling the user already downloaded to 80% reads as missing; the run resumes it (`fetched` is
then True, `:864-866`) and the inner `finally` evicts the whole repo (`:914-921`), whose ledger
entry merges every download into one list (`fetch.py:721-745`) and whose `evict` removes every
path in it (`:1250-1277`).

**Test:** `tests/test_fable_s4_f11.py::test_the_users_own_partial_of_a_sibling_survives_the_runs_eviction`
— **fails on the current tree** (`review/fable-verify`, base `714e8f6`).


The test uses the **real** `fetch.downloaded` and the **real** `fetch.evict` against a scratch
cache, and a `download` seam that finishes the same repo's transfer. The user's partial is
written and ledgered through the real `fetch._record`, which is exactly what an interrupted
`download` leaves (`fetch.py:715-718`). Everything is 400 bytes; nothing is hashed from the
network, no model is loaded and no runtime is started.

## What the cache holds afterwards

The same fixture, dumped instead of asserted on:

```
blob before: False incomplete before: True
ok True ended finished evicts ['org/small-oq4']
  FILE /models--org--small-stock/snapshots/aaa…/model.safetensors 400 link
  FILE /models--org--small-stock/blobs/cccc…c 400
  FILE /models--org--small-oq4/refs/main 40
ledger: { "repos": {} }
```

The sibling's repo is left with only its `refs/main` file: the user's 320 bytes of partial and
the run's completed blob are both gone, the ledger entry is empty, `not_evicted` is `[]`, and
the run reports `finished`. Nothing anywhere tells the user the bytes they fetched from the
Models screen are gone.

## The code path, with line numbers

1. **The stage-B decision is whole-repo.** `sibling_plan.downloaded` comes from
   `downloaded(sibling, cache_dir)` at `:299`; `fetch.downloaded` requires every file's link
   and blob at the catalog size (`fetch.py:285-298`) and documents that a `.incomplete` alone
   is **not** a download (`:280-283`).
2. **So a partial reads as missing, and the run fetches.** `:852-866` downloads it and sets
   `fetched = True`; `:890` adds it to `outstanding`.
3. **The eviction is unconditional on what was already there.** `:914-921` calls
   `evict(sibling.repo, True, …)` whenever `fetched`.
4. **The ledger entry is per repo and merged, never replaced.** `fetch._record` (`:721-745`)
   reads the entry already there (`:729-736`) and appends the new paths to its existing lists
   (`:737-741`). The entry `evict` walks is therefore user bytes + run bytes.
5. **`evict` removes everything in the entry.** `fetch.py:1250-1258` removes every
   `created_links` path, `:1261-1277` every `created_blobs` path and its `.incomplete`, and
   `:1280-1288` the directories.
6. **The contract it breaks is written twice.** `quickbench.py:20` — "**The user's chosen model
   stays.** Only a sibling this run downloaded is ever evicted" — and the app's Stage B row at
   `app/Sources/OhYesMLX/Screens/BenchmarkView.swift:175-180`, which says either "already on
   disk" or "one extra download, <size>". Neither describes deleting a partial the user
   started.

## Red-check

With the eviction gated on the sibling having had no bytes on disk at plan time (and the repo
dropped from `outstanding` in that case, so the run-level sweep does not take it instead), the
test passes and the whole quickbench suite is unaffected:

```
$ ... -m pytest -q tests/test_fable_s4_f11.py tests/test_quickbench.py
60 passed in 0.15s
```

Reverted, it fails again. The source tree is unmodified (`git diff ohyesmlx/` empty).

## What I did not verify

No network, no `fetch.download`, no model, no runtime: the transfer is a seam and the "80%" is
320 literal bytes. I did not verify the app's actual Models-screen resume path (`fetch.download`
with a real `Range` request); the finding needs only that the partial it leaves is ledgered,
which `tests/test_fetch.py:1075-1076` already pins and which this test reproduces through
`fetch._record`. I did not test the case where the user's partial is of a *different revision*
of the same repo (`_record` overwrites `revision`, `:742`); that would be a separate finding.
