# S5-F1 — verified

**Claim, one line:** `_engine_env` prefixes every lab-paths entry to PATH for every engine
rather than only the engine being started, so on this Mac (where `lab-paths.json` names only
`optiq`) the mlx-lm control cell's bare `python` resolves inside OptiQ's venv — mlx-lm 0.31.3
on mlx 0.32.4 rather than the control venv's mlx 0.32.2 — and the version probe reports
`0.31.3` either way, so no row can tell the two apart.

## Read

`ohyesmlx/runtimes.py:471-531` (`_engine_env`, the loop at `:510-528` builds one `prefixes`
list over `manifest.items()` with no engine argument anywhere); `:508-509` (both loaders);
`:528-531` (one PATH, one join); `:569-586` (`_run` calls `_engine_env()` with no arguments);
`:588-608` (`_spawn`, same); `:2421-2424` (`MlxLm.start_command` → bare `"python"`);
`:2463-2464` (`MlxLm.version_command` → `"python", "-m", "mlx_lm", "--version"`);
`:2120-2130` (`Runtime.version` → `_run` → that command); `:534-580` (`_resolve_program`,
whose `ENGINE_BUNDLE_EXECUTABLES` at `:163-172` has keys `omlx`/`osaurus`/`vmlx` only, so
`python` gets no bundle fallback); `ohyesmlx/engines.py:384` (`LAB_ENGINES = ("mlxlm", "optiq")`),
`:387-410` (`check_lab_dir`), `:413-462` (`lab_paths`), `:465` (`record_lab_path`).

Dossier S5 §7 Q6 (lines 464-470) already records the mlx-lm venv preflight as UNENFORCED,
but frames it only as "a host without that entry starts `python -m mlx_lm.server` from
whatever `python` resolves to" — it does not reach the stronger fact verified here: on a host
*with* the OptiQ lab entry, the control's `python` is pulled **away** from its own venv.

`mlxlm` is the only runtime whose start command is a *generic* program name; the other five
are unique engine names that a venv's `bin/` cannot shadow by accident.

### The failure is real on this Mac, not just in a fixture

`lab-paths.json` on this machine is exactly what the finding says:

```
$ cat "$HOME/Library/Application Support/OhYesMLX/lab-paths.json"
{
  "optiq": "/Users/jrazz/Library/Application Support/OhYesMLX/engines/optiq-0.5.13/bin"
}
```

The harness's own real environment, then, resolves the control's interpreter into OptiQ's venv:

```
$ python -c "from ohyesmlx import runtimes; import shutil
env = runtimes._engine_env()
print(shutil.which('python', path=env['PATH']))"
/Users/jrazz/Library/Application Support/OhYesMLX/engines/optiq-0.5.13/bin/python
```

OptiQ's venv has a `python` — the finding's Confidence note asked for this, and it holds:

```
$ ls -l ".../engines/optiq-0.5.13/bin/python"
python -> python3.14
python3.14 -> /opt/homebrew/opt/python@3.14/bin/python3.14
pyvenv.cfg: command = .../python3.14 -m venv .../engines/optiq-0.5.13
```

So it is a venv, not a stray shim, and its `sys.prefix` is the OptiQ tree. The two venvs
differ exactly as claimed — same `mlx_lm`, different `mlx` core:

| venv | mlx_lm | mlx | `mlx_lm --version` |
|---|---|---|---|
| `…/engines/optiq-0.5.13` | 0.31.3 (`_version.py`) | **0.32.4** | `0.31.3` |
| `~/.local/share/ohyesmlx/mlx-lm-0.31.3` | 0.31.3 (`_version.py`) | **0.32.2** | `0.31.3` |

```
$ .../optiq-0.5.13/bin/python -c "import mlx.core as mx; print('mlx', mx.__version__)"
mlx 0.32.4
$ .../mlx-lm-0.31.3/bin/python -c "import mlx.core as mx; print('mlx', mx.__version__)"
mlx 0.32.2
```

Both `python -m mlx_lm --version` invocations print `0.31.3`, so `Runtime.parse_version`
(`runtimes.py:2132-2134`, first line of stdout) returns an identical stamp for either
interpreter. The row field is `runtime_version` (`measure.py:865`, `:1464`); nothing anywhere
in `ohyesmlx/` reads or records `mlx.core.__version__` or any `mlx-*.dist-info`
(`grep -rn "__version__" ohyesmlx/*.py` returns only the harness's own `0.3.0` and
`engines.py:228`'s manifest parser for engine version literals). The canary row's fields are
`[…] 'runtime_version', 'status', 'warmup_count', …` with no mlx core version.

**The runners do not save it.** Every `scripts/run_*.sh` begins
`export PATH="$HOME/.local/share/ohyesmlx/mlx-lm-0.31.3/bin:$PATH"` (20 scripts). That is the
*ambient* PATH, and `_engine_env` prepends the lab prefixes ahead of ambient — so the export
loses:

```
$ PATH=".../optiq-0.5.13/bin:$HOME/.local/share/ohyesmlx/mlx-lm-0.31.3/bin:/usr/bin:/bin" \
    sh -c 'command -v python; python -c "import sys,mlx.core as mx; print(sys.prefix, mx.__version__)"'
.../engines/optiq-0.5.13/bin/python
.../engines/optiq-0.5.13 mlx 0.32.4
```

Also `_resolve_program` does not intervene: `python` is not in `ENGINE_BUNDLE_EXECUTABLES`,
and the name *does* resolve under the harness PATH, so the early-return at `:556-557` leaves
the command untouched.

### What is NOT yet reached

No mlx-lm cell has been measured since the lab copy appeared. `lab-paths.json` was born
`2026-10-30 13:24:21` (and the `optiq-0.5.13` directory `2026-10-30 13:23:50`, both written by
`engines.install`), while the only mlx-lm canary row is
`results/canary/20261029T201017Z-mlxlm/results.jsonl`, born `2026-10-29 16:15:15` — before.
`find results -name results.jsonl -newermt '2026-10-30 13:24'` returns no file mentioning
`mlxlm`. So the finding's strongest phrasing — that already-published rows were joined under
one stamp across a changed mlx core — is **not** true of the corpus on disk in the main
checkout: the previously published mlx-lm rows predate the lab copy and are clean. The defect
is live and would corrupt the *next* control cell, not any existing one.

## Other things checked

- The `_engine_env` docstring at `:476-479` still describes the pre-change command ("five of
  the six start commands begin with a bare name (`mlx_lm.server`, `optiq`, `vmlx`, `osaurus`,
  `omlx`)"). Today `MlxLm.start_command` begins `"python"` (`:2421`) and `Mlplx`'s begins an
  absolute path — so the docstring's enumeration is stale in two ways (it names a token the
  command no longer starts with, and counts five when only four start with a bare name). This
  is a documentation defect on the same lines, not a behaviour one; it is worth naming because
  it is the reason the `python`-vs-`mlx_lm.server` widening was not noticed.
- `LAB_ENGINES = ("mlxlm", "optiq")` and `lab_paths`'s refusal of other names means the leak
  set is these two. With both recorded, the failure is symmetric: OptiQ's environment gets
  mlx-lm's prefix too (harmless only by luck — `optiq` is not in mlx-lm's bin).
- The app path is unaffected in the ordinary case: `BackendLauncher` gives the child
  `/usr/bin:/bin:/usr/sbin:/sbin`, where neither venv's `python` exists, so a launch with no
  lab paths fails loudly rather than silently measuring the wrong build (that is S4-F2's
  finding).

## Not verified

- Whether mlx 0.32.2 → 0.32.4 moves tok/s. The finding says it does not claim a number and
  neither do I; the defect is that the harness cannot say which one it measured. I did not
  start a server.
- Whether OptiQ's venv and the control venv have byte-identical `mlx_lm` installs (only their
  `_version.py` and `dist-info` were compared; a patched `site-packages` would be invisible to
  the version string as well, which sharpens rather than weakens the finding).
- The `python3`/`python3.14` aliases: the same reasoning applies but only `python` is cited by
  a start command.
