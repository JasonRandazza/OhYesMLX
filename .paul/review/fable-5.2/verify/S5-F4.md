# S5-F4 — An orphan entry that cannot be verified is dropped without a word and its ledger file deleted, so the engine is never recoverable

**Claim restated:** when `_stop_orphan` cannot *prove* an entry names a live engine — `lsof` returned
`None`, or the recorded `lstart`/argv no longer equals today's `ps` answer — it returns silently, so
`stop_orphaned_engines` treats the entry as handled and unlinks `<owner>.json`. The engine keeps its
port and its weights and no later launch looks at it again.

**Verdict: confirmed on the drop-and-delete path, with one part of the finding refuted — the DST
sub-claim is wrong.**

## The code, as shipped

`ohyesmlx/runtimes.py:1827-1864` (`_stop_orphan`) has six early `return`s, all before the single
`_shutdown` call at `:1864`:

```
1841:        return                     # pid/port not ints
1845:        return                     # listeners is None  <- lsof failed
1853:            return                 # live launcher whose identity is unproved
1857:                return             # a listener whose identity is unproved
1861:            return                 # nothing listening: no recorded identity / pid dead
1863:            return                 # nothing listening: identity mismatch
1864:    _shutdown(pid, port, command)  # the only stop
```

The caller (`stop_orphaned_engines`, `:1867-1905`) removes the file whenever no exception was raised:

```
1893:        for entry in _ledger_entries(path):
1894:            try:
1895:                _stop_orphan(entry)
1896:            except RuntimeStopError as error:   # the only thing that keeps the file
1897:                failures.append(str(error))
1898:                failed = True
1899:        if not failed:
1901:                path.unlink(missing_ok=True)
```

A drop raises nothing, so `failed` stays `False` and `:1901` deletes the only claim on the process.
`:1908-1940` (`stop_own_engines`) reads `<this pid>.json` only, and `cli.py:1078` is the one caller of
`stop_orphaned_engines` — I grepped `RUNNING_ENGINES_DIRNAME|_ledger_path|running-engines` across
`ohyesmlx/` and there is no other reader of the ledger, and no stale-port sweep at launch. So
"never recoverable" is exact: the file is the whole record.

`_run((PS, "-ww", "-o", "lstart=,args=", "-p", …))` at `:1735` runs with `_engine_env()` (`:572`),
which is `dict(os.environ)` (`:527`) — the ambient `LANG`/`LC_*`/`TZ`. The finding's evidence line is
accurate.

## Why this is not merely theoretical: the module builds its own unprovable entry

`_record_running_engine:1763-1768` deliberately writes `lstart: None, argv: None` when the launcher's
`ps` call fails, and its docstring (`:1757-1758`) calls that *"recorded without an identity rather
than failing the start"*. `tests/test_runtimes.py:3775-3805` pins that shape as intended and asserts
no stderr. If that launcher pid is still alive when the sweep runs, `:1849-1853` sees
`launcher is None` and returns — and the probe recorded below shows the file goes. The module
produces, on purpose, an entry the recovery path is guaranteed to discard.

## The identity sub-claim, and the one part that is refuted

`ps -o lstart=` does render from the caller's locale and `TZ`. Through the module's own
`_process_identity` on one live pid, varying only the environment:

| environment | `lstart` for the same pid |
|---|---|
| ambient (`LANG=C.UTF-8`, host `America/New_York`) | `Sun Nov 15 16:50:19 2026` |
| `TZ=UTC` | `Sun Nov 15 21:50:19 2026` |
| `TZ=Asia/Tokyo` | `Mon Nov 16 06:50:19 2026` |
| `LC_ALL=de_DE.UTF-8` | `Mo. 16 Nov. 06:50:19 2026` |

The argv halves were identical in all four. So a recorder in one environment and a checker in another
genuinely cannot match — that half of the finding stands, and it is enough on its own.

**But the DST mechanism named in the finding is wrong, and I am refuting that part.**
`ps` renders via `localtime()`, which resolves the UTC offset **in effect at that instant**, not
today's:

```
winter (Jan 15) epoch=1768496400  ->  Thu Jan 15 12:00:00 2026 EST
summer (Jul 15) epoch=1784131200  ->  Wed Jul 15 12:00:00 2026 EDT
```

Both conversions ran at the same "now" (2026-11-15, EST). A start recorded before a DST transition
still renders at the hour it happened, so *a DST change between record and check does not move the
rendered hour*. The finding's confidence of 50 on "locale/DST being hit in practice" should be split:
the locale/TZ half is demonstrated, the DST half is not a mechanism at all.

## This is written down as intended, and two green tests enforce it

`docs/interfaces/v5-hardening.md:32-34` says, in the contract:

> An unreadable port, a stranger listening, or an identity that no longer matches — a reused pid, or
> the user's own identical command started later — **is dropped and never signalled** … A stop that
> does not take effect keeps the file and raises `RuntimeStopError`.

And two existing tests pin the deletion, passing today:

```
$ … -m pytest -q tests/test_runtimes.py::test_an_unreadable_port_is_dropped_and_never_signalled \
                     tests/test_runtimes.py::test_a_listener_whose_recorded_identity_no_longer_matches_is_dropped
2 passed in 0.43s
```

So the finding is a **contract** objection, not a code/contract mismatch. Any fix must change that
paragraph and those two tests in the same commit — which is why I am reporting rather than fixing.

The asymmetry the contract encodes is defensible for safety (never signal an unproved process) and
indefensible for recovery (the unproved process keeps 20 GB). The finding's fix direction — keep the
file plus one stderr line when the recorded pid is alive or the port is listening but identity is
unproved — separates the two: nothing is signalled *and* the claim survives. `LEDGER_ERROR_CODE`
(`:143`) exists for the line.

## Severity

The finding's Medium is right, and I would not raise it: the harm needs a start that was already
orphaned (crash/SIGKILL, F5's window), plus one failed probe or one environment mismatch, and it
costs memory and one port until reboot — not a published number. The interaction it names with F3 is
real and confirmed there: a later start checks only its *own* port (`:2295`) and the Osaurus app
(`:2300`), so a different runtime will measure beside the orphan. What the orphan cannot do is corrupt
a number by itself.

I would not lower it either: the locale half needs no fault at all, and the module manufactures one
of the unprovable shapes on purpose.

  that nothing listens on 8081 — the control case in my first counterfactual run reached the real
  `_shutdown` before I faked it, and it did so against a nonexistent pid on an unheld port.
- I did not reproduce the real-world *trigger* (a CLI-shell record followed by a launchd-environment
  check on the same machine). I showed the two environments render the same pid differently, which is
  the mechanism; I did not stage the cross-process handoff.
- I did not run a grid, so I did not observe a dropped entry in production state. The evidence is the
  code path, the tests, and the measured silence.
- The 20 GB figure is the finding's, from AGENTS.md's 35B MoE resident size; I measured no footprint.
