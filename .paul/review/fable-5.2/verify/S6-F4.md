# S6-F4 — After the app moves, an engine venv still reads installed and tested, and the doc's reinstall is refused

Verified 2026-11-16 in the `fable-verify` worktree (branch `review/fable-verify`, base `714e8f6`).
Nothing was started: no app, engine, server, model or download. The only temporary file outside the
repo was a throwaway venv in the session scratchpad, removed after the two commands quoted below; the
new test writes only under pytest's `tmp_path`.

## The claim, in one line

Engine venvs are built from the bundled `sys.executable`, so when that bundle path goes away (the app
is moved) or changes minor (a later release replaces it), the venv's `bin/python` no longer leads to an
interpreter — but detection reads only regular files and keeps reporting the engine installed and
tested, while `install` refuses the reinstall the gatekeeper doc promises with `already_installed`, and
there is no uninstall surface.

- `ohyesmlx/engines.py:265-279` — `_venv_package_version` reads `pyvenv.cfg` and then

  `bundlePath.contains("/AppTranslocation/")`; nothing else about the bundle's location is checked.
- `docs/release/gatekeeper.md:21-24` — "If you move the app **after** you have installed engines, open

## The unstartable half, at the executable level

A real venv's interpreter is a symlink whose chain ends at an absolute path in the base install — the
shape is the same for the app's bundled Python. This machine's test venv shows it directly:

```
$ head -1 /Users/jrazz/.local/share/ohyesmlx/test-venv/bin/pytest
#!/Users/jrazz/.local/share/ohyesmlx/test-venv/bin/python
$ ls -l .../test-venv/bin/python*
.../bin/python     -> /Users/jrazz/.local/share/uv/python/cpython-3.13-macos-aarch64-none/bin/python3.13
.../bin/python3    -> python
.../bin/python3.13 -> python
```

Reproducing the post-move state with a scratch venv (short `/tmp` alias because a shebang is limited to
127 bytes; the venv itself lives in the session scratchpad, then removed):

```
--- live: demo runs ---
hello
exit=0
--- after the bundle moved (target gone), console script's shebang -> <venv>/bin/python ---
/bin/sh: /tmp/f4-venv/bin/demo: /tmp/f4-venv/bin/python: bad interpreter: No such file or directory
demo exit=126
/bin/sh: /tmp/f4-venv/bin/python: No such file or directory
python exit=127
```

At start time the harness never reaches that shell error: `MlxLm.start_command` is
`("python", "-m", "mlx_lm.server", ...)` (`ohyesmlx/runtimes.py:2421-2434`) and `Optiq.start_command`
is `("optiq", "serve", ...)` (`:2929`). `_engine_env` (`:471-531`) prefixes the recorded lab directory —
still present, still a private directory, so it passes `check_lab_dir` — which puts the dead
`<venv>/bin/python` and `optiq` ahead of everything. `_resolve_program` (`:534-565`) finds neither
(the dangling link is not executable; `ENGINE_BUNDLE_EXECUTABLES` at `:163-172` has no `python` or
`optiq` entry), and `_spawn` (`:588-609`) turns the `OSError` into
`RuntimeStartError("could not start <program>: [Errno 2] No such file or directory ...")`. That is the
finding's "No such file" — on `optiq` it is literally the console script's dead shebang; on `mlxlm` it
is the `python` the command names from the same `bin/`.

## The "later release, different Python minor" arm

Checked, with one deviation from the finding's wording. Replace the app in place at the same path with a
build carrying another minor: `bin/python` now resolves, but the venv's packages are still under
`lib/python3.13`, so a 3.14 interpreter sees no venv site-packages:

```
--- control: 3.13 base, the venv's own minor ---
42
exit=0
--- the same venv path after the app is replaced with a 3.14 build ---
3.14.10
[]                                # no site-packages on sys.path
ModuleNotFoundError: No module named 'fakepkg'   (exit=1)
```

So the minor-change arm is real but its symptom is `ModuleNotFoundError` / "No module named ...", not
ENOENT. Everything the finding claims follows anyway: detection still reads the old minor's `pyvenv.cfg`
and version file and reports installed + tested, and `install` still refuses. The trap is identical; only
the printed error differs.

## What I did not verify

- I did not run the app, so `sys.executable` under the launcher is read from
  `BackendLauncher.swift:149-156,185` and `engines.py:1173`, not observed in a live backend. The venv
  shape was reproduced with another interpreter (same absolute-symlink-into-the-base-install shape), not
  with the bundled python-build-standalone.
- I did not test macOS translocation itself (no app launch). "A quarantine-free copy in `~/Downloads` or
  `~/Desktop` is not translocated" is documented macOS behaviour; the code only ever checks the
  `/AppTranslocation/` substring, which is what makes the finding's non-default trigger reachable.
- I did not click through the Engines screen; the refusal is proven at the `install` surface every
  install path goes through (`server.py:732-738` → `engines.install`).
- I did not verify a repair passes, because the order forbids fixing the code. The test is red on the
  current code in the three places a fix must change: detection must return not-installed for a venv
  whose `bin/python` does not resolve, and `install` must not answer `already_installed` for it.
