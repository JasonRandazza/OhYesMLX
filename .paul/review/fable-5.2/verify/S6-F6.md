# S6-F6 — the SBOM can name a commit that does not hold the shipped code, and its digest is of the repository, not the bundle

## The claim, in one line

`scripts/build_app.sh:68` `ditto`s the working tree into the bundle — uncommitted and
untracked files included — and no script ever asks `git status`; `make_sbom.py` then stamps
`git rev-parse HEAD` as "the git commit it was built from" (`docs/release/gatekeeper.md:59`)
and a `source_sha256` computed over `$ROOT/ohyesmlx/*.py` at SBOM time, which covers only
top-level `.py` files — so a dirty release names a commit that does not contain its code, a
mid-build edit is hashed although it did not ship, and the shipped data files are unhashed.

## The artifact settles the first claim — no hypothetical needed

The release on this Mac already exhibits it. `dist/OhYesMLX-0.3.0-sbom.json` says:

```
"generated": "2026-11-14T22:09:47Z"
"app": { "name": "OhYesMLX", "version": "0.3.0",
         "git_commit": "bb762c6fe8de443fda1ee63f7462e8081364dc54",
         "source_sha256": "0a17bd4e9c98ee27ca32bbe1bef2c6390d949c2d023bdc7f4a30fb81753848ed" }
```

Hashing each top-level `*.py` blob of `bb762c6`'s tree with `_source_sha256`'s exact
construction (`git show <commit>:<path>`, names sorted, digest updated with each file's
bytes) gives `bde0d125d999c5616af15ca433828d65122a2733a4973c7b1b4ef4294d734c22` — **not** the
recorded digest. The recorded digest is the digest of what shipped: the same construction
over `dist/OhYesMLX.app/Contents/Resources/python/lib/python3.14/site-packages/ohyesmlx/*.py`
is `0a17bd4e…3848ed`, and so is the tree of commit `101df7c`. That commit was created at
`2026-11-14 17:13:53 -0500` — **four minutes after the SBOM was written**. The release was
built from a worktree whose `HEAD` was `bb762c6` and whose package held the code that became
`101df7c`; the SBOM names neither the commit that holds the shipped code nor any marker that
the tree was dirty. `bb762c6` is a real ancestor of `101df7c`, but a user who checks out the
commit the document names gets different code.

(What the artifact does *not* show is the second claim biting: the recorded digest happens to
be the shipped one because no edit landed between `:68` and `:111` that day. That equality is
timing, not a guarantee — the test above shows the window is real.)

## Claim by claim

- **Dirty tree, bare `HEAD`** — confirmed, in code and in the shipped artifact. No script
  checks `git status`; `gatekeeper.md:59` promises "the git commit it was built from"; the
  0.3.0 SBOM names `bb762c6` for code that is `101df7c`.
- **Digest from the repository, after the copy** — confirmed. `:111` runs the repo script
  with `${PYTHON:-/usr/bin/python3}`; `source_sha256()` hashes `REPO_ROOT/ohyesmlx/*.py` at
  that moment, not the copy at `:68`. The failing second test shows an edit committed between
  the two is hashed and did not ship.
- **Top-level `*.py` only** — confirmed. `measure.py:438` globs `*.py` in one directory. The
  bundle ships `ohyesmlx/catalog.json`, `ohyesmlx/engines-tested.json`, `ohyesmlx/longtext.md`,
  `ohyesmlx/constraints/mlxlm-0.31.3.txt` and `ohyesmlx/constraints/optiq-0.5.13.txt`; none
  is in the digest, and the third test shows a catalog change moves no recorded digest.
  Nuance: the constraint files' pins and hashes are re-read into `engine_dependencies`, so
  their *contents* are recorded elsewhere in the document; the three data files are recorded
  nowhere.
