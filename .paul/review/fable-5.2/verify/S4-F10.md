# S4-F10 — An exception on the install failure path skips rollback

**Claim, one line:** `engines.install`'s failure branches call `send("error", …)` *before*
`_rollback(...)` (`engines.py:1270-1280`, `:1232-1237`), and `send` (`:1199-1213`) runs an
unguarded `_append_install_log` (`open(log_path, "a")`, `:1155`) and then the caller's `emit`,
so either one raising (an ENOSPC append, a throwing emitter) skips the rollback and leaves the
half venv the failed step created.

**Test:** `tests/test_fable_s4_f10.py` — both tests **fail on the current tree**
(`review/fable-verify`, base `714e8f6`):

  own test idea (`emit` raises on type `error`).

## The code path, with line numbers

1. `run_steps` splits `exit_code != 0` into `send("error", …)` (`:1271-1277`), `_rollback(created,
   engines_dir, send)` (`:1278`), `send("done", …)` (`:1279`) — three sequential statements, no
   `try`/`finally`.
2. `cancelled(created)` is the same shape: `send("error", …)` (`:1234`), `_rollback(...)`
   (`:1235`), `send("done", …)` (`:1236`).
3. `send` runs `_append_install_log(...)` (`:1203-1211`) **before** `emit(event)` (`:1212`).
4. `_append_install_log` (`:1141-1156`) ends in `with open(log_path, "a", …)` at `:1155` with no
   `try` — an `ENOSPC` propagates out of `send`.
5. `run` (`:1266`) is called unguarded too: a `Popen` failure inside `_real_run` (`:988`) also
   leaves `run_steps` without reaching `:1270`, and with no `error`/`done`.
6. The venv the failed install created is already in `created` (`:1268-1269`), so the state the
   finding calls F2 — a half venv, and possibly a written console script — is on disk with
   nothing that will remove it.

## What I did not verify

No real pip run, venv, subprocess or engine. The ENOSPC is simulated by raising `OSError(28)`
from the log handle's `write` for the `error` line only; I did not fill a filesystem. I did not
test a `Popen` failure inside `_real_run` as a separate case — it is the same unguarded
`send`-before-`_rollback` ordering and adds nothing the two tests do not already pin. I did not
check whether the app's emitter (the other `emit` implementation) can raise; the finding's
claim needs only that one can.
