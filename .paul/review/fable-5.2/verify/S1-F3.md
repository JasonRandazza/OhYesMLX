# S1-F3 — A network error mid-body escapes `_fetch_file`: no retry, and the partial is never ledgered

**Claim, one line:** a `TimeoutError`/`ConnectionResetError`/`ssl.SSLError` raised by
`response.read()` mid-body is not caught anywhere in `_fetch_file`, so it leaves `download`
without the four-attempt retry, without `fetch_file`'s residue bookkeeping, and reaches the
server's catch-all as `internal`; the leftover `.incomplete` is never named by the ledger, so
`evict` cannot remove it.

Where the finding lives: `S1-findings.md:30-37`. `dossier-S1.md:119` carries only the file map
for `_fetch_file`/`fetch_file` (`:906-1122`, `:1124-1135`); there is no separate per-finding
dossier entry for F3.

The test drives only the module's injected seams: a `Transport` whose `CutResponse.read`
delivers 4 bytes of a 100-byte body and then raises `TimeoutError` on every response
(Range requests get a matching 206), a literal free-space number, recording `sleep`/`clock`,
and a `tmp_path` cache/ledger/lock/log. It asserts the fixed behaviour — `download(...) is
False`, more than one `open_url` call, at least one backoff, an error code in
`{"http_error", "size_mismatch"}`, the lock released, and (if a `.incomplete` survives) it is
named in `created_blobs`. The exception escapes at the `response.read` frame, exactly as the
finding states; none of the assertions after the call are reached.

## The code path, with line numbers

1. **Only `open_url` has an `except OSError`.** `fetch.py:936-954` wraps the
   `open_url(planned_file.url, headers)` call; `:944` is the sole `except OSError` in the
   function. The body read at `:1070` (`chunk = response.read(CHUNK_SIZE)`) sits inside
   `try:` opened at `:955`, which has only `finally: _close(response)` at `:1121-1122` — no
   `except`. `TimeoutError`, `ConnectionResetError` and `ssl.SSLError` are all `OSError`
   subclasses; `http.client.HTTPException` is not an `OSError` and is caught nowhere either.
2. **The retry budget is bypassed.** The 4-attempt loop (`MAX_ATTEMPTS = 4`, `fetch.py:78`)
   retries only through the code below the read loop: short transfer at `:1110-1120`,
   `429`/`5xx` at `:1006-1016`, connection refusal at `:944-954`. A raise from `:1070` jumps
   straight to the `finally`, then out of `_fetch_file`.
3. **`fetch_file`'s residue bookkeeping is unreachable on a raise.** `fetch.py:1124-1135`:
   `if _fetch_file(planned_file): return True` at `:1130`; the `.incomplete` append at
   `:1132-1134` runs only when `_fetch_file` *returns* False. A raise skips it.
4. **`download`'s `finally` cannot recover it.** `fetch.py:710-718` records only
   `created["blobs"]`/`created["links"]`/`created["dirs"]`. The residue is written directly by
   the chunk loop (`:1066-1076`) and never entered in `created`, so `_record` writes a ledger
   entry whose `created_blobs` is empty (or skips the write entirely when nothing else was
   created).
5. **The server sees an unexpected error.** `server.py:754-758`:
   `except Exception as error: job.append(_event("error", ..., {"code": "internal"}))`. The
   user-visible failure is `internal`, not a fetch refusal such as `http_error`/`size_mismatch`,
   and the job's `ok` is `False` with no record of what was downloaded.
6. **`evict` cannot remove what the ledger does not name.** `fetch.py:1261-1265` removes a
   residue only for a path in `created_blobs` (`residue = path + ".incomplete"`); the
   `created_dirs` rmdir at `:1280-1288` fails on the non-empty `blobs/` directory. If an
   earlier run had already created the directories, `created` is empty, `_record` never runs,
   and `evict` answers `unknown_repo` at `:1228-1232` instead.
