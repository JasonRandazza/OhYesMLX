# S5-F13 — verification

**Claim, restated in one line:** the ledger's `stop_command` field is data on disk that is handed
to `_shutdown` and executed via `_run`, so a same-user process that writes
`results/running-engines/<owner>.json` chooses an argv this harness runs — unchecked by
`stop_own_engines`, and checked-only-against-the-entry's-own-fields by `_stop_orphan`.

## What the code does (line numbers verified in this worktree)

Record and read:

- `ohyesmlx/runtimes.py:1747-1783` `_record_running_engine` — writes `"stop_command":
  list(stop_command)` into the entry at `:1780`. It is stored as a plain list of strings with no
  signature, no schema, no per-entry provenance.
- `ohyesmlx/runtimes.py:1693-1702` `_ledger_entries` — reads the file as JSON and returns every
  `dict` in `entries` (`:1702`). Nothing about the contents is validated beyond "is a dict".
- `ohyesmlx/runtimes.py:1813-1824` `_entry_stop_command` — the one parse: `isinstance(list)` and
  every part `isinstance(str)` (`:1820-1822`), else `()`. That is the whole filter. Any list of
  strings passes.

Executed:

- `ohyesmlx/runtimes.py:1908-1937` `stop_own_engines` — `_shutdown(pid, port,
  _entry_stop_command(entry))` at `:1930`. The loop at `:1924` has already checked only that `pid`
  and `port` are `int` (`:1925-1928`); there is **no** `_process_identity` call, **no** port
  listener check, and no comparison of anything before the command is run.
- `ohyesmlx/runtimes.py:1827-1864` `_stop_orphan` — the identity checks the finding credits it
  with are real: `:1850-1852` compares the launcher's live identity to the recorded one, `:1854-1857`
  compares each listener's, `:1859-1863` the no-listener case. But every one of those values comes
  from the *same entry dict* (`_recorded_identity`, `:1800-1810`). A writer who supplies both
  halves satisfies all of them, then `:1864` runs `_shutdown(pid, port, command)`.
- `ohyesmlx/runtimes.py:1656-1684` `_shutdown` — `_run(stop_command, STOP_TIMEOUT_S)` at
  `:1674-1675`.
- `ohyesmlx/runtimes.py:569-585` `_run` — `subprocess.run(_resolve_program(command, env), ...)`
  at `:573-581`. A real exec of the recorded argv.

The finding's correction to the dossier's Q7 is accurate on both halves: in `_stop_orphan` the
identity checks do precede the command (`:1850-1863` before `:1864`), and only `stop_own_engines`
runs it with no check at all.

Also worth naming because it bounds the exposure precisely: `stop_orphaned_engines` (`:1867-1905`)
skips any ledger file whose owner pid is alive (`:1890-1891`), so the orphan path needs a *dead*
owner. `stop_own_engines` needs the file to be named for *this* pid — which any same-user process
can read and write.

## Reproduced

New file `tests/test_fable_s5_f13.py`, two tests, one per entry point. The ledger is written to a
scratch root, the recorded command is `/usr/bin/touch <scratch>/marker`, and the module's own
seams (`_process_alive`, `_port_is_free`, `_listener_pids`, `_process_identity`, `_engine_env`) are
the fakes. The only thing actually executed is the test's own `touch`.

On unmodified code:

```
E       AssertionError: the ledger's stop_command was executed verbatim: a file nothing vouches
        for chose the argv this process ran
        assert not True
```

```
E       AssertionError: the orphan entry's stop_command was executed: the entry's own fields
        satisfied every identity check the argv was never compared against
        assert not True
```

Both marker files existed after the calls, which is the finding's exact test idea, and both tests
also assert their precondition — `stopped == 1` in the first, and a matching identity supply in the
second — so a green result is not "nothing happened".

## Red-check (performed)

Applied the finding's fix direction in its smallest form: `_entry_stop_command` returns `()` for
any entry, i.e. the ledger's field is no longer a source of a command. Result: **2 passed**.
Reverted with `git checkout -- ohyesmlx/runtimes.py` (`git status --short ohyesmlx/` empty):
**2 failed**, same assertions.

## Severity

Low, as the finding says, and its reason is the right one: this is a same-user primitive, and a
same-user process that can write `results/running-engines/` can already do worse things directly.
The finding's "confidence 60 that it is worth acting on" is honest. Two notes that argue *for*
keeping it at Low rather than raising it:

- The value the design actually needs is recoverable without trusting the file: `RUNTIMES` is keyed
  by port, and `Runtime.stop_command()` (`:2015-2016`) is a method the module already owns. The
  finding's fix direction — derive it from the port, delete the field — removes the primitive
  rather than hardening it, and a deletion cannot drift from a definition.
- It is not exploitable across users, and it does not silently corrupt a measurement; that is the
  line that separates this from the Medium-and-above findings.

One thing I would add rather than change: the finding's stated blast radius ("an exec primitive the
design does not need") understates the *specific* one. `stop_own_engines` is the app's "Stop now"
daemon thread (`server.py:803-808`), so in the shipped app this runs on a path a user triggers, in
the app's own process, with the app's privileges. Still Low — same user either way — but the
"runs with no identity check at all" half is the half worth fixing first.

## What is not verified

- No real ledger was tampered with and no engine was stopped. The pids are integers, not processes.
- The "attacker who started the listener controls the identity it reports" half of `_stop_orphan`
  is shown by construction (the entry supplies both sides of the comparison), not by a live
  process.
- `stop_orphaned_engines`' dead-owner gate (`:1890-1891`) was satisfied by using a pid that is not
  alive; the real interaction between a live owner and a tampered file was not exercised.
- Whether any caller in the shipped app writes a ledger entry from an untrusted source was not
  audited beyond `_record_running_engine`, which writes what `Runtime.stop_command()` returns.

## Verdict
