## The claim, in one line

`build_app.sh` reads `ohyesmlx.__version__` with the *cache* interpreter and no `-B`, which
writes timestamp pycs into the tree `:55` copies into the bundle; `compileall` at `:76` omits
`-f`, so it leaves those pycs alone while the comment at `:71-75` claims the whole tree is
unchecked-hash — so 51 stdlib modules ship with bytecode that *is* revalidated against source
mtimes, and one child interpreter rewrites them inside the signed bundle.

## The consequence, reproduced end to end

Two copies of the real bundled interpreter at `Contents/Resources/python`. In one, source
mtimes were moved +2 s (a transfer that does not reproduce mtimes); the other was
`cp -Rp`, mtimes intact. Both then ran the exact child command the finding names.

```
CONTROL (cp -Rp, mtimes intact): pycs changed = 0  new pycs = 0  timestamp-flagged = 51
SHIFTED (mtimes moved +2 s):    existing pycs changed: 51 of which timestamp->rewritten: 0
                                (rewritten in place: 51 pycs whose bytes differ)
```

The flags stay `0` because the rewrite produces another timestamp pyc — the *content* and
mtime change, which is what a seal measures. Byte-diff against the shipped bundle: **51 pycs
changed**, exactly the 51.

The seal itself, on a `ditto` copy of the real app:

```
$ codesign --verify --deep --strict <copy>          → PASS at copy time
… shift every source mtime +2 s (content untouched) …
$ codesign --verify --deep --strict <copy>          → PASS (mtimes alone are not sealed)
$ "$PY/bin/python3" -I -m venv engine-venv          → completes, 1.75 s
$ codesign --verify --deep --strict <copy>
<copy>: a sealed resource is missing or invalid
$ echo $?
1
```

The venv shares the bundle's stdlib rather than copying it —
`base_prefix` is the bundle tree and `json.__file__` resolves under it — which is why a venv
created for mlx-lm or OptiQ writes into the stdlib it is standing on. This is the same
failure shape 05-06 finding #1 recorded ("before that fix, child interpreters wrote stdlib
bytecode into the bundle"), arriving through the 51 pycs the fix skipped.

## The confidence-50 sub-claim: REFUTED as a normal path

The reviewer wrote: "50 that a normal Archive Utility unzip makes them stale; that needs one
unzip-and-stat." Two of three tests say no.

- `ditto -x -k` on the shipped release zip restores both mtimes to the second:
  `__init__.py` → `Dec 31 19:00:00 2023`, its pyc → `Nov 14 16:35:08 2026`.
- `/usr/bin/unzip` likewise restores both exactly.
- The zip carries full Unix mtimes in the InfoZIP `0x5855` extra field
  (`mtime=1704067200` on the source, `1794692108` on the pyc), so a correct extractor has
  what it needs.
- Archive Utility's Finder path could not be exercised: the binary at
  `/System/Library/CoreServices/Applications/Archive Utility.app/Contents/MacOS/Archive Utility`
  accepts `-kernel` but produced no tree in a non-GUI session. **So the Finder double-click
  path remains untested.** It is the one realistic path that might still trigger this, and it
  is the reason the finding is worth fixing even though two native extractors are clean.
- `cp -R` *without* `-p` does trigger it, and I demonstrated that accidentally and then
  deliberately: it resets source mtimes, and the child venv then rewrote all 51.

So "any transfer that does not reproduce mtimes" is correct in mechanism but is not the
ordinary macOS path. A `cp -R` from a Terminal, an `rsync` without `-t`, or a sync/backup
restore does it; `ditto -x -k` and `unzip` do not.

- **pip and the engine servers** as the rewriting child. I ran the interpreter `engines.py:797`
  spawns and it rewrote the pycs; pip and an engine server run the same stdlib closure, but I
  did not run either.
- **The read-only-volume case.** On a read-only mount the rewrite cannot land, so the failure
  there is silent in-memory recompilation rather than a corrupted seal. I did not test it, and
  it does not weaken the finding: the defect is that the pycs are revalidatable at all.
- **Whether `-f` costs a rebuild on future interpreter upgrades.** Adding `-f` forces a
  recompile of the entire stdlib on every build; I did not measure that cost.

## Verdict

The finding is correct in every load-bearing particular: the missing `-B`, the missing `-f`,
the `ditto` copy that carries the pycs, the 51-file consequence, the falsified comment, the
insufficient `:78` assertion, and the child-venv rewrite that breaks the seal. Its one
overstated sub-claim is that an ordinary unzip makes the pycs stale — two native macOS
unarchivers restore mtimes exactly. The reviewer's confidence arithmetic was honest and its
diagnosis was right; I settled confidence 80 at 100 and confidence 50 at "not by `ditto` or
`unzip`, Archive Utility untested."
