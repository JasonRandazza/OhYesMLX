# S6-F11 — verification

**Claim, restated in one line:** the P5-4 gate calls `urlopen` before it asserts
`CERT_REQUIRED`/`check_hostname`, and any `URLError` (DNS down, an HF incident, an offline build
machine) takes the same `fail P5-4 "the HTTPS GET failed"` branch a certificate regression would,
so a transient network failure turns the release gate red and the two causes cannot be told apart.

## What the code does (line numbers verified in this worktree)

`scripts/check_bundle.sh:105-133`, the P5-4 block:

- `:105` — `echo "==> P5-4: an HTTPS GET to huggingface.co on a clean environment"`.
- `:108` — the interpreter runs under `env -i` with `HOME="$WORK/p54-home"` and a fixed PATH.
- `:114-119` — `context = ssl.create_default_context()`; a `facts` dict is built from
  `context.verify_mode.name`, `context.check_hostname`, `ssl.OPENSSL_VERSION`.
- `:120-122` — `with urllib.request.urlopen("https://huggingface.co/…", timeout=60) as response:`.
  **This call can raise `URLError` for a dead network.**
- `:124` — `print(json.dumps(facts, indent=2))` — reached only after the GET returns.
- `:125-126` — `assert context.verify_mode == ssl.CERT_REQUIRED` and
  `assert context.check_hostname`. These are the two assertions that are the actual property,
  and they sit **after** the network call. A raised `URLError` skips them.
- `:127` — `assert facts["status"] == 200`.
- `:128-133` — heredoc ends; `pass P5-4 "… answered 200 with verification on"` on success, else
  `fail P5-4 "the HTTPS GET failed (see above)"` — one constant message for every cause.

The shell side has no way to branch on the cause:

```
$ grep -c "URLError\|SSLCertVerificationError\|get_default_verify_paths" scripts/check_bundle.sh
0
```

`ssl.get_default_verify_paths()` is never consulted, and the CA file the status table credits
(``macOS's `/etc/ssl/cert.pem` `` — `docs/threat-model.md:601`) is never checked for existence
before the call. The block therefore *does* depend on the endpoint being reachable, which the
property P5-4 states (`docs/threat-model.md:580`: "An HTTPS fetch to `huggingface.co` succeeds on
a clean account, and certificate verification is never disabled") does not require in order to
be falsified by a certificate error.

`fail` is `scripts/check_bundle.sh:35`, and the script exits non-zero at `:260-262` whenever
`FAILURES` is non-zero, so a network outage fails the release gate.

The dossier's own **Q8** (`dossier-S6.md`, "P5-4 needs live internet, so a network hiccup reads
as a packaging failure") states the same behaviour, which means this finding and the dossier do
not conflict — the finding is the reviewer promoting Q8 to a defect with a fix direction.

## Reproduced

New file `tests/test_fable_s6_f11.py`, three tests:

```
$ /Users/jrazz/.local/share/ohyesmlx/test-venv/bin/python -m pytest -q tests/test_fable_s6_f11.py
3 passed
```

1. `test_the_certificate_assertions_run_only_after_the_network_call` — extracts the P5-4
   heredoc from the script and asserts both `CERT_REQUIRED`/`check_hostname` assertions appear
   after `urllib.request.urlopen(`. Proves the ordering; a `URLError` at `:120-122` skips them.
2. `test_one_failure_line_covers_both_a_dead_network_and_a_bad_certificate` — asserts the block's
   failure line is `fail P5-4 "the HTTPS GET failed (see above)"`, that no
   `SSLCertVerificationError` branch exists, and that neither `URLError` nor
   `get_default_verify_paths` occurs anywhere in the script.
3. `test_a_urlerror_from_a_dead_endpoint_prints_no_certificate_facts` — runs the block's own
   Python source against `https://127.0.0.1:1/` (a closed local port; no external network) and
   observes `rc=1`, empty stdout, and
   `urllib.error.URLError: <urlopen error [Errno 61] Connection refused>` on stderr: the
   `facts` dict, including `verify_mode` and `check_hostname`, is never printed because `:124`
   is behind the call. A dead network and a certificate rejection therefore reach the shell
   identically.

Red-check: with the module's `TEXT` patched in memory so the `certificate verification is not
required` assertion precedes the `urlopen` call, test 1 fails at the assertion index comparison;
with a `SSLCertVerificationError` branch added to the block, test 2 fails. Restored, all three
pass. No repository file was edited.

## What is not verified

- The real TLS-failure leg was not observed: nothing here can make huggingface.co present a
  certificate this machine rejects without editing the script, and no network call to the real
  endpoint was made. The claim that a certificate failure produces a `URLError` whose `reason`
  is `ssl.SSLCertVerificationError` is standard `urllib` behaviour, not an observation.
- The suggestion to check `ssl.get_default_verify_paths()` resolves to an existing CA file is a
  fix direction, not something I verified would succeed under `env -i` on a clean account.
- Whether the "clean account" (P5-5, still open per the status table) has the same trust store
  was not examined; that is a different finding.
