# S4-F8 — Stage B runs the winner engine on every sibling, whether or not the sibling's row lists that engine

**Claim, one line:** stage A takes its engines from the chosen row's `engines` list
(`quickbench.py:292`), but the stage-B plan is every `catalog.siblings` row with no engine test
(`:294-302`) and the run hands the winner to each of them (`:895`), so a sibling whose row does not
list the winner would still be downloaded and measured on it.

The test builds a two-row base through the module's own `models` parameter: the chosen row lists
`mlxlm` only, its sibling lists `optiq` only, both engines are installed, and only the chosen repo

stage-B row is `SKIPPED` with a reason naming the engine.

## The code path, with line numbers

1. **Stage A is filtered by the chosen row.** `quickbench.py:289-293` keeps an installed engine
   only `if status.installed and status.name in model.engines` (`:292`).
2. **Stage B is not filtered by anything.** `quickbench.py:294-302` builds `PlannedSibling` for
   every `catalog.siblings(model, models)` row. `PlannedSibling` (`:114-121`) carries only
   `repo`, `format`, `size_bytes`, `downloaded` — there is no `engines` field, so the plan cannot
   show a per-sibling conditional even if the run learned one.
3. **The estimate counts every sibling.** `quickbench.py:313` is
   `estimate_seconds(len(stage_a) + len(stage_b), missing_bytes)`, and `missing_bytes` (`:303-305`)
   sums every undownloaded stage-B row.
4. **The run dates the download.** `quickbench.py:848` looks the sibling row up from
   `catalog.siblings`, and `:862-890` downloads it when `sibling_plan.downloaded` is false —
   before any question of whether the winner can serve it.
5. **The run does not gate the cell.** `quickbench.py:895-901` calls
   `measured(top["engine"], sibling.format, …)` with no `top["engine"] in sibling.engines` test.
6. **Nothing else on the path could supply the gate.** `_skip_reason` (`quickbench.py:431-447`)
   answers only Osaurus consent and a busy port; `grep -n engines ohyesmlx/quickbench.py` shows the
   only engine-list read in the module is line 292.

## Reachability: the trigger does not exist in the shipped catalog

The finding's confidence (70) said it rises "by finding one `base` in `catalog.json` whose rows
carry different `engines` lists". There is none, and the catalog forbids one:

- `ohyesmlx/catalog.json` has 12 rows over 10 bases. The only multi-row bases are
  `Qwen3.5-0.8B` and `Qwen3.5-2B`, and both of their rows list all five engines
  (`mlxlm, osaurus, omlx, optiq, vmlx`). Bases with more than one distinct engines list: **0**.
- `tests/test_catalog.py:428-433` asserts `sorted(model.engines) == sorted(ENGINES)` — all five —
  for every shipped row, so a divergent row would fail the suite before it could reach a run.
- Every production path feeds `catalog.load()`: the CLI at `cli.py:1015-1020`, the app's plan at
  `server.py:629` with `load_catalog=catalog.load` (`server.py:1011`), and the app's run at
  `server.py:743-750`, which passes no `models` and so defaults to `catalog.load()` in
  `quickbench.run` (`:551`). The injected `models` argument is the test seam, not a user route.

So the code shape the finding describes is real and provable, but reaching the failure scenario
requires editing `catalog.json` and deleting the test that pins it. The finding's own confidence
riser did not fire.

## What I did not verify

No engine, server, model or app was started, per the order. Whether a real engine would
*half-load* an unlisted format and clear the coherence gate is therefore unknown; the run-path
evidence is that nothing stops the attempt and nothing labels it unsupported.
