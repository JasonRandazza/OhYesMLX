# S4-F13 — The download lock can be stolen between its creation and its pid being written

**Claim, one line:** `fetch._acquire_lock` creates the lock with `O_CREAT|O_EXCL` at
`fetch.py:373` and writes this process's pid only at `:387-388`; a second process arriving in
that window gets `FileExistsError`, folds the empty read into `pid = None` at `:375-379`, skips
the liveness check at `:380` because `pid is None`, removes the **live** owner's lock at `:383`
and creates its own.

**Test:** `tests/test_fable_s4_f13.py::test_an_empty_lock_naming_no_pid_is_held_not_reclaimed`
— **fails on the current tree** (`review/fable-verify`, base `714e8f6`).

```

E       AssertionError: the empty lock at the create/write window was reclaimed and re-created:
E       a second process now holds the lock a live first process is about to write its pid to,
E       so two downloads run at once

FAILED tests/test_fable_s4_f13.py::test_an_empty_lock_naming_no_pid_is_held_not_reclaimed
```

The test is the finding's own idea: an empty `download.lock` exists, so `_acquire_lock` must
answer False. It does not — it removes the file and returns True.

## The code path, with line numbers

```
    for _ in range(2):
        try:
            descriptor = os.open(path, os.O_CREAT | os.O_EXCL | os.O_WRONLY, 0o644)   # :373
        except FileExistsError:
            try:
                with open(path, encoding="utf-8") as handle:
                    pid = int(handle.read().strip())                                  # :377
            except (OSError, ValueError):
                pid = None                                                            # :379
            if pid is not None and _pid_alive(pid):                                   # :380
                return False
            try:
                os.remove(path)                                                       # :383
            except OSError:
                return False
            continue                                                                  # :386
        with os.fdopen(descriptor, "w", encoding="utf-8") as handle:
            handle.write(str(os.getpid()))                                            # :388
        return True
```

Between `:373` (the file exists, empty) and `:388` (the owner's pid is in it) the lock exists
with no owner recorded. Every process that arrives there follows the `pid = None` branch: no
liveness evidence, so remove-and-retry. The first holder keeps its open descriptor and goes on
to write its pid into an unlinked inode, so even its own `_release_lock` (`:393-405`, which
re-reads by path and returns when the content is not its pid) will not clean up the lock the
thief now owns.

Two writers then share one `.incomplete` and do two read-modify-writes of `fetched.json`: the
per-repo residue and the ledger entry can interleave.

## Why this is not the accepted race

The dossier records one `_acquire_lock` race as accepted — `dossier-S1.md:269` and `:273`:
"`_acquire_lock` stale-reclaim check-then-remove race — accepted (crash + two-process race at one
instant)", and `dossier-S4.md:324`: "two processes that both find a **dead** owner can both
proceed". That accepted case requires the previous owner to be *dead*. The window above has a
live owner whose pid is merely not written yet; the stale-reclaim rule is being applied to a
lock it was never meant for. The finding is distinct from the accepted item, and the code has
no age or content test that would distinguish the two.

## Reachability

The window is microseconds wide, so it needs two starts almost simultaneously — a CLI download
beside the app's, which is exactly the cross-process case the lock exists for (`fetch.py:95-98`:
"one download at a time, across repos and processes"). It is not a same-process hazard: a
single process serialises its own calls. Two app instances cannot both spawn (P5-7: `flock` on
`app.lock`, `dossier-S1.md:219`), so the second process is a `ohyesmlx download` run in a
terminal beside the app.

## Red-check

With an empty/unparseable lock younger than one second treated as held (the finding's second
fix direction), the test passes and the whole fetch suite — including the existing
`test_a_stale_lock_from_a_dead_pid_is_reclaimed` and `test_a_live_lock_holder_makes_the_download_busy`
— is unaffected:

```
$ ... -m pytest -q tests/test_fable_s4_f13.py tests/test_fetch.py
109 passed in 0.21s
```

Reverted, it fails again. The source tree is unmodified (`git diff ohyesmlx/` empty).

## What I did not verify

I did not run two real processes racing; that needs two `download` invocations started at once
and a network transfer, both outside this order. The test stages the window's observable state
(a lock file with no pid) rather than the timing. I did not test the finding's first fix
direction (`os.link` of a temp file into place) — only the second (age-based hold), which is
what the test pins. I did not check whether an empty lock left by a **crashed** previous
process is now held forever; with the age test it is held for one second and then reclaimed,
which is the same behaviour the suite's stale-lock test still shows.

## Verdict

VERDICT: CONFIRMED (test: tests/test_fable_s4_f13.py::test_an_empty_lock_naming_no_pid_is_held_not_reclaimed)

SEVERITY-CHECK: agree — Low. The consequence (two concurrent downloads, interleaved ledger
writes, a shared `.incomplete`) is real data-integrity damage, but reaching it needs two
processes started within microseconds of each other, against a window only a few instructions
wide. Probability is what keeps it Low; the impact half is worth the small fix.
