# S3-F5 — The app treats a job as over at `error`, but the backend holds the slot and runs rollback until `done`

**Claim (one line):** `AppModel.apply` flips the job out of `isActive` at `error`, while the
backend only frees its one job slot at `done`; during install rollback the app therefore offers
start controls that earn `409 busy` and tells `quit` no job is running, so the no-job signal
escalation (10 s grace, SIGTERM, 5 s, SIGKILL) is applied to a backend inside `_rollback`.

**Verdict:** reproduced at the model level, deterministically. With a stub install that sends
`error` and holds the stream open, `canStartJob` is `true`, `oneSlotReason` is `nil`, and
`requestQuit` passes `jobRunning: false` — for exactly the interval in which the backend has not
yet sent `done` and still holds the slot.

## Code path

The app:

- `app/Sources/OhYesMLXKit/AppModel.swift:689-699` — the `.error` case sets
  `status.state = code == "cancelled" ? .cancelled : .failed` (`:691`), assigns `job = status`
  (`:695`) and returns. Both states are outside `isActive` (`:39-42`).
- `AppModel.swift:674-687` — the `.done` case flips the state only `if status.state.isActive`
  (`:676`), so for an error-then-done job `done` leaves the already-failed state alone and only
  clears `inflightJob` (`:684`).
- `AppModel.swift:650-660` — `start` keeps consuming the stream until `done` (`:653`), so the
  client is still attached and merely disagrees about whether the job is running.
- `AppModel.swift:263-271` — `oneSlotReason` is `job.state.isActive`-derived and `canStartJob`
  is its inverse; `:562-577` — `requestQuit` computes `job?.state.isActive == true` at `:569`.
- `AppModel.swift:611-615` — `start` clears `summary`, `summaryData` and `liveCells` for a
  quickbench *before* `startJob` at `:627`, so a start that the backend then refuses has already
  discarded the previous run's summary.
- Buttons follow `canStartJob`: `EnginesView.swift:170`, `:194`; `ModelsView.swift:224`, `:240`;
  `BenchmarkView.swift:249`.

The backend:

- `ohyesmlx/engines.py:1232-1237` — a cancel sends `error {code: cancelled}`, then
  `_rollback(created, engines_dir, send)`, then `done`; `:1270-1280` — a failed step sends `error
  {code: step_failed}`, then the same rollback, then `done`.
- `ohyesmlx/engines.py:1098-1123` — `_rollback` unlinks / `shutil.rmtree`s each created path
  (`:1115-1122`): real filesystem work, seconds on a venv, between the two events.
- `ohyesmlx/server.py:176-202` — `_Job.append` calls `self._registry.finished(self)` only when the
  stored event is `done` (`:182-184`, `:198-202`); `_Jobs.finished` (`:256-259`) is what clears
  `self.running`. So the slot is held from `error` until `done`.
- `ohyesmlx/server.py:681-685` — a `POST /jobs` in that window is answered `409 busy`.
- `ohyesmlx/cli.py:1156-1169` — the backend installs a SIGTERM handler (`_stop`, `:1173-1181`)
  and, on the way out, `cancel_and_wait(120 s)`; `:1184-1202` — stdin EOF stops the serve loop
  the same way.

Downstream of `jobRunning: false`, `app/Sources/OhYesMLXKit/BackendLauncher.swift:380-398`
closes stdin, waits `timing.grace` (10 s), calls `process.terminate()`, waits
`timing.terminateGrace` (5 s), then `process.kill()`; `QuitTiming.standard` is
`grace: 10, terminateGrace: 5, jobBound: 150` (`:28`). With `jobRunning: true` the same function
waits `jobBound` and signals nothing.

## Which kinds are actually exposed

- **install — yes.** `_rollback` does `shutil.rmtree` between `error` and `done`; both the cancel
  path (`engines.py:1234-1236`) and the step-failure path (`:1271-1279`) go through it.
- **download / evict — a gap of two adjacent sends:** `fetch.py:766-773` (cancel) and
  `fetch.py:441-442` (refusal) emit `error` then `done` with nothing in between.
- **quickbench — likewise adjacent:** `quickbench.py:1004-1011`.

So the long window is install's, as the finding said.

## The two consequences

**(a) Quit in the gap** — reproduced at the model level (`quitCalls == [false]`), read onward
from source, not run: the launcher then takes the no-job branch. One correction to the finding's
phrasing: the backend catches SIGTERM (`cli.py:1173-1181`) and its exit path waits up to
`JOB_SHUTDOWN_WAIT_S` = 120 s for the job's `done` (`cli.py:1168`, `server.py:261-303`), so the
SIGTERM at 10 s does not itself kill anything. The destructive step is the SIGKILL at 15 s,
which lands only if the rollback outlives 15 s. The contract violation is unconditional: the app
is permitted by `docs/interfaces/v5-app.md:58-61` to escalate precisely because it believes no
job runs.

**(b) A start in the gap** — read from source: every control gated on `canStartJob` is enabled
during rollback, the POST is answered `409 busy` (`server.py:684`), and for a quickbench start
the previous summary has already been cleared (`AppModel.swift:611-615` precedes `:627`).
`StubBackend` models no slot, so the 409 half is not exercised by the test; it is the backend's
one-slot code cited above.

VERDICT: CONFIRMED (test: app/Tests/OhYesMLXKitTests/FableS3F5Tests.swift::testTheJobIsStillRunningDuringTheRollbackThatFollowsAnError)
SEVERITY-CHECK: agree — Medium. The state disagreement is unconditional and violates two pinned rules at once (one slot, no signalling a running job), and it is reachable through ordinary actions: cancel an install, then press Install again — or Start Benchmark, which clears the summary before earning the 409. It is not High because the backend's own signal path is graceful: SIGTERM re-enters the 120 s shutdown wait, so only a rollback longer than 15 s reaches SIGKILL, and no measurement or on-disk record is corrupted; and it is not Low because the window is a real filesystem deletion, not a single round trip, and the summary wipe is a silent loss of what the user was looking at.
