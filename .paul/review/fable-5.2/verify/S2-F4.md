# S2-F4 — `peak_mb` is published from a sampler that stopped early

**Claim (one line):** when `footprint` returns nothing three times running, `Sampler._loop`
sets `error` and returns for good, `stop()` still returns the maximum of the samples taken
before that, and `report._row` publishes it as the cell's `peak_mb` on a PASS row while
nothing between `sampler.stop()` and the row ever reads `memory["error"]`.

**Verdict:** reproduced. The chain holds link for link, and the last link is the one that
fails: a memory dict carrying `{"peak_mb": 4096.0, "error": "footprint read nothing 3 times
running for pid 4242; the process has most likely exited"}` is summarized into a PASS row
whose `peak_mb` is `4096.0`, with no note and no marker anywhere on the row.

## Code path, line by line

- `sample.py:264-278` — `_loop` increments `misses` on every `phys_footprint_mb` that
  returns `None`; at `CONSECUTIVE_MISSES_BEFORE_STOP` (3, `sample.py:34`) it sets
  `self.error` (`:270-273`) and `return`s at `:274`. The loop is gone for good; nothing
  restarts it while the pid is alive.
- `sample.py:282-288` — `stop()` sets the stop event and joins. Nothing here inspects
  `self.error` or `n_samples`, so a loop that already returned is indistinguishable from
  one stopped on request.
- `sample.py:290-291` — `peak_mb = max((s["mb"] for s in samples), default=None)` over
  whatever `samples` holds. Two samples then three misses gives a real number; zero samples
  gives `None`, which is the only case that reads as absent.
- `sample.py:292-302` — the result dict carries both `"peak_mb": peak_mb` and
  `"error": self.error` to the caller, side by side and equal in standing.
- `measure.py:878-880` — `_workload_visit` returns that dict and `_highest_peak` folds it
  onto `result.memory`.
- `measure.py:1216-1220` — `_highest_peak` compares `peak_mb` only. When the disowned
  visit holds the larger peak it is kept **with** its error (checked below), so the error is
  not dropped as the finding's Evidence suggests in that direction; the number reaches the
  row intact.
- `measure.py:1463` — `_record` writes `"memory": result.memory` whole, so the error survives
  in `results.jsonl` too.
- `report.py:865` — `"peak_mb": (result.memory or {}).get("peak_mb")`. This is the only read
  of `result.memory` in the module (`grep -n "memory" ohyesmlx/report.py` → lines 202, 299,
  337, 1368, which are prose; line 865 is the only code).
- `report.py:1343` — `_number(row.get("peak_mb"), 1)` renders it; `_number` prints `—` only
  for `None` (`report.py:2600-2601`).

**Nothing reads the error.** An AST pass over every `ohyesmlx/*.py` for a `"error"` subscript,
a `.get("error")`, or an `"error" in …` membership test found the only `"error"` keys are
`SAMPLER.result["error"]`, `transport.Observation.error` and `server`'s payload dicts. No
consumer of `CellResult.memory` asks for its `error`. The one other `peak_mb` reader is
`measure._highest_peak` (`:1216-1220`), which reads `peak_mb` alone.

### Satisfiability of the stated fix

`report._row` was wrapped in a scratch script to publish `peak_mb: None` when
`memory.get("error")` is set — the finding's own fix direction — and the failing test body was
re-run. It passes, and the two clean cases are unchanged: `{"peak_mb": 9150.0, "error": None}`
still publishes 9150.0 and `{}` still publishes `None`. `_why_none`
(`report.py:779-784`) already has a fallback wording for a `None` peak,
"the run recorded no peak_mb for this (cell, workload)", and `_number` already renders `—`.
So the test does not over-constrain the fix and the renderer needs no new field. No code was
changed to make the tests pass; this is a verify role.

## Two corrections to the finding's evidence

Both are refinements, not refutations.

1. **`_highest_peak` drops the error only in the harmless direction.** The finding says "the
   error can also be dropped when the other visit's peak is higher". Probed both ways:
   - disowned visit wins (`4096 + error` vs `9150 + None`) → `{"peak_mb": 9150.0, "error":
     "gave up"}` — error **kept**;
   - clean visit wins (`9150 + error` vs `4096 + None`) → `{"peak_mb": 9150.0, "error":
     None}` — error dropped, and correctly, because the peak published is the clean visit's
     own number.

   So `measure.py:880` is not a hole; it is the path by which the error *does* reach the row
   in the case that matters. `report.py:865` is where the chain breaks.
2. **The still-alive error publishes a bare peak too.** `stop()` sets
   `"sampling thread for pid … is still alive after join"` (`sample.py:286`), and a memory
   dict carrying that error and a peak summarizes to `peak_mb: 9150.0`, PASS, no note. The
   finding calls its scenario "distinct from the accepted thread-still-alive case", but the
   *publishing* behaviour is identical; the difference is only that the short window makes
   the number low rather than long. The fix direction as written (`error` set → no `peak_mb`)
   covers both, which is right.

## Severity: the consequence, not the mechanism

`peak_mb` is in `RANK_METRICS` (`report.py:177`, direction `"lower"`), `CARD_FIELDS`
(`:227`), and the sortable set behind `order_rows`. A format-axis ordering by `peak_mb` is
**permitted** — `CROSS_RUNTIME_UNCOMPARABLE` (`report.py:304-318`) blocks it only on the
runtime axis, and `test_a_cross_runtime_ranking_is_refused_and_a_format_one_is_not`
(`tests/test_report.py:1855-1908`) pins that the format axis still numbers 1 and 2 by it.

Demonstrated on the current code: two formats of one runtime, one carrying the disowned
peak, order as `['oq4__mlxlm', 'jang__mlxlm']` with peaks `4096.0` and `9150.0`. The format
whose sampler gave up wins the memory column, and the row says nothing about it. That is the
same class of published number the project refuses everywhere else — a figure that is not a
measurement of what the column claims.

Against Medium: the trigger is unobserved in the corpus. `docs/research/` and
`docs/runtimes/` were searched for a recorded `footprint` failure and none was found, and no
run on disk is known to carry a disowned peak. The finding's own failure scenario is a
clock timeout under decode load, which is plausible on this machine (the sampler shells out
to `/usr/bin/footprint` with a 10 s timeout, `sample.py:30`) but has not been watched
happening. When it does fire, though, the number is silently **low**, and a low peak is the
favourable outcome in a "lower is better" column — the direction that flatters the cell. The
record keeps the error, so the fault is recoverable after the fact; only the publish path is
blind.

## What I did not verify

- I did not check whether `footprint`'s 10 s timeout is ever hit in practice; that needs a
  real run and is the coordinator's to make.
- I did not attempt the fix, and did not run the fix-satisfiability wrapper as a test in the

- I did not test the `report.render_markdown` / `render_cards` output for a `None` peak from
  this path; `_why_none` and `_number` were read, and the `—` rendering is already covered by
  the existing empty-memory case.
