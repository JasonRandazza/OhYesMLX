# S4-F9 — A failed or refused sibling download leaves its partial on disk, unreported, and hides why it failed

**Claim, one line:** in stage B, a sibling `download` that returns False is branched away at
`quickbench.py:869-889` before `outstanding.add(sibling.repo)` at `:890`, so its ledgered
`.incomplete` is never evicted (the inner `finally` evicts only `if fetched`, `:914-915`), never
swept by the run's `finally` (which walks `outstanding` only, `:944`), and never recorded in
`not_evicted`; the run still ends `finished`, and because the sibling fetch's events go to
`_discard` (`:865`), a refusal's code never reaches the skipped cell's reason (`:862`).

**Test:** `tests/test_fable_s4_f9.py::test_a_failed_sibling_download_is_evicted_or_recorded`
— **fails on the current tree** (`review/fable-verify`, base `714e8f6`). A second test in the
same file, `::test_a_refused_sibling_download_keeps_the_refusals_code_in_the_cell_reason`,

The fake downloader does what a real failed transfer does: it writes the
`<blob>.incomplete`, adds it to `created_blobs` of the ledger at
`fetch.ledger_for(cache_dir)` (`fetch.py:1124-1135`, persisted by `download`'s `finally` at
`fetch.py:715-718` — the existing test `tests/test_fetch.py:1075-1076` asserts exactly this
residue-on-ledger behaviour), then emits the `error`/`done` pair `fetch._refuse` emits
(`fetch.py:439-443`) and returns False. `evict` removes that repo's partial, so a run that
evicted would leave no file behind. The 1 KiB partial stands in for the finding's 2.5 GB.

## What the failing run actually does

The same fixture, dumped instead of asserted on:

```

evicts: []
not_evicted: []

stage_b_cells: [('org/two-b-stock', 'PASS', None),
                ('org/two-b-oq4', 'SKIPPED', 'org/two-b-oq4 could not be downloaded'),
                ('org/two-b-jang', 'SKIPPED', 'org/two-b-jang could not be downloaded')]
```

So every part of the finding is present at once: both refused downloads leave their ledgered
partials on disk, no `evict` is attempted for either, `not_evicted` is empty, the run returns
True and reports `finished`, and each skipped cell states only that the repo "could not be
downloaded" — no `busy`, no message, nothing the fetch layer knew.

## The code path, with line numbers

1. **`fetched` starts False and only a success moves past the branch.** `quickbench.py:851`
   sets `fetched = False`; `:863-866` calls `download(..., emit=_discard)`; `:867-868` folds an
   exception into `reason`; `:869-889` builds the SKIPPED cell and `continue`s.
2. **`outstanding` is populated after the guard.** `:890` `outstanding.add(sibling.repo)` is
   reachable only when `fetched` is true.
3. **The per-cell eviction is gated on the same flag.** `:914-930` runs `evict(...)` only
   `if fetched:` (`:915`); `note_not_evicted` (`:921`) is inside that block.
4. **The run-level sweep cannot see the repo either.** The outer `finally` (`:943-953`) walks
   `sorted(outstanding)`, which never received the failed repo, so the residue survives every
   ending — not only `finished`.
5. **The ending is unchanged by a failed sibling.** `:938-939` turns a still-`running` summary
   into `finished`; `:1019-1020` emits `done: quickbench finished` and returns True. The only
   trace is the SKIPPED cell.
6. **The cause is discarded, not merely dropped by the summary.** `quickbench.py:146-153`
   defines `_discard` as a no-op and documents it as "the sibling fetch's ... events: their
   outcome is quickbench's to report"; `_refuse` puts the code in the `error` event's
   `payload.code` (`fetch.py:439-443`) — `busy` (`fetch.py:708`), `low_disk` (`:823`, `:1150`),
   `integrity_failed` (`:787`, `:794`, `:802`, `:862`, `:897`, `:911`). None of it is read.
7. **The residue is real disk, not bookkeeping.** `fetch.downloaded` treats a `.incomplete`
   alone as not downloaded (`fetch.py:280-283`), so the bytes sit outside every "is it already
   here" question the app asks and count against the free-disk guard the next download must
   pass.

## Reachability

Unlike S4-F8, nothing has to be edited to reach this. A sibling download returns False for an
ordinary network failure, a busy cross-process lock (`fetch.py:707-708`), or the disk guard
(`:1145-1155`); the finding's stated trigger — failing at 2.5 of 3 GB — is the common case.
The only correction to the finding's wording is that the residue is not orphaned forever: it is
on the fetch ledger, so a later successful run of that sibling evicts the repo wholesale, and
the library's Remove path can evict it. But nothing in this run tells the user it is there or
why the download failed.
