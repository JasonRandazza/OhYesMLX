# S1-F5 — `done` is emitted, and frees the job slot, before the download's ledger write and lock release

**Claim, one line:** `fetch._download` emits `done` (and, through `_Job.append`, frees the
server's one job slot) before `download`'s `finally` writes the fetch ledger and releases the
cross-process lock, so `done` is not the last thing that happens and a client that reacts to it
meets a lock that still names this live process and a ledger that does not yet list the repo.

Where the finding lives: `S1-findings.md:48-56`. The dossier has no separate per-finding entry;
the relevant map lines are `dossier-S1.md:119` for `fetch.download` (`fetch.py:662-718`) and
`dossier-S1.md:20` for `_Job`/`_Jobs` (`server.py:153-304`).

The test passes an `emit` callback into `fetch.download`, and when the `done` event arrives it
reads the two files the ordering is about: the lock is still present and the ledger does not
list `org/name`. The transport is the fake from `test_fetch` (same directory, not a package);
the cache, ledger, lock directory and log are all under `tmp_path`. No socket is opened.

The same file carries a supporting check that passes today and states the server half of the
claim: `test_the_job_slot_is_freed_when_done_is_stored_not_when_the_module_returns` — storing
`done` empties `_Jobs.running` before `_run_job`'s module call has returned.

## The code path, with line numbers

1. **The module emits `done` from inside `_download`, then returns.** `fetch.py:1177`
   `send("done", "download finished")`; the other two terminal paths do the same
   (`fetch.py:772` "download cancelled", `fetch.py:887` "already present"). `_download` returns
   immediately after.
2. **The ledger write and lock release only happen in `download`'s `finally`.**
   `fetch.py:711-718`: `try: return _download(...)`, then `finally: if any(created.values()):
   _record(ledger_path, planned, created, clock, send)` (`:716-717`) `; _release_lock(lock_path)`
   (`:718`). `_record` (`fetch.py:721-749`) reads the ledger and does a full atomic write; that
   write is the fsync work the finding timed.
3. **The server frees the slot on the event, not on the call's return.** `_run_job`
   (`server.py:736-741`) hands `emit=job.append` to `fetch.download`. `_Job.append`
   (`server.py:176-202`) treats `done` as terminal (`:183-184`), sets `self.done = True`
   (`:199`) and calls `self._registry.finished(self)` (`:202`). `_Jobs.finished`
   (`server.py:256-259`) clears `running` under the registry lock.
4. **A client acting on `done` meets a held lock.** The next `download` asks `_acquire_lock`
   first (`fetch.py:706-708`) and is refused `busy` naming this live pid; `evict` asks the same
   lock (`fetch.py:1219-1223`) and is refused `busy` too.
5. **If `_record` itself fails, the loss is silent.** `_record` catches `LedgerError` and emits
   only a `log` event (`fetch.py:723-727`), so the ledger can remain without an entry the
   completed download created. That is a second, rarer route to an evict not seeing the repo.

## A refinement to the finding

The sub-scenario "an evict that wins the lock race before `_record` would not see what was just
created" is not reachable: `evict` takes the same lock before it reads the ledger
(`fetch.py:1219-1223`), so it cannot observe the window — it is refused `busy` until
`_release_lock` at `:718`, which runs *after* `_record`. The observable symptom is the spurious
`busy` for either operation (and, independently, the silent `_record` failure above), not a
lost-entry evict. That does not weaken the ordering claim; it narrows one consequence.

## What I did not verify

- A real HTTP/SSE round trip: I did not time `_record`'s fsync against a loopback POST. The
  test shows the deterministic ordering at the emit boundary, which is what makes the race
  possible; the width of the window was not measured.
- `_stream_job`'s delivery of `done` to a socket (`server.py:896-935`) was read, not executed.
- No download, evict or server was started; the lock mechanics were read, and the test only
  asserts the lock file's presence.
