# S4-F7 — A partly-downloaded row is excluded on its full size

**Claim, one line:** a row whose download was interrupted is absent from the `/recommendations`
picks (and so from the only screen that offers Download or Remove) whenever free disk is below
`disk_needed(full size)`, even when free disk covers `disk_needed(bytes still missing)` — the
number `fetch.download`'s own guard uses.

Where the finding lives: `S4-findings.md` F7. `dossier-S4.md` has no per-finding entry for F7;
its hotspot 5 (`dossier-S4.md:359`, the disk guards) and hotspot 7 (`:361`, `downloaded`) are
the two pieces the finding joins.

The test drives the real `_Handler._get_recommendations` with its three injected dependencies
and a captured `_write_json` — no socket, no model, no download. It builds the finding's own
numbers from the catalog's LFM2.5-8B-A1B row (`size_bytes = 4_782_228_614`):

- 80% present as `blob + ".incomplete"` = 3,825,782,891 bytes; remainder 956,445,723 bytes;
- free disk = `disk_needed(remainder) * 1.5` = 1,721,602,302 bytes;
- `disk_needed(remainder)` = 1,147,734,868, so `fetch.download`'s guard passes;
- `disk_needed(full size)` = 5,738,674,337, so `exclusion_reason` excludes.

That is the finding's sentence, generated from the full size, while 1.1 GB would cover the
resume. The second test in the file,
`test_a_row_with_nothing_on_disk_is_still_excluded_on_its_full_size`, is the control: with no
partial and half the full-size margin free, the row is excluded and the test **passes**. So the
failure is the missing remainder term, not "the disk guard is broken" or a mis-shaped fixture;
a fix that simply never excludes would fail the control.

The test targets the response payload rather than `exclusion_reason` directly on purpose:
`exclusion_reason` takes only an all-or-nothing `downloaded` set today
(`recommend.py:122`), so the finding's desired call cannot be expressed against the current
signature without guessing the fix's parameter name. The response is the observable claim and
leaves the internal shape to the fix.

## The code path, with line numbers

1. **The server's `downloaded` set is all-or-nothing.** `server.py:582`:
   `downloaded = frozenset(model.repo for model in models if fetch.downloaded(model))`.
2. **`fetch.downloaded` cannot see a partial.** `fetch.py:272-298` requires, per planned file,
   the snapshot link present, link size equal to the catalog size, the blob present and the
   blob size equal to the catalog size; any miss returns False. Its own docstring says why:
   "a `.incomplete` file alone is not a download, because the snapshot link is written only
   after every file verifies (AC-15)" (`fetch.py:280-282`). The all-or-nothing answer is
   deliberate; nothing else answers "how much is here".
3. **`fetch.download` judges the remainder.** `fetch.py:811-814`:
   `remaining(planned_file) = 0` if the blob is verified present, else
   `max(0, size - _partial_size(blob + ".incomplete"))`; `fetch.py:817-827`:
   `missing_bytes = sum(remaining(...))`, `needed = disk_needed(missing_bytes)`, and the guard
   refuses only when `free < needed`. `_partial_size` (`fetch.py:574-578`) is `os.path.getsize`
   with 0 on `OSError`.
4. **`exclusion_reason` judges the full size.** `recommend.py:139-146`:
   `if model.repo in downloaded: return None`, then `needed = disk_needed(model.size_bytes)`
   and the sentence "Needs about {gb(needed)} GB of free disk to download; this Mac has
   {gb(free)} GB free". A partly-present row is not in `downloaded`, so it reaches this branch
   with the whole artifact's size.
5. **The server never passes a remainder.** `server.py:594-604` hands `hw.disk_free_bytes` and
   the same `downloaded` set to both `recommend.pick` (`:588-597`) and the excluded list
   (`:599-606`). There is no third input, so `exclusion_reason` cannot apply the margin to what
   is left even if it wanted to.
6. **`pick` drops the row before the screen can act on it.** `pick` skips every model with a
   non-None `exclusion_reason` (`recommend.py:183-186`), and the app renders only `picks` as
   `ModelRow`s with a Download button (`app/Sources/OhYesMLX/Screens/ModelsView.swift:28-30`,
   button at `:237-243`) or, when `pick.downloaded`, a "Downloaded" state with Remove
   (`:207-226`). Excluded rows are plain `Text` under "Not recommended for this Mac"
   (`:33-48`) with no control at all. So the finding's qualifying clause is confirmed from the
   source: a partial row has neither Download nor Remove, and `Continue to Benchmark` is
   disabled unless there is a fully downloaded pick (`:58`). The partial is stranded — the app
   shows no way to resume it or to reclaim its 4 GB.
7. **The resume exists and works; the screen just never offers it.** `fetch.download` resumes
   from `.incomplete` through the `Range` path (the behaviour `tests/test_fetch.py::
   resume_sends_a_range_and_writes_only_the_remainder` and `::a_cancelled_download_resumes_and_
   completes` pin), and `disk_guard_counts_missing_bytes_not_the_total`
   (`tests/test_fetch.py:698-709`) pins that its guard counts missing bytes. The contradiction
   is between two shipped rules, not between a rule and its absence.

## One correction to the finding's fix direction

The finding says "fetch's plan already computes it". `fetch.plan` (`fetch.py:204-269`) returns
the `PlannedFile` list (each with its `blob` path) and the total `size_bytes`; it does **not**
compute a partial-aware remainder. That arithmetic exists only inside `_download`
(`fetch.py:811-818`, with `_partial_size` at `:574`). The fix direction is still right — one
definition of bytes-still-to-fetch, asked by both the guard and the recommendation — but the
definition has to be lifted out of `_download` (or recomputed from `plan` + `_partial_size`),
not merely called from where it already is.

## Severity check

Medium holds. The failure is user-visible and self-contradicting: the app says the download
"needs about 5.7 GB" when 1.1 GB would finish it, removes the only control that could resume
it, and offers no way to remove the 4 GB already spent — in exactly the interrupted-download
scenario the resume path exists for. It is not higher: nothing is corrupted or discarded, no
measurement or number is published from the partial, and the user can recover by freeing disk
(the row returns once free disk clears the full-size margin) or by clearing the cache outside
the app. It is not lower because the misleading sentence and the stranded bytes are both shown
on the main onboarding screen, and the failure needs no unusual state beyond an interrupted
download on a Mac that is short of space.
