# S3-F14 — any failure to open or lock `app.lock` is reported as "already running" and the app quits silently

**Claim (one line):** `acquireLock` returns nil for an `open` failure and for every `flock`
failure, and `BackendLauncher.start` maps nil to `.alreadyRunning`, so an unusable lock path is
reported as another instance and the app activates that (nonexistent) instance and terminates
with no message.

## Reproduction

`app/Tests/OhYesMLXKitTests/FableS3F14Tests.swift`, one test: point `appSupportDirectory` at a
fresh temporary directory in which `app.lock` is a **directory**, so `open(2)` on the lock path
fails with EISDIR. A launcher whose interpreter resolves and whose process factory would hand back
a fake is then started.

```
$ cd app && OYMLX_DEV_PYTHON=…/app-dev-venv/bin/python swift test --filter FableS3F14Tests
FableS3F14Tests.swift:32: error: -[OhYesMLXKitTests.FableS3F14Tests testAppLockThatCannotBeOpenedIsNotAlreadyRunning]
  : failed - a lock path that could not be opened was reported as another instance
Test Case '-[OhYesMLXKitTests.FableS3F14Tests testAppLockThatCannotBeOpenedIsNotAlreadyRunning]' failed (0.001 s).
```

The case that fired is `.alreadyRunning`, with no second instance anywhere on the machine.

## Code path, as cited — every line number verified

- `app/Sources/OhYesMLXKit/BackendLauncher.swift:260-269` — `acquireLock`:
  - `:262-263` — `let descriptor = open(path, O_CREAT | O_RDWR, S_IRUSR | S_IWUSR)`; `guard
    descriptor >= 0 else { return nil }`. Every `errno` is collapsed to nil: `EACCES` (Application
    Support unwritable), `EISDIR` (the test), `ENOSPC`, `ENAMETOOLONG`, …
  - `:264-267` — `if flock(descriptor, LOCK_EX | LOCK_NB) != 0 { close(descriptor); return nil }`.
    Only `EWOULDBLOCK` means "another process holds it"; `ENOLCK`, `EBADF`, `EINTR` are also
    collapsed to nil.
- `BackendLauncher.swift:170-172` — `guard let lockFD = acquireLock() else { return
  .alreadyRunning }`. The outcome carries no message (contrast `:163` and `:167`, the
  `couldntStart` returns either side of it, which carry the path and the reason).
- `AppModel.swift:369-381` — on `.alreadyRunning` the model sets `alreadyRunning = true` and
  returns; it does not set `launchError` and does not leave `.launching`, so no error screen can
  render.
- `OhYesMLXApp.swift:40-49` — `onChange(of: model.alreadyRunning)` looks up
  `NSRunningApplication.runningApplications(withBundleIdentifier:)`, takes `.first?`, activates it
  if it exists, and calls `NSApp.terminate(nil)` unconditionally. With no other instance the
  `.first?` is nil, so nothing is activated and the app quits.
- `OhYesMLXApp.swift:88-95` — the terminate goes through `applicationShouldTerminate`; `shouldExit`
  is false, so it returns `.terminateLater` and awaits `requestQuit`. With a live `runner` of nil
  at this point (`adopt` never ran — `launch` returned before it), `requestQuit` takes the `guard
  let runner else { finishQuit(); return }` branch (`AppModel.swift:565-568`) and the app exits.
  No dialog is presented at any point.
- `prepareAppSupport` (`:243-254`) is not a guard against this: it only creates the directory when
  it does not exist. It does not check writability, and an existing non-directory or an
  unreadable directory passes through to `open`.

## What I did not verify

- The unwritable-Application-Support variant (`EACCES`) and the `ENOLCK` variant were not
  reproduced; they take the same two `return nil` lines, so the class of failure is the same.
- The real second-instance path (`.alreadyRunning` for the right reason) is covered by the
  existing launcher tests and was not re-run here; this finding is only about the wrong reason.
- I did not run the app bundle to watch it terminate; the terminate path is cited, and the
  `.alreadyRunning` state is what the test stops at.

VERDICT: CONFIRMED (test: app/Tests/OhYesMLXKitTests/FableS3F14Tests.swift::testAppLockThatCannotBeOpenedIsNotAlreadyRunning)
SEVERITY-CHECK: agree — Low. It is a launch failure, not data loss, and it needs an unusual lock path (unwritable or non-file); but the one symptom the user sees is the app refusing to open, with nothing anywhere saying why.
