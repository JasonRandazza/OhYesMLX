# S2-F7 — a lost second visit fails the row; a lost first visit is an annotation

**Claim (one line):** `_visit` writes `FAIL` on a row that already holds samples and returns
`"retry"`; the reason goes into `run_cells`' `lost` dict, which only a later *measured* visit
consumes — so a lost second visit ends as `FAIL` with `lost_visit_reason` never written, while
the mirror case (first lost, second measured) is `PASS` with an annotation.

**Verdict:** reproduced as an asymmetry in behaviour. Whether the asymmetry is a defect is a
contract question, not a code question, and the contract's sentence reads the other way.

## Code path

- `ohyesmlx/measure.py:843-852` — the start's failure handler:

  ```python
  except Exception as error:
      reason = f"runtime {cell.runtime!r} did not start: {type(error).__name__}: {error}"
      for result in results:
          if result.observations:
              result.status, result.reason = "FAIL", reason   # :849
          else:
              _na(result, reason)                             # :851
      return "retry"                                          # :852
  ```

  A row that already holds samples is set `FAIL`; a row with none is `N/A`.
- `ohyesmlx/measure.py:654-668` — the consumer:

  ```python
  if outcome == "measured":
      reason = lost.pop(cell.id, None)
      for result in cell_results:
          if reason is not None:
              result.lost_visit_reason = reason               # :661
              result.cold_load_after_lost_visit = ...          # :662
          _set_status(result)                                # :663
  elif outcome == "retry":
      lost[cell.id] = cell_results[0].reason                 # :668
  ```

  `lost_visit_reason` is written **only** inside the `"measured"` branch. A final visit that
  returns `"retry"` leaves `lost[cell.id]` populated and nothing consumes it.
- `ohyesmlx/measure.py:1231-1234` — `_set_status` returns early when there are no observations,
  leaving whatever reason the visit wrote. But the second-lost row **does** have observations, so
  the early return does not apply; the `FAIL` set at `:849` stands because no later
  `"measured"` outcome overwrites it.

The two outcomes are therefore decided by which visit index failed, with identical healthy
samples in hand.

## The contract sentence, and why this is a decision rather than a verdict

`docs/interfaces/sweep-pins.md:185-186`:

> Three additions, all of them annotations and none of them floors — the same rule drift follows:
> a window that was short is a result, and dropping it would delete the only row that says so.

`docs/interfaces/sweep-pins.md:217-220` adds that the lost-visit note rides the card "beside the
status whose reason it is not. Neither is a floor and neither moves a published number."

The lost **first** visit follows this exactly: the surviving samples decide, the loss is an
annotation, the row ranks. The lost **second** visit does not — it is a floor, and it deletes a
row that had already measured. The finding is right that "nothing read says" the second direction
should differ.

The counter-argument the finding raises and I cannot settle is also real: a cold visit that never
happened and a hot visit that never happened are different losses, and a cell with only half its
planned requests may be one the harness should not rank. If that is the intent, the contract
sentence needs to say so, because as written it reads the other way.

One existing test pins the current behaviour deliberately:
`tests/test_measure.py::test_a_visit_that_fails_last_changes_nothing_new`, added in `0898fd7`
("A lost visit keeps its reason and a short window says so") — the same commit that introduced
`lost_visit_reason`. Its docstring says "the row keeps the failure as its own reason, as it always
did", which is a statement of the current shape, not a rationale for the asymmetry.

## Consequence, for what it is worth

Quickbench drives `warmup=3, measured=5` (`quickbench.py:61-62`), so its cells split 3 + 2. I
stubbed `run_cells` to return the row a lost second visit leaves (`FAIL` with three healthy
samples) and ran the real `quickbench.run`: `status: FAIL, decode_tps: 60.0` in the summary and
`best = None`, so stage B does not run and the run reports
`no stage-A cell passed, so there is no winning engine to hold constant for stage B`. A transient
second `start()` on an otherwise healthy cell therefore loses the user's whole benchmark — and,
through F1, publishes the failed cell's rate beside the word Failed.

## What I did not verify

- I did not verify that a transient second `start()` happens in practice. The finding names a
  port not yet released and the Osaurus relaunch race; `_visit`'s own docstring (`:760-762`) calls
  the port-held case "usually deterministic" but not always, which is why `"retry"` exists.
- I did not change the code or decide the direction. The test is red until someone decides.
- I did not check whether the `cold_load_after_lost_visit` bookkeeping would need a second form
  for the reversed case (a first visit that measured and a second that did not leaves the *first*
  start's cold load in place, which is correct, so probably not).
