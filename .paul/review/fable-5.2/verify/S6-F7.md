# S6-F7 — check_bundle's P5-9 environment check

**Claim, one line:** on this Mac (Darwin 27.2.1) `ps eww` returns no environment for another
process, so `scripts/check_bundle.sh`'s `*)` branch FAILs P5-9 and the AGENTS.md packaging gate
can never print "all checks PASS" — which would make `docs/threat-model.md:606`'s P5-9 evidence
unobserved — *or* the script's comment is false; and when the block is readable, its PATH and
PYTHON matches are substrings that accept what they name as failures.

**What is true:** the substring half is real and reproduced by test.
**What is false:** the contradiction half. The environment *is* readable for the process this
check inspects, the block prints two PASS, and the gate reaches "all checks PASS" on this OS.

---

## 1. The experiment the finding asked for, and why it lands on the wrong side

The finding says the question is "settled by one `ps eww -p <own pid> -o command=` on this OS".
Run that literally:

```
$ ps eww -p $$ -o command=
/bin/sh -c ps eww -p $$ -o command= ...        # argv only, no KEY=value pairs
```

It appears to confirm the comment. It does not: `$$` is `/bin/sh`, an Apple platform binary, and
`ps` withholds the environment of Apple platform binaries on this OS. The command is only
decisive when run against a process of the same signature class as the backend.

## 2. The controlled comparison

Same shell, same OS, one variable changed — the target's signature:

| target | `ps eww -p <pid> -o command=` |
|---|---|
| `/bin/sleep 30` (Apple platform) | `/bin/sleep 30` — no env |
| `/usr/bin/yes MARKER_Y` (Apple platform) | argv only (`grep -c 'PATH='` → 0) |
| Finder (Apple platform, launchd) | `/System/Library/CoreServices/Finder.app/Contents/MacOS/Finder` |
| `cp /bin/sleep X; codesign --remove-signature X; codesign -s - -f X` (ad-hoc) | `X 20 MARKER_A=adhoc NVM_INC=… PATH=… HOME=…` — full env |
| `~/.local/share/ohyesmlx/test-venv/bin/python -I -B -c '…sleep…'` (ad-hoc, linker-signed) | full env, `MARKER_F7=xyzzy` present |

The ad-hoc process spawned the way a GUI app's child is spawned is also readable:

```
$ osascript -e 'do shell script "MARKER_L=via-launchd <scratch>/sleep-adhoc 25 >/dev/null 2>&1 &"'
$ /bin/ps eww -p <pid> -o command=
<scratch>/sleep-adhoc 25 MARKER_L=via-launchd …
```

So `ps eww` on this Darwin 27.2.1 does expose another process's environment; it does not for
Apple platform binaries.

## 3. The backend is on the readable side

`scripts/build_app.sh:95` signs every Mach-O in the tree with `codesign --force --sign -`
(ad-hoc); `:105-106` do the same for the app. The shipped artifact confirms it:

```
$ codesign -dv --verbose=2 /Users/jrazz/Dev/active/OhYesMLX/dist/OhYesMLX.app/Contents/Resources/python/bin/python3
CodeDirectory v=20400 size=38121 flags=0x2(adhoc) … Signature=adhoc
```

No `Platform identifier`, unlike `/bin/sleep` (`Platform identifier=27`). The backend also lives
under `Contents/Resources/python/bin`, not a SIP path. The exact discriminator (platform signature
vs SIP-protected location) cannot be separated by my controls — the platform-signed copy at a new
path was killed by the kernel at launch, so it gave no reading — but both candidate rules put the
backend on the readable side, so the conclusion does not depend on which one it is.

## 4. The script's own block, fed the real `ps` output

A process whose whole environment is the launcher's six keys (`BackendLauncher.swift:116-117,
213-214`), ad-hoc signed like the backend:

```
$ env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin HOME=/tmp USER=tester LOGNAME=tester \
      TMPDIR=/tmp LANG=en_US.UTF-8 <scratch>/sleep-adhoc 20 &
$ /bin/ps eww -p $! -o command=
<scratch>/sleep-adhoc 20 PATH=/usr/bin:/bin:/usr/sbin:/sbin HOME=/tmp USER=tester \
LOGNAME=tester TMPDIR=/tmp LANG=en_US.UTF-8
```

That single line, passed to `scripts/check_bundle.sh:214-231` extracted verbatim, prints:

```
PASS P5-9: the backend's PATH is launchd's default
PASS P5-9: the backend carries no PYTHON* variable
COUNT = 0
```

So the `*)` branch at `:229-230` is not taken for the backend, the section reports no failure, and
`all checks PASS` at `:263` is reachable with the P5-9 section included. `docs/threat-model.md:606`
("check_bundle P5-9: the backend's PATH is launchd's default and it carries no PYTHON* variable")
is exactly what this path prints, so it is consistent with the script — and the evidence could have
been produced on this OS build: `softwareupdate --history` dates macOS 27.2.1 to 2026-11-10, four
days before the 2026-11-14 status table, and `kern.boottime` shows no reboot since.

**The false published statement is the script's comment at `:209-212`** ("macOS no longer exposes
another process's environment: on 27.2.1 `ps eww`, `ps -E` and KERN_PROCARGS2 all return the argv
with no environment block"). It is false as written and false for the process the check reads.
The consequence the finding draws from it — an unmeetable gate and an unobservable P5-9 row — does
not follow. The "decision" the `*)` message asks for is moot for this backend, and making the
withheld case a SKIP would remove a fail-closed branch on the strength of a false premise.

## 5. The half that is real

`scripts/check_bundle.sh:217` matches `*"PATH=/usr/bin:/bin:/usr/sbin:/sbin"*` and `:223` matches
only `*"PYTHONPATH="* | *"PYTHONHOME="*`. The test file reads that `case` block and the script's
own `pass`/`fail`/`FAILURES` helpers out of `check_bundle.sh` (so the test cannot drift from the
script) and feeds it fixtures:

- `… PATH=/usr/bin:/bin:/usr/sbin:/sbin:/opt/homebrew/bin` → prints *"the backend's PATH is
  launchd's default"* and `COUNT=0`. Must be a FAIL.
- no `PATH` at all, `MANPATH=/usr/bin:/bin:/usr/sbin:/sbin` → same PASS, because `MANPATH=` ends in
  `PATH=`. Must be a FAIL.
- `PYTHONEXECUTABLE=/tmp/x` → prints *"the backend carries no PYTHON* variable"*. The message names
  `PYTHON*`; the pattern names two variables.

Three tests fail on the shipped script (`3 failed, 1 passed` — the happy path passes), and all four
go green against a copy in the scratchpad with the match narrowed to whole space-delimited tokens
(`case " $ENV_DUMP " in` + `*" PATH=… "*`, `*" PYTHON"[A-Z]*=*`), so the tests are satisfiable and
discriminate. `check_bundle.sh` itself was not edited, per the order.

This is latent rather than live: the launcher's environment is a fixed six-key dictionary
(`BackendLauncher.swift:117`), so `MANPATH`, a homebrew PATH, or `PYTHONSTARTUP` cannot appear
today. The check's assertion is weaker than its message, not wrong about the current bundle.

## What I did not verify

- **I did not run `scripts/check_bundle.sh`.** Its P5-6/P5-9 section launches the app and writes
  `~/Library/Application Support/OhYesMLX`, both forbidden to this role, and this worktree has no
  `dist/`. Sections 2-4 reproduce its exact `ps` invocation and its exact `case` block instead.
- **I did not read the real backend's environment** (that needs the app running). The ad-hoc probe
  stands in for it; the signature of the shipped `python3` is the link, and it is inspected, not
  assumed.
- **The mechanism is inferred, not documented.** I did not find an Apple statement of the rule; the
  observation is that Apple platform binaries hide the environment and ad-hoc-signed ones do not.
  A future macOS could change this, and then the `*)` branch would fire — fail-closed, which is the
  right direction but would need the SKIP the finding describes.
- **Other macOS releases** (26.x, other 27.x) were not tested; only 27.2.1 build 26B131.
- I did not check whether a PATH containing a space could forge the padded token match proposed in
  §5; that is fix design, not this review.

VERDICT: REFUTED (on Darwin 27.2.1 `ps eww -p <pid> -o command=` prints the full environment of an ad-hoc-signed process — the class `build_app.sh:95` puts the bundled `python3` in (`codesign`: `flags=0x2(adhoc)`, no platform identifier) — and fed that live dump the script's own block at `check_bundle.sh:214-231` prints two PASS with `COUNT=0`, so the `*)` branch is not taken, "all checks PASS" is reachable, and `docs/threat-model.md:606` is consistent with the check; the false statement is the comment at `:209-212`, which reads `ps eww` against Apple platform binaries (`/bin/sh`, `/bin/sleep`, Finder) that hide it; the surviving substring/PYTHON* weakness is real and proved by `tests/test_fable_s6_f7.py`)

SEVERITY-CHECK: lower to Low — the headline failure ("the gate cannot print all checks PASS", "the P5-9 evidence was not observed") is refuted: the gate passes on this machine and the threat-model row matches what the script emits, so no published security claim is false. What remains is a `case` pattern weaker than its own message (`PATH` prefix-superset, any `*PATH=` variable, two of the `PYTHON*` names) and a comment that misstates macOS; the launcher's fixed six-key environment means none of the false-positive fixtures can occur in the shipped bundle today, so this is a precision defect in a coordinator-run script, not a wrong number or an unverified security property.
