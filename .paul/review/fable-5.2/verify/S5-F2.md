# S5-F2 — `cold_load_s` includes the version probe and an `lsof` call

**Claim restated:** `Runtime.start` takes its clock before `_spawn` and stops it only after
`await_ready`, `self.version()` and `_serving_pid` have all returned, so the published
`cold_load_s` carries a per-runtime subprocess constant that is not load time.

**Verdict: confirmed, and the bias is larger than the finding estimated.**

## The code, as shipped

`ohyesmlx/runtimes.py:2317-2344`:

```
2317        started = _now()
2318        pid = None
2319        try:
2320            pid = _spawn(command, log_path)
2321            resolved = self.await_ready(              # <- the load time
2327            version = self.version()                  # <- a subprocess, 30 s ceiling
2328        except BaseException as start_error:
2339        _RUN_STARTED_PIDS.add(pid)
2340        serving_pid = _serving_pid(pid, self.port)    # <- lsof -nP -iTCP:<port> -sTCP:LISTEN -t
2344        cold_load_s = _now() - started
```

`Runtime.version` (`:2120-2130`) has no memo: `result = _run(command, VERSION_TIMEOUT_S)` runs
on every start, unconditionally. `_serving_pid` (`:749-771`) calls `_listener_pids`, which runs
`lsof` (`:717-731`). Both are inside the window.

The intent is stated two lines above the measurement (`:2342-2343`) but only half-executed:
*"the ledger entry is written after the load time is taken, so no measured `cold_load_s`
contains the `ps` calls"* — true of the ledger's `ps` calls, false of the version subprocess and
the `lsof` next to it.

## The spec says this is wrong, in writing

- `docs/interfaces/measurement-core.md:132` — `cold_load_s: float  # spawn -> ready. Its own metric`
- `docs/interfaces/measurement-core.md:278` — *"`cold_load_s` is spawn until `await_ready` returns."*
- `ohyesmlx/runtimes.py:3306-3310`, the vMLX `version_command` comment, records the coupling as
  already measured: *"the import ... measured 9.2s, **which `start()` times as part of cold
  load**, and cold load is a published metric that must not carry harness overhead."* The
  comment says the metric must not carry harness overhead; the code puts harness overhead in it.

## Reproduction

`tests/test_fable_s5_f2.py::test_cold_load_s_does_not_include_the_version_probe_or_lsof`

The injected clock advances 2.0 s at `_spawn` (the load), 5.0 s in `_run` for the version
command and 0.5 s in `_run` for `lsof`. The inventory answers on the first poll, so no readiness
poll sleeps. Nothing is started, loaded or signalled; only the clock and the module's own
outward seams are faked.

```
$ /Users/jrazz/.local/share/ohyesmlx/test-venv/bin/python -m pytest -q tests/test_fable_s5_f2.py
E  AssertionError: cold_load_s carries the helper probes: the version subprocess costs 5.0s
E  and the lsof listener probe 0.5s, and the metric reported 7.5s for a 2.0s load
E  assert 7.5 == 2.0 ± 2.0e-06
1 failed
```

**Attribution is isolated, not inferred.** The same seams, varying one probe at a time:

| spawn | version probe | lsof | reported `cold_load_s` |
|---:|---:|---:|---:|
| 2.0 | 0.0 | 0.0 | **2.0** |
| 2.0 | 5.0 | 0.0 | **7.0** |
| 2.0 | 0.0 | 0.5 | **2.5** |
| 2.0 | 5.0 | 0.5 | **7.5** |

**Red-check (counterfactual, no file edited).** `Runtime.start` re-bound in memory to a body
byte-identical to the shipped one except that `cold_load_s = _now() - started` runs immediately
after `await_ready`. The test's assertion then holds exactly:

```
fixed ordering: cold_load_s=2.0 version=9.9.9
PASS: the test's assertion holds (2.0s) when the clock stops at readiness
```

So the test discriminates on precisely the ordering the finding names, and on nothing else. The
second assertion (`handle.version == "9.9.9"`) rules out the wrong fix — dropping the probe
instead of moving it.

## Size of the bias, measured on this host

Each runtime's real `version_command`, timed through the module's own `_run` (median of 3):

| runtime | command | median s |
|---|---|---:|
| mlxlm | `python -m mlx_lm --version` | **1.193** |
| optiq | `optiq --version` | **1.177** |
| osaurus | `osaurus doctor --json --redact` | 0.308 |
| mtplx | `~/.mtplx/bin/mtplx --version` | 0.081 |
| omlx | `omlx --version` | 0.053 |
| vmlx | `sed -n …/vmlx_engine/__init__.py` | 0.005 |
| — | `lsof … -t` on an idle port | 0.100 |

The spread across the six is **1.19 s / 0.005 s ≈ 240×**, which is what makes this a
cross-runtime contamination and not a constant offset.

Against the `cold_load_s` values actually on disk in the main checkout (263 run files, 1289
rows; p50 per column):

| column | p50 published | probe + lsof | share of the number |
|---|---:|---:|---:|
| vmlx 1.6.59 | 7.07 | 0.11 | 1% |
| omlx 0.6.4 | 2.12 | 0.15 | 7% |
| **optiq 0.5.13** | **3.27** | **1.28** | **39%** |
| **osaurus 0.25.x** | **1.30** | **0.41** | **32%** |
| **mlxlm 0.31.3** | **2.51** | **1.29** | **51%** |

The finding's "a 1-2 s interpreter import on top of a 4 s load is tens of percent" was
conservative. On the mlx-lm column **half** the published cold-load figure is a version probe.
Corrected, the mlx-lm and OptiQ columns land at 1.22 s and 1.99 s — which reorders mlx-lm from
slowest-but-one to the fastest loader in that set.

Caveat I will not paper over: those p50s are per-column medians over 263 *different* runs, not a
same-artifact grid, so the table above sizes the bias and does not itself prove an inversion of a
published ordering. Zero same-artifact cross-runtime groups exist in the recorded corpus (I looked).
The claim that stands on the recorded data is the per-runtime share; the reordering is arithmetic
on it.

## Scope of the defect

`started`/`self.version()` in this order dates from the measurement core's first commit
(`b1fc311`), so **every** published `cold_load_s` carries it — this is not a recent regression.

Severity: the report already refuses a cross-runtime ordering on `cold_load_s`
(`CROSS_RUNTIME_UNCOMPARABLE`, `report.py:304-316`), and the documented cross-runtime comparison is
`cold_load_s + first_request_s` (`measurement-core.md:291`). So the harm is not a ranked table built
from this column alone; it is (a) the number itself, which is published per row and is a cold-start
metric by AGENTS.md definition, and (b) the recommended sum, which carries the same constant. Within
one runtime column the constant repeats, so a format-axis comparison absorbs it — the defect is
specifically the runtime axis and the absolute figure.

## What I did not verify

- No runtime was started, no model loaded, no grid re-measured. The probe timings above are the
  probe subprocesses only, run standalone; a cold-page-cache first run of `python -m mlx_lm
  --version` could be worse than the 1.19 s median (a separate `/usr/bin/time` on a fresh shell gave
  1.18 s and 1.20 s, consistent).
- I did not measure the bias on the runs that produced the p50s (different host state, different
  dates), and I did not re-derive any published table.
- The 9.2 s figure in the vMLX comment is the repo's own record; I did not reproduce it (the vMLX
  engine import is inside an app bundle I did not import).
