## The claim, in one line

`docs/release/gatekeeper.md:52` tells the user a sha256 is published next to the zip, but
`scripts/build_app.sh` never computes one (its last line `:129` prints `$APP`, `$ZIP`,
`$SBOM` only), no other release step exists, and `scripts/make_sbom.py:128-147` records no
digest of the zip, the Swift binary or the bundled tree — while `gatekeeper.md:30-31`
credits the ad-hoc signature with telling that the files "have not been changed since they
were built", which an ad-hoc signature cannot do against anyone who re-signs.

## The signature limb, by command

The same experiment run by hand in the session scratchpad:

```
== sign ad hoc ==
Probe.app: replacing existing signature
== verify (1) ==
exit=0
== replace the sealed executable, no re-sign ==
Probe.app: code has no resources but signature indicates they must be present
verify exit=1
== re-sign ad hoc as any third party would ==
Probe.app: replacing existing signature
== verify (2) ==
exit=0
== identity ==
Identifier=invalid.verifier.probe
Signature=adhoc
TeamIdentifier=not set
```

The first verification failing is the one thing the seal does: it notices a file changed
after signing. It does not survive re-signing, and re-signing is one command available to
anyone. Because the signature carries no developer identity — `TeamIdentifier=not set`, no
`Authority=` — a downloader has no way to distinguish the builder's ad-hoc signature from a
repackager's. `gatekeeper.md:30-31`'s "macOS can tell the files have not been changed since
they were built" therefore describes a property that macOS checks against *whatever
signature is present*, not against the build the release notes claim. The finding's
statement — alter the zip, re-sign, it verifies — is exactly what the probe shows.

Note the narrower truth the doc could have claimed: `build_app.sh:107` and `:122` verify the
bundle before zipping, so accidental damage or a stray `.pyc` written during the SBOM step
is caught at build time. That is a build-time guard for the builder, not evidence available
to a downloader, and the zip is created after the last verify (`:124-126`).

## Claim by claim

- **No step produces the promised sha256** — confirmed. `build_app.sh`'s only `shasum`
  occurrence is a header comment; the last line prints three paths; no other release script
  exists (`ls scripts/`); the 0.3.0 release directory has no `.sha256`.
- **The doc tells users to compare that value** — confirmed, `gatekeeper.md:52-56` and `:98`.
- **The plan never asked for the producing step** — confirmed. AC-5 requires the doc
  sentence; AC-2 requires the zip; Task 1 allows `shasum` but requires no digest output.
  This is a plan gap as well as a code gap: a doc promise was accepted with no artifact
  deliverable behind it.
- **The SBOM cannot be tied to the zip** — confirmed. No field is a digest of the zip, the
  Swift binary or the bundled tree; the zip's actual digest appears zero times in the
  shipped SBOM. (The SBOM does pin the interpreter tarball and every engine package hash,
  so it is not worthless — but it cannot tie itself, or the app, to the downloaded file.)
- **The ad-hoc signature is credited with tamper evidence it does not give** — confirmed by
  the probe. It detects post-signing modification only until someone re-signs, and it names
  nobody, so it cannot tell a downloader who built the zip.
