# S1-F4 — The retry budget is cumulative per file and its exhaustion deletes a valid partial

**Claim (one line).** `_fetch_file`'s `attempts` counter is initialised once per file and is never
reset when a pass makes progress, so on the fourth short close anywhere in the transfer the
`attempts + 1 >= MAX_ATTEMPTS` branch calls `size_mismatch(..., remove=incomplete)` and unlinks every
byte correctly received so far — the same partial a user cancel deliberately keeps for a resume.

**Dossier.** `/Users/jrazz/Dev/active/OhYesMLX/.paul/review/fable-5.2/dossier-S1.md:119` — "`_fetch_file`
(:906-1122) — `.incomplete` symlink refused (:908-914), Range resume with strict `Content-Range`
checks (:1024-1055), over-length and short transfers refused, 403/410 re-resolved exactly once
(:984-998)… `fetch_file` (:1124-1135) keeps failed residue on the ledger so evict can remove it."
The dossier records the short-transfer refusal but does not distinguish a size contradiction from a
transport drop, which is the defect.

## Code

- `ohyesmlx/fetch.py:916` — `attempts = 0`, set once, before `while True` at `:922`. No assignment to
  `attempts` exists inside the loop except `attempts += 1` on the three failure paths (`:953`, `:1015`,
  `:1120`). Confirmed by grepping the function: the only resets are the initialiser.
- `ohyesmlx/fetch.py:1110-1120` — after a pass ends short:
  `if written == planned_file.size: return finish(...)` else
  `if attempts + 1 >= MAX_ATTEMPTS: return size_mismatch(f"{path}: the transfer ended at {written} of
  {size} bytes", path=..., remove=incomplete)`. The budget counts every short close in the file's
  lifetime, not consecutive failures, and the refusal deletes the partial.
- `ohyesmlx/fetch.py:775-778` — `size_mismatch` calls `_remove(remove)` (`:581-585`) before refusing, so
  the deletion is unconditional on the message's cause.
- `ohyesmlx/fetch.py:766-772` — the contrast the finding names: a cancel emits "the partial file is kept
  for a resume", and never calls `_remove`. Existing tests prove it:
  `tests/test_fetch.py:1049` `test_cancel_keeps_the_partial_links_nothing_and_releases_the_lock` and
  `tests/test_fetch.py:1079` `test_a_cancelled_download_resumes_and_completes`.
- `MAX_ATTEMPTS = 4` (`:78`), `BACKOFF_S = 0.5` (`:79`).

## Not verified

- The magnitude claim (20 GB, gigabytes of progress per pass) is not run; the code path is
  size-independent and the harness cannot download. The byte counts are the full evidence the code
  offers.
- I did not test the interaction with `fetch_file`'s residue ledger (`:1124-1135`): the branch is
  guarded by `os.path.lexists(residue)`, so a deleted partial records nothing and `evict` has nothing
  to clean. Consequence is limited to re-download, not to a stale ledger entry.
- Whether the design intends "four drops anywhere in a file's lifetime fails the file" is not stated
  in `docs/interfaces/` or the AC list; I verified the behaviour, not the intent.

SEVERITY-CHECK: agree — no corruption and no published number: the deleted bytes are a valid prefix
and `_verify` guards the completed file, so the cost is bandwidth and a silent retry from zero. Two
notes that do not raise it: the refusal is labelled `size_mismatch` (a content contradiction) when it
is a transport failure, so the record misnames the cause; and on a flaky link four drops anywhere in

a reliability ceiling worth the fix direction's one-line reset, but still Low.
